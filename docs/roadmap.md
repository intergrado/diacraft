# Roadmap

> **Last reviewed:** 2026-10-31

The target is the reference app's desktop edition. The reference app was not inspected, nothing was launched or measured, and our output has not been opened in it by the project. Milestones, the current focus, and what comes next. No hours or dates until M1 sets the parity count. Order, not scope: features that come late stay in the count.

## Current focus

The first public release, 0.2, with DiaCraft's own `.diacraft` format as the default (the 0.2 row below), beside the editor's slices (M3), the libraries (M5) and the baseline (M1) that feed them. A functional desktop app comes first, and it exists: it opens, draws, edits and saves drawings.

## Shared libraries (carves into craft-libs)

The owner's rule (2026-11-07, 2026-11-08): reuse the other Craft apps' engines through craft-libs rather than build them again, and use what is carved as soon as possible. Each carve follows the route `craft-pathops` set:
- a crate in craft-libs, opened as a pull request from the one-bit fork;
- DiaCraft depends on the fork, pinned to a pushed revision, until the pull request is accepted, then on storytold;
- no DiaCraft or the reference app names in public;
- bugs the source app shares are reported to it in one batch once the pull request is ready.

## Out of scope by policy

Decisions not to follow the reference app, with the reason. Each still keeps a file's data whole.

| What | Decision | Why |
|---|---|---|
| VBA macros and COM add-ins (owner, 2026-11-07) | VBA and add-ins are out of scope by policy (owner, 2026-11-07), the stance GridCraft, WordCraft and DeckCraft take: a drawing's VBA project (`.vsdm`, `.vssm`, `.vstm`), with its signature parts, is kept byte for byte by every save and is never run, read or edited; saving it as a macro-free type asks first (`drop_macros`). Automation is the command registry, reached by the window, the control channel, the CLI and MCP; extending the app will go through the shared Craft plugin host when craft-libs has one (WebAssembly plugins, craft-libs RFC #414), not through VBA or COM add-ins. | Running macros from files is a common route for malware, a VBA engine and the reference app's object model are each a large project, and the other Craft apps already took this stance |
