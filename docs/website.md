# DiaCraft website

The public website is two sites, each a Cloudflare Pages project of its own (the owner, 2026-11-23: "I'd like to use the .dev for the website and the .app to serve the web app"). **The pages**, the contents of `site/`, are `https://diacraft.dev`. **The web app** is `https://diacraft.app`: `cargo xtask site --web` makes it into a folder of its own with the app at its root and a `_headers` file of its own (see "The web app"), and the pages link it. Each page contains its text, navigation and download links as HTML. The home page loads one optional script to look up the latest release. Preview the pages from the repository root with `python3 -m http.server --bind 127.0.0.1 --directory site 8000` and visit `http://127.0.0.1:8000/` (the links to the app go to `https://diacraft.app/`). To preview both, make them with the app's address on this machine, `cargo xtask site --web --app-url http://127.0.0.1:8101/` (or `DIACRAFT_APP_URL`: the option wins), and serve each folder: `python3 -m http.server --bind 127.0.0.1 --directory dist/site 8100`, and `dist/app` on port 8101. A plain file server applies neither `_headers`.

## Prepare a release

Edit [site/site.json](../site/site.json). This is the source of the publication settings.

| Field | Value to supply |
|---|---|
| `domain` | The HTTPS origin of the pages, with the hostname that readers should see: `https://diacraft.dev`. |
| `app_url` | The HTTPS origin of the web app, a site of its own: `https://diacraft.app`. The pages' "Open DiaCraft in your browser" links go to it, and it is the one other site (beside GitHub's) the pages may name. It is never the pages' own origin. |
| `repository` | The public GitHub owner and repository name, as `owner/name`. |
| `assets` | An object with the asset filename of each of the fourteen downloads, keyed by the download's id (`<system>-<cpu>-<kind>`: `linux-x86_64-appimage`, `linux-x86_64-deb`, `linux-x86_64-targz`, `linux-arm64-appimage`, `linux-arm64-deb`, `linux-arm64-targz`, `windows-x86_64-msi`, `windows-x86_64-zip`, `windows-arm64-msi`, `windows-arm64-zip`, `macos-arm64-dmg`, `macos-arm64-zip`, `macos-x86_64-dmg`, `macos-x86_64-zip`), as the release workflow makes them (`release.yml`; [Releasing](releasing.md)). Use the exact name, or use `{tag}` for the release tag and `{version}` for that tag without a leading `v` before a digit: the files of the release are named `diacraft-{version}-linux-x86_64.AppImage` and so on (the names an app launcher reads, `diacraft-<version>-<system>-<cpu>[-portable].<extension>`, so `aarch64` for Linux on ARM, `x64` for Windows on Intel or AMD, and `-portable` on the Windows zips). **The ids are the site's own keys and keep the CPU as the site says it** (`linux-arm64-deb` is the file `diacraft-{version}-linux-aarch64.deb`, `windows-x86_64-zip` is `diacraft-{version}-windows-x64-portable.zip`). A missing or an extra id is refused, and `--release` refuses an empty name. A link of a page names its download in `data-download`, and `--write` gives it the name as `data-asset`; a test holds `site.json`, the workflow's list of files and the home page to the same fourteen. |

Run these commands after choosing the settings.

```sh
cargo xtask site --write
cargo xtask site --release
```

The first command writes canonical and social URLs, GitHub links, the pages' links to the app (each is written `<a data-app="" href=...>`, and takes `app_url` and a slash; a link that names the app without the mark is refused, since it would keep the old address when the setting moves) and the address in the picture of the browser's window (`data-app-host`: the host of `app_url`), each download card’s asset name (a card names its platform in `data-platform`: `linux`, `windows` or `macos`), the `twitter:*` tags and the structured data of each page ("Search engines and social cards", below), `sitemap.xml` (with the date of each page) and `robots.txt`. Keep those generated changes with the settings. The release check also rejects the draft domain, repository and an empty asset name for any of the three platforms. The ordinary CI check accepts the draft settings and checks that every generated value matches them.

**Each download link is the file itself** (the owner, 2026-11-25), in the release of the version in `[workspace.package]` of `Cargo.toml`: `https://github.com/<repository>/releases/download/v<version>/<file>`, so that a click starts the download, with no page of the release between and no script needed. A link is written `<a data-repo="/releases/download" href=... data-download=... data-asset=...>`: `cargo xtask site --write` makes the `href` from `repository` and the asset name of its download in `site.json` (`{tag}` is `v<version>`, `{version}` the version; a file name is percent-escaped as a path segment), so after `cargo xtask version set` the pages are stale until `cargo xtask site --write` is run, and the plain `cargo xtask site` says so. The site check also holds the links to the release workflow (`xtask/src/site/downloads.rs`): every asset name of `site.json` is one of the files the workflow's checksums job lists (`expected=$(printf`), and every download link of every page is an address in the folder of the release of the version and names one of those files. The pages of a site deployed for a release therefore link that release's files, whenever they are served. **The script** (`site/download.js`) only upgrades them: it reads the repository and the release from the first download link, makes one request to the GitHub release API for the latest release, without credentials or a referrer, with a 3.5-second timeout, and replaces the links with the files of the latest release only when it is strictly newer than the pages' own (compared as `major.minor.patch`, a suffix such as `-rc.1` older than the release without it), since the API never names a draft: while a release waits for its Publish the latest one is an older release, and it must not take the links back to it. Each file is accepted only at the exact address `https://github.com/<repository>/releases/download/<tag>/<file>`; a newer release that lacks a file leaves that link on the file of the release the pages were made for. A visitor with no script, or whose request fails, has the links as they were made. A draft of `site.json` with an empty asset name links the page of the release (`/releases/tag/v<version>`), which `--release` refuses. The home page’s first button goes to the download section, which holds one card each for Linux, Windows and macOS. In each card the installer for Intel/AMD (x64) is the main button (`.AppImage`, `.msi`, `.dmg`; on macOS the Apple silicon build), alone, with no word of the CPU beside it (the owner, 2026-11-25), and under it every download is a smaller link in a row for each CPU, labelled "Intel/AMD (x64)" and "ARM64" (on macOS "Apple silicon (ARM64)" and "Intel (x64)", builds for that chip alone). **Every row lists all its formats** (the owner, 2026-11-25), in one order for the whole card, so that no format reads as missing: `.AppImage .deb .tar.gz` on Linux, `.msi .zip` on Windows and `.dmg .zip` on macOS. The main button repeats the link of one of its card's rows, and a test holds each of the fourteen files to exactly one place in the rows. The list of a card's rows is named for what it holds to a screen reader: "All Linux downloads", "All Windows downloads" and "All macOS downloads". **There is no universal macOS download** (the owner, 2026-11-25): **the macOS main button is the Apple silicon `.dmg`**, as the other cards' main button is their x64 installer, and the card's "Needs" says that the button is for Apple silicon Macs and that Intel Macs use the Intel row; its "File" line is as short as the other cards' (".dmg disk image, or .zip"). Its Apple silicon row has the `.dmg` and the `.zip`, as the Intel row does. The three cards share four rows of a grid (`subgrid`: the name, the facts, the button, the other downloads), so that the three buttons stand at one height whatever the length of the facts above them; on a narrow screen (52 rem and under) the cards are stacked and need no shared rows. With no script every link is still the file. For each release, settle the release notes in `changelog.html` (its title block names the release and its date) and the release's state in `index.html` (`.release-state`, which says the version and its day to a visitor without the script, and which the script replaces with the latest release's tag): both are settled for 0.2.1, released on 25 November 2026 (for 0.2.0). Linux, one Intel Mac and one Windows 11 machine are the desktop builds recorded as run (a universal macOS download, which the release no longer makes, was made on that Mac and its Intel half ran; on the Windows machine the x64 `.msi` was installed and its programs smoke tested, with no window; `hardware-parity.md`), and the release workflow builds and smoke tests every download on GitHub's runners, as it did for 0.2.0 (`releasing.md`); the cards claim nothing of Windows or macOS beyond saying that the downloads are unsigned. **Search engines and social cards** (`xtask/src/site/seo.rs`, tests in `seo_tests.rs` and `xtask/tests/it/seo.rs`). Each page has its own title, description, canonical address (the address without `.html`, which Pages serves: the links between pages keep the extension, so that the site also works on a plain file server) and `og:*` tags, written by hand beside the page's text. **A title is at most 60 characters and leads with what the page is about, and a description is 140 to 160 characters** (the lengths a result shows whole), each its own: `xtask/tests/it/seo.rs` holds every page but the one for a missing address to them, and `og:title` to the title. `cargo xtask site --write` makes the rest, so that it follows the settings and the release:

- **The `twitter:*` tags** are `twitter:card` (`summary_large_image`) and the page's own `og:title`, `og:description`, `og:image` and `og:image:alt` as `twitter:title`, `twitter:description`, `twitter:image` and `twitter:image:alt`, after the last `og:*` tag. Every page has them, the page for a missing address too.
- **The structured data** is JSON-LD (`<script type="application/ld+json" data-generated="">`, a block of data that a browser does not run and that the content security policy does not see), before `</head>`. A block with the mark is the generator's and is made again each time; a block written by hand (the same tag with no `data-generated`) is the page's own and is left as it is. The home page has a `SoftwareApplication` (the name, the page's address and description, the category `DesignApplication`, the systems, a free offer in US dollars, the version of `[workspace.package]` in `Cargo.toml`, the release page of that version as `downloadUrl`, the licences as the repository's own files `LICENSE-MIT` and `LICENSE-APACHE` as `Cargo.toml`'s `license` names them, the share picture and the repository as `sameAs`) and a `WebSite`. A guide is a `TechArticle` (its title without ` · DiaCraft` as the headline, its description, address and picture, the language and the site it is part of). The guides' own index, `guides/index.html`, is a `CollectionPage` (the properties of a `WebPage`: it lists the guides and is no guide). The changelog, privacy and browser pages and the four pages about kinds of diagram and file (`vsdx-editor.html`, `flowcharts.html`, `org-charts.html`, `architecture-diagrams.html`) are a `WebPage`. The page for a missing address has none. **Nothing is in them that the site does not say elsewhere**: no rating, review, author or date. A date of change is not in a page: the last commit that touched a page would be a commit of the page, which holds the date, and the two would never settle. The text is escaped so that the page stays well-formed (`<`, `>` and `&` are written `\u003c`, `\u003e` and `\u0026`, which JSON readers turn back), the keys are in alphabetical order, and a line is one value. A new licence in `Cargo.toml` needs its file named in `LICENSE_FILES` of `seo.rs`; `cargo xtask site` refuses one that has none. The check reads each block as JSON and holds it to an object with the context `https://schema.org` and a `@type`; `xtask/tests/it/seo.rs` holds each type to the properties schema.org lists for it.
- **`sitemap.xml`** lists the fourteen pages, each with `<lastmod>`: the date (UTC, `YYYY-MM-DD`) of the last commit that touched the page's file, from `git log`, written by `cargo xtask site --write` and by nothing else. Where the history is not the whole history (a shallow checkout holds its one commit as the first, so it would give every file that commit's date; `git` is missing; the folder is not in a repository) the sitemap is written with **no** `<lastmod>`, and a line says so: a missing date is better than a wrong one. **The workflows check out one commit** (`actions/checkout` with its default depth), so they cannot work the dates out: `cargo xtask site` and `site --web` in them keep the dates of the committed sitemap, and hold only that each is a date that exists. The check never compares a date with the history (after a page is edited the date is stale until `--write` is run again, and the deployed one is the committed one). A page's date moves with the page's last commit, not with the version or the downloads it names.
- **`robots.txt`** lets every crawler in and names the sitemap.

**The pages' policy lets a page connect to its own site** (`connect-src 'self' https://api.github.com`). A robots.txt audit such as Lighthouse's fetches the file as the page, under the page's policy, and reports a valid file as invalid when `connect-src` allows GitHub's API only. The page's own scripts do not fetch other files of the site.

**After the deploy.** Run `cargo xtask deploy-check https://<the domain of site.json> https://<its app_url>` once after the first deploy, and after any change to `site/_headers` or `apps/diacraft-web/_headers` ("Deploy to Cloudflare Pages", step 7; "The web app", "Caching"). It asks each deployed site what it sends for its start page and every file that loads, and fails on a wrong `Cache-Control`. The release workflow does not run it (step 7 says why).

## Deploy to Cloudflare Pages

The two sites are deployed by the release workflow's `deploy` job (the owner, 2026-11-24: the tag deploys `diacraft.dev` and `diacraft.app` together with the downloads, and only when every build has succeeded), from the folders the `site` job builds (`site-dist`, the pages, and `app-dist`, the app, which it keeps as the artifacts `diacraft-site-<name>` and `diacraft-app-<name>`), and not from the Git integration. **Why:** Cloudflare's own build image has neither Rust nor the time for the app's build, and a Git-connected project that builds nothing and serves `site/` has no app, so the "Open DiaCraft in your browser" link would lead to a site with nothing in it. **Why two projects:** a Pages project has one `_headers` file and one set of custom domains, and the two sites differ in what they must send: the app's policy allows WebAssembly (`'wasm-unsafe-eval'`) and connects to its own address only, the pages' allows neither and connects to GitHub's API, and the app keeps its hashed files for a year under paths of its own.

**What the workflow does.** For a pushed tag that is not a pre-release (`v0.2.0`; a tag with a suffix, `v0.2.0-rc1`, and a run by hand on a branch build both folders and deploy nothing, so the rehearsals of `docs/releasing.md` leave the live sites alone), a job of its own, `deploy`, runs last. It `needs` the plan, the `site` job, the Linux, Windows and macOS jobs and the checksums, and its condition has no status function, so GitHub's own `success()` applies to all of them: it runs only when every one succeeded, and a job that failed, was cancelled or was skipped leaves the sites as they are (re-running the failed jobs runs it once they pass). It checks out the repository, for the lock below, and downloads the two artifacts of the run with GitHub's own `actions/download-artifact` (pinned by commit like the other actions): `diacraft-site-<tag>` into `site-dist` and `diacraft-app-<tag>` into `app-dist`, which the `site` job kept with its hidden files, so that the folder deployed is the folder built. Then three steps follow:

- **Install wrangler,** Cloudflare's tool, at one exact version (4.166.0) from the lock in `packaging/cloudflare`: `npm ci --prefix packaging/cloudflare --ignore-scripts --engine-strict`. The lock holds each of its 133 packages with the SHA-512 that `npm` checks, so nothing but the packages of the lock is installed, and no install script runs; the step stops if the program does not report the version asked for. It uses the Node and npm of the runner's image (Node 22.23.5 and npm 10.9.9 on the `ubuntu-24.04` image 20261116; wrangler's `engines` need Node 22.12 or later, which `--engine-strict` holds the image to, since the workflow may use no action to choose another Node). This step has no secret.
- **Deploy the pages:** `wrangler pages deploy site-dist --project-name diacraft-site --branch main`, with the tag's commit as the deployment's commit hash and `DiaCraft <tag>` as its message.
- **Deploy the web app:** `wrangler pages deploy app-dist --project-name diacraft-app --branch main`, the same way.

`--branch main` makes each a **production** deployment (the workflow runs on a tag, which has no branch for wrangler to read). The two deploy steps read the repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, and nothing else reads them (a test holds it); one token and one account serve both projects. wrangler sends Cloudflare a usage report for each command unless told not to, and the job tells it not to (`WRANGLER_SEND_METRICS`). **The deploy waits for the downloads** (the owner, 2026-11-24): a tag whose build fails deploys nothing, so the sites never show a release whose files are missing. **The sites go live when the job finishes, before the owner presses Publish on the draft:** the download links already point at the files of the release in `Cargo.toml` (they answer once the draft is published, and a click on one before that finds no file), and the script upgrades them only to a newer published release (see "Prepare a release"). A re-run of the job deploys again. **To move wrangler:** change the version in `packaging/cloudflare/package.json`, run `npm install --package-lock-only --ignore-scripts` there, set `WRANGLER_VERSION` in the `deploy` job of `release.yml`, and write the version and the package's `npm view wrangler@<version> dist.integrity` in the wrangler row of `docs/releasing.md`; a test in `xtask/tests/it/pages_deploy.rs` holds the four to one version, and the lock to the npm registry with a SHA-512 for every package. The lock lists the optional native packages of every platform, as npm's locks do; on the runner `npm ci` takes only those of the runner's own system.

What the workflow cannot do is for the owner or the coordinator, **before the first tag** (nothing in Cloudflare is set up by the repository; the two secrets and the zones of the two domains were in place on 2026-11-24):

1. In Workers & Pages, create two Pages projects named **`diacraft-site`** and **`diacraft-app`**, each as a **Direct Upload** project (no Git connection), or run `npx wrangler pages project create diacraft-site --production-branch main` and the same for `diacraft-app`. The production branch is `main`, which `--branch` of the deploy steps names. Without the two projects the deploy steps fail (project not found) after every build has passed. A name that is taken on Cloudflare needs another one there and in `--project-name` of the two steps (a test holds the two names, and changes with them).
2. In the repository's secrets, `CLOUDFLARE_API_TOKEN` (an account API token with **Cloudflare Pages: Edit** and no other permission, so that a leaked token can change these Pages projects and nothing else) and `CLOUDFLARE_ACCOUNT_ID` (shown on the Workers & Pages overview page). One token and one account serve both projects.
3. Nothing to switch on: the three steps above are in `release.yml`, and the workflow's comment says what they need.
4. To deploy from a computer instead, or when the workflow below is not to be used, install the tool as the workflow does and run it with the two values in the environment: `npm ci --prefix packaging/cloudflare --ignore-scripts --engine-strict`, `cargo xtask site --web --out dist/site --app-out dist/app`, then `packaging/cloudflare/node_modules/.bin/wrangler pages deploy dist/site --project-name diacraft-site --branch main` and the same with `dist/app` and `diacraft-app`. The two folders are the two deploys; neither holds a file of the other.
5. In each project's Custom domains settings, add its hostname and follow the DNS instructions: **`diacraft.dev` to the pages' project and `diacraft.app` to the app's.** For an apex domain, use the Cloudflare zone in the same account (both domains are the owner's, registered on 2026-11-23). **`www.`** (recommended for the pages, not needed for the app): add `www.diacraft.dev` to the pages' project as a second custom domain and give it a redirect to `https://diacraft.dev` (a Redirect Rule), so that the pages have one address and each page's canonical URL is the one that answers; `www.diacraft.app` is left out, since nothing links it.
6. Check the home page, a guide, an unknown URL, the app's start page (`https://diacraft.app/`), the response headers of both (the app's page has the policy with `'wasm-unsafe-eval'` and no page of the pages does), that the "Open DiaCraft in your browser" link of the home page opens `https://diacraft.app/`, and the static release link. Keep Cloudflare Web Analytics and other script-injection features off in both projects to preserve the privacy policy and the content security policies: a script Cloudflare adds to the app's page would be blocked by its policy, and a change to the app's files would fail their integrity checks.
7. Run `cargo xtask deploy-check https://diacraft-site.pages.dev https://diacraft-app.pages.dev`, with the addresses Pages gives the projects, and again `cargo xtask deploy-check https://diacraft.dev https://diacraft.app` once the custom domains are attached (one address checks one site; the run fails if either site has a failure). It prints, for each file, the status, `Cache-Control`, `Content-Encoding`, `ETag` and whether a second request with `If-None-Match` got `304`; it fails on a wrong `Cache-Control` and warns when a `.wasm` part comes back uncompressed. A failure on the glue, the style or the icon of the app, with `max-age=0`, means Pages did not read the splat in the middle of a path in the app's `_headers`: write it in a gaps row, and the fix is to move those three files into `assets/` (which `/assets/*` keeps) and name them in the manifest. A warning on a `.wasm` part means Pages did not compress it: the 17.35 MiB module would then be sent as it is, where a Brotli edge at quality 5 sends 5.82 MB of it (the measurement), and that is for the owner to see. **The release workflow does not run this check.** It has not been run against Pages, which may not read that splat or compress that part (`docs/gaps.md`, J9), and the address of a project may answer from the edge's old state for a moment after a deploy; a check that fails the job after a good deploy, for a reason that breaks nothing, would turn a release run red with nothing to be done in the run. Once it has passed against a real deploy, add it as the last step of the `deploy` job, so that a failure fails the job: `cargo xtask deploy-check https://diacraft-site.pages.dev https://diacraft-app.pages.dev`.

**Deploying by hand, between releases (the owner, 2026-11-25).** A fix of the pages or of the web app need not wait for a release: the workflow `.github/workflows/deploy-site.yml`, "Deploy the website", is run by hand (Actions, Deploy the website, Run workflow) **on `main` only** (a run on another branch stops at its first step, and its `deploy` job has the condition as well). It builds the two sites as the release workflow's `site` job does (`cargo xtask site`, then `cargo xtask site --web --out site-dist --app-out app-dist`, after the same script, `packaging/install-site-tools.sh`, has installed trunk, wasm-bindgen and wasm-opt from the same versions and checksums, which a test holds equal in the two workflows), **never builds a download**, and deploys both folders with the same pinned wrangler to the same two projects with the same two secrets, which only its two deploy steps read; its token is `contents: read`, and its actions are GitHub's own, pinned by commit, as the release workflow's are. Its `deploy` job is in the concurrency group `deploy-site`, the group the release workflow's `deploy` job names too, so the two never deploy at once (a run that has to wait is not cancelled). **Its download links still point at the release in `Cargo.toml`**: they are made from that version, so a fix deployed after 0.2.0 is out and before the next version is set links 0.2.0's files, and the script moves them only to a newer published release. The workflow has not run on GitHub; the owner's set-up of Cloudflare (step 1 and 2 above) is what it needs, and nothing more.

Pages serves extensionless canonical URLs and uses the top-level `404.html` for missing files. Links in the HTML include the file extension so they also work on an ordinary static file server (the link to the app is to the other site's root, `https://diacraft.app/`). Each click on such a link costs Pages a 308 to the address without the extension (one extra request, answered at once). **The links are not switched to the extensionless form**, because `python3 -m http.server` and any other plain file server answer `/privacy` with a 404 (there is no file of that name), so the preview this page describes, and the rule above, would break; the pages' canonical addresses are the extensionless ones already, and `cargo xtask deploy-check` accepts the 308. Neither site needs redirect rules (but the optional `www.` one), runtime services or Pages Functions. A file over 25 MiB is refused by Pages and the app holds itself to a budget below that (see "The web app"). ## The web app

`apps/diacraft-web` is the editor window, `DiacraftApp`, started on a canvas by eframe's web runner (WebGPU where the browser has it, WebGL 2 where not). `cargo xtask site --web` builds it, makes it into a folder of its own with the app at its root, which is `https://diacraft.app/` (it was the pages' `/app/` folder before, and the measurements below were made so, with the app's block of `site/_headers`, which is the app's `_headers` now: its files, bytes and headers are the same and its paths lose the `/app` prefix), and checks the result. A person reaches it from the home page's "Open DiaCraft in your browser" link, card button and answer, which go straight to the app's address (`app_url` of `site.json`; each link is written `<a data-app="" href=...>` and `cargo xtask site --write` keeps it there; each carries the label "Open DiaCraft in your browser", which is true of the link). The page about it, `browser.html` (what the browser version needs, keeps and cannot do), is linked from the home page's Features section (the item "Runs in your browser"), from the answer to "Can I try DiaCraft without installing it?" and from the footer of every page ("In your browser"), and its own button goes to the app; a test of `xtask` (`web_site.rs`) holds every link that says "Open DiaCraft in your browser" to the app's address, marked `data-app`, and the footer's link to `browser.html` on all fifteen pages (owner, 2026-11-23). The module is not one file: it is served in parts, and the data it does not need for its first frame is fetched after it (below).

**Build and check.** `cargo xtask site --web [--dist DIR] [--out DIR] [--app-out DIR] [--app-url URL]` runs `cargo xtask site` on the pages first, copies `site/` into the pages' folder (`dist/site`, or `--out DIR`) with the links to the app at the address of this build (`app_url` of `site.json`, or `--app-url` / `DIACRAFT_APP_URL` for a preview on this machine: an HTTPS address, or `http://localhost:PORT` or `http://127.0.0.1:PORT`, and no other http address; the copy's `site.json` and the address in the browser picture follow it, and `site/` is not touched) and checks the copy as it checks `site/`, then runs `trunk build --release --locked` in `apps/diacraft-web` (or takes the finished build in `--dist DIR`), makes the app's folder from it (`dist/app`, or `--app-out DIR`) and checks that. The two folders are two deploys: neither may be the other or inside it, a folder under `dist/` that an earlier run made is cleared, and any other full folder is refused. The tools are `trunk` 0.22.2, `wasm-bindgen` at the version of the `wasm-bindgen` crate in `Cargo.lock` (trunk reads the lock and downloads the matching program when none of that version is on the `PATH`) and binaryen's `wasm-opt` at the version `Trunk.toml` names (`version_133`: a program on the `PATH` is used only at exactly that version, else trunk downloads one). To install them: `cargo install --locked trunk@0.22.2` and `cargo install --locked wasm-opt@0.133.0` (binaryen version 133), which put both in `~/.cargo/bin`; the release workflow installs the release archives instead, each checked against a SHA-256. A test in `xtask/tests/it/web_site.rs` holds the workflow's versions to the lock and `Trunk.toml`. The command is no step of `ci`: the app's compile check there is `cargo xtask wasm`, and the pages' check is `cargo xtask site`. A warm build takes about 40 seconds, a cold one a few minutes (fat LTO).

**One change to trunk's page.** trunk starts the app with an inline `<script type="module">`, and the app's content security policy has no `'unsafe-inline'`. The command moves that script, unchanged, into `start.js` of the app's folder and has the page load it by `src`. The page's styles are `apps/diacraft-web/page.css`, copied by trunk, for the same reason (no inline style). That script is no longer kept as trunk wrote it: `start.js` is the loader below.

**Loading in parts.** The module is not served as one file. `cargo xtask site --web` cuts it into parts of at most 8 MiB, near equal in size and in order (`parts/diacraft-web-N-<the first 16 digits of its SHA-256>.wasm`: the `.wasm` ending is what makes a CDN compress them, and Cloudflare compresses `application/wasm` and not `application/octet-stream`), copies the data the module does not carry into `assets/` under names with their hashes (next paragraph), and writes `manifest.json`: its version (1), the name of the program's start script (the glue trunk made), the module's size and SHA-256, each part's file, size and SHA-256, and each asset's file, size and SHA-256. The unsplit file is not in the site. `start.js` is `apps/diacraft-web/loader.js`, the site's one script that is not generated (about 280 lines, no `npm`): it reads the manifest, fetches the parts in parallel, counts the bytes that arrive, joins the parts in order into one `ReadableStream`, wraps it in a `Response` of type `application/wasm` and has the browser compile it with `WebAssembly.compileStreaming` while the bytes are still arriving (and while the glue is fetched), then starts the program from the compiled module. **Each part is held to its length and, where the browser has `crypto.subtle` (every https page and `localhost`), to its SHA-256, while the next part comes, and the program is not started until every part has passed**: a bad part stops the stream, and bytes that failed a check are compiled (which harms nothing) and never run. A part that is missing, has the wrong length or digest, comes with an HTML page for a body, or stops coming (nothing for 30 seconds) is told on the page in words with a "Try again" button, never a hang or a blank; a missing or bad manifest or glue the same. The loader reads the manifest to a bound (64 KiB), takes at most 16 parts of 8 MiB and 64 MiB in all, accepts only plain file names of `parts/` and the app's own folder, and has no address in it but the manifest's. The page preloads the manifest and each part (`<link rel="preload" as="fetch" crossorigin>`, so that the loader's fetch of the same address is answered from the preload and each file is requested once: 11 requests at the load, all to the app's own address) and shows how many bytes of the parts have arrived, in a `<progress>` and a line of words in the page's own colours (the theme tokens of the app's text, top bar and canvas, light and dark), until the program has drawn its first frame and takes the element away. The policy is unchanged (`connect-src 'self'`).

**The data the module does not carry.** The splash picture (`diacraft-splash.png`, 0.20 MiB), the cover (2.29 MiB, which no compression makes smaller) and the licence list (`THIRD-PARTY-LICENSES-WEB.txt`, 0.21 MiB) were 2.84 MB of the module, and none is needed for the first frame. While one is on its way the window shows a placeholder with a short wait in it (the splash panel at its size, in the picture's paper colour, with its text; a tile in the File view; the licence card with its words); one that could not be had is said in words (the status bar for the pictures, the card for the list, with a way to try again) and the window works without it. Each is fetched from the app's own folder: the manifest's text names it (a plain file of `assets/`, a size of at most the window's limit for it, a SHA-256), the room is asked for with `try_reserve_exact` before a byte is read, the body is read in pieces and stops at the size, and the whole is held to its digest. The desktop programs keep them inside (`include_bytes!`, now `cfg(not(target_arch = "wasm32"))`). **The icon** is the page's own (`<link rel="icon">`: the module never held it). **Fonts:** Ubuntu Light and Hack (0.67 MB, 3.7% of the module) stay inside. Ubuntu Light draws every word of the first frame and must be there. Hack is drawn by two dialogs only (Insert Symbol and the licence list), so it could be fetched when one opens; it is not, because its bytes are in a crate's source and not a file of this repository (the build tool would have to read them out of the cargo checkout), the window would have to install the faces again after the first frame, and what it saves is 0.31 MB, 1.7% of the module.

**What the check holds** (`xtask/src/site/app.rs` and `parts.rs`; tests in `app_tests.rs` and `parts_tests.rs`): the start page and every file it loads exist, and nothing leaves the folder; nothing is inline (no script, style element or style attribute); no file is over the limit or its budget (a part 8 MiB, the module 19 MiB in all, any other file 4 MiB); the manifest is the version the loader reads and agrees with the folder (each part is a file of `parts/` of the size it says, named by the first 16 digits of its hash, and its bytes have that hash; the parts joined are the module whose hash it gives; each asset is there by its name and hash and within its limit; nothing else is in `parts/` or `assets/`); the page preloads the manifest and each part and nothing else, `as="fetch"` with `crossorigin` so that the loader's fetch is answered from them; the parts joined are a WebAssembly module whose memory is not shared (**the build uses no threads and no `SharedArrayBuffer`, so no cross-origin isolation headers are sent**, and the check refuses a module that would need them); the JavaScript has no `XMLHttpRequest`, `WebSocket`, `sendBeacon`, `EventSource`, `eval` or `new Function` and no string that is another site's address; the page, script and style name no vendor; the page's search and social data and the three files beside it are as "Search and social data of the app's page" says; no link or special file is in the folder; and `_headers` is the app's own (`headers::check_app`: for every path the app's policy and the three headers every page has, the rules that cache the parts, the data, the glue, the style and the icon for good, and no other route, no other header and no detach) and, read as Pages applies it, keeps for a year the files named by the SHA-256 of their own bytes and no others ("Caching", below). The module's own text is not scanned for names: it carries the namespace addresses and content types of the file formats it reads (names `AGENTS.md` allows for interoperability) and the licence texts of its libraries with their copyright lines, as the desktop downloads do (`docs/gaps.md`, J6).

**Headers.** Each site has a `_headers` file. The pages' is `site/_headers`: the strict policy and the three headers under `/*`, and the rule for the pictures named by their hash; it has nothing of the app's, and `cargo xtask site` refuses a rule for a path of the app (`/app/...`), a policy under any route but `/*`, and a detach. The app's is `apps/diacraft-web/_headers`, which `cargo xtask site --web` puts in the app's folder; its policy is for every path of its site: `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; img-src 'self'; style-src 'self'; manifest-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`. It differs from the pages' policy in two places (`manifest-src 'self'`, only names the web app manifest, which `default-src` allowed already): `'wasm-unsafe-eval'` (WebAssembly may be compiled and nothing else evaluated) and `connect-src 'self'` (the page fetches its own `.wasm` file; the pages' policy allows the site's own files and GitHub's API, for the release lookup the app does not have). The app's file had been a block of the pages' (`/app/*`), which had to take the pages' policy off before it set its own (`! Content-Security-Policy`, since Pages applies every rule that matches a path and joins a header that is set twice); as a file of its own it has no such detach, and the check refuses one. **Five more rules**, `/parts/*`, `/assets/*`, `/diacraft-web-*.js`, `/page-*.css` and `/diacraft-icon-256-*.png`, set `Cache-Control: public, max-age=31536000, immutable` and nothing else: a file they match is named by the hash of its own bytes and never changes under its name, so a returning visitor asks about none of the module's 18 MB, the glue (0.16 MB), the style or the icon (0.12 MB); the page, the loader, the manifests and the snippets of the glue keep Pages' own revalidation, one small conditional request each, and "Caching" says why; `cargo xtask site --web` refuses a folder whose `_headers` lacks them. The other headers (`X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`) are the pages' as they are. The app is not cross-origin isolated and needs no isolation. `Referrer-Policy: no-referrer` on the pages means the app is not told which page of the pages a visitor came from.

**Caching.** The owner asked that everything be kept in the visitor's browser as long as it safely can, so that Cloudflare sends as few bytes as possible. **What Cloudflare documents** ("Serving Pages" and "Headers", read 2026-11-23): requests for static assets are free and unlimited on every plan; Pages always sends an `ETag` and answers `304 Not Modified` to a matching `If-None-Match`; a cacheable asset gets `Cache-Control: public, max-age=0, must-revalidate` unless `_headers` says otherwise; it serves Gzip and Brotli whenever possible; and a path that several `_headers` rules match gets all their headers, a header set twice being joined with a comma. **The rule the site follows:** a file is kept for a year (`public, max-age=31536000, immutable`) if its name is the hash of its own bytes, and no other file is kept at all, so a release reaches a visitor on the next visit and a file that did not change is never sent twice. A name is a hash when it is `<stem>-<16 digits>.<ext>` (the parts and the data of the app, and the glue, style and icon Trunk makes) or `<stem>.<12 digits>.<ext>` (the pictures of `assets/hashed/`) and the digits are the first of the SHA-256 of the file. Trunk hashes the glue, the style and the icon with its own function, whose digits nothing here can recompute, so `cargo xtask site --web` names them again by the SHA-256 of their bytes (`rehash` in `xtask/src/site/app.rs`: the page and the module's manifest follow, and the `integrity` attributes stay, being of the bytes).

**What is not kept.** The page, the loader (`start.js`), `manifest.json`, the web app manifest and its two icons, the site's pages, `styles.css`, `download.js`, `icon-512.png` and `social.jpg` have no hash in their names, so each is one small conditional request on a visit, a `304` with no body when it did not change. **The snippets of the glue** (`snippets/eframe-<hash>/inline0.js` of the app, 280 bytes) are asked about too, and this is where the task found something its brief did not expect: the hash in their folder's name is of the crate's name and version (`wasm-bindgen`'s crate identifier) and not of the file, so a rule that kept them would keep a changed file under the same name, and the page's `integrity` attribute would then refuse it for a year. Making them cacheable would mean rewriting the glue's imports and naming the glue again, for one request of 280 bytes. `styles.css` and `download.js` could be hashed into `assets/hashed/` as the pictures are, which the site check could hold; they are not, since every edit would rename them and rewrite every page, to save 13 KB of conditional requests.

**The check** (`xtask/src/site/cache.rs`, run by `cargo xtask site` over every file of `site/` and by `site --web` over every file of each of the two folders, each a site of its own: the pages or the app). It reads `_headers` as Pages applies it: every rule that matches a path, in order; a pattern with one splat (`*`, any characters, a slash too) and any number of placeholders (`:name`, one or more characters but a slash); `! Name` taking away what earlier rules set; a header set twice joined; at most 100 rules and 2,000 characters in a line, as Pages takes. A pattern for a host, and a value that refers to `:splat` or a placeholder, are refused, since nothing here substitutes them and the site uses none. For each file and each address it is served at (`/` and `/index.html`; `/privacy` and `/privacy.html`) it fails: (1) a file whose name is not a hash of its own bytes (or whose hash is another file's) that is given `immutable`, or a `max-age` or `s-maxage` above 0; (2) a file named by the hash of its own bytes that is not given `immutable` and a year; (3) a file that two rules give two `Cache-Control` values (they would be sent as one joined value, which a browser reads as it likes); (4) a page that has no content security policy, or two (joined, a browser applies both), or one that is not the one the site holds (the pages' own for the pages, the app's own for the app's folder). The tests give each rule a `_headers` that breaks it (`xtask/src/site/cache_tests.rs`, `app_tests.rs`). **Not verified:** that Pages reads a splat in the middle of a path (`/page-*.css` of the app's file) as the check does. Its documentation shows a splat at the end of a path only, and says that a splat "greedily" matches all characters; the check, and the local server of the run below, follow that sentence. A rule that Pages ignored would leave the glue, the style and the icon (0.29 MB) asked about on every visit, and would not break the app: the check after the deploy is where it would show.

**The check after a deploy: `cargo xtask deploy-check <BASE_URL> [<BASE_URL>]`** (`xtask/src/site/live.rs`, tested in `live_tests.rs`). Each `BASE_URL` is a site, `https://host`, or `http://host:port` for a server of one's own: the pages' first and the app's second, or one of them alone; each is checked on its own, from its start page `/`, and the run fails if either has a failure (the same address twice is refused). A link from one site to the other (the pages' to the app) is not followed: that site has its own check. It runs `curl` (as `site --web` runs trunk) and fetches the start page (the home page, or the app's page), the pages it links to, and every file they load: the style, the pictures (`<img>`, `srcset`, the share picture, a style's `url()`), the web manifests and their icons, the app's script, glue and snippets, and, from the module's `manifest.json`, the parts and the data. Each is asked for with `Accept-Encoding: br, gzip`, as a browser asks (the answer is not decoded), and again with `If-None-Match` and the `ETag` it was given. It prints, for each, the status, `Cache-Control`, `Content-Encoding`, `ETag`, the status of the second request (`304` is the right one) and the bytes that came. **It fails** (exit status 1) on a status that is not 200, but for the 308 that Pages sends a page to (below), and on a wrong `Cache-Control`: a file named by its hash must be `immutable` for a year, any other must not be kept. **The 308 of Pages.** Cloudflare Pages answers a link to `/privacy.html` with a 308 to `/privacy`, which it serves; run against the live site, the check failed on every such link with "answered 308, and a file of the site is answered 200". A page whose address ends in `.html` and that answers 308 to its own address without the extension (`/index.html` to `/`, `/dir/index.html` to `/dir/`), with a `Location` that is a path or an address that begins with the site's own (`https://host`), is right: the check follows it once, probes the target as it probes any file (its status, `Cache-Control`, `ETag` and the second request), and finds what the target loads. Any other 308, any other redirect, a redirect of a path that is not a page, a `Location` with a query or a fragment or another host, and a target that sends on again are failures. **It warns** when a `.wasm` part, or another text file of 1 KiB or more, comes back uncompressed, when a file has no `ETag` or the second request does not get `304`, and when a file that must be asked about says nothing about asking. It is a command of xtask and not a script because the project's tools are Rust, are tested with the rest, and share what they know: it uses the same shape of hashed name as the offline check, so the two hold one rule. The owner runs it once after the first deploy, and after any change to `site/_headers` or `apps/diacraft-web/_headers`. **Run here** (before the app was a site of its own: one site with the app in a folder; the check is the same for each of the two now) against a local server that applies `_headers` as the documentation says (a Python script outside the repository, written independently of the Rust reader, with brotli at quality 5): 39 URLs, 0 failures, 0 warnings; and against the same site with the rule for the style turned into a rule for the loader, and no compression: 2 failures (the style not kept, the loader kept), 18 warnings (the three `.wasm` parts and fifteen other text files uncompressed), exit status 1. What Pages itself sends, which `_headers` rules it applies and how it compresses a `.wasm` file is not known until that first run.

**What the browser version lacks.** Measured in the app (what it does with files is in "Files in the browser", below):

- **Files.** A drawing that is too large for the browser's memory (a read there may hold 1 GiB, where the desktop's may hold 2.6 GB) is refused in words; saving is a download unless the browser can write to a file the person chose; a page cannot reach a printer, so the Print view offers Save as PDF and says so. A drawing is lost when the tab closes unless it was saved. The rest of the gap is `docs/gaps.md` J5.
- **Fonts.** Only the two typefaces built into the window (Hack and Ubuntu Light): the browser gives no list of the computer's fonts, so the font scan does nothing there.
- **The control channel, the CLI and the MCP server**: they need a program that listens or runs on the computer.
- **Threads.** The window draws, reads and snaps on its one thread.
- **The window frame**: the page is the window, and the tab title is the page's.

**Files in the browser.** The engine reads and writes a file by its path, and a tab has no paths, so the engine keeps files in memory where there is no file system (`crates/engine/src/memfs.rs`: always on `wasm32`, and on another target only for a thread that asks, which is how the tests run the flow on the desktop). The page puts the file the person chose in that store under a path of its own making (`/web/N/name`, the name with every separator and control character made `_`), the commands `file.open`, `stencil.open` and `insert.picture` read that path with the budgets and the refusals they have on the desktop, and what `file.save`, `file.save_as`, `file.export` and `file.print` wrote there is taken out and handed over. The window is given the page's side as a `FileHost` (`crates/ui-egui/src/file_host.rs`; the page's is `apps/diacraft-web/src/web_files.rs`), and is otherwise the desktop's, with two differences: the work a thread does on the desktop (reading a file, drawing an export) is done on the page's thread one frame after the progress card is drawn, and where the page has no save dialog of its own the window asks for the name and the type with a card. **Choosing** is the File System Access API where the page has it (`showOpenFilePicker`, `showSaveFilePicker`) and a file input where not; a file dropped on the page is taken by a handler on the window that runs before the browser's own, so no file is read before its size is judged. **Judging:** a file is judged from its size before a byte is read (`memfs::admit`, the rule `file.open` applies, against the web budget of 1 GiB, `diacraft_vsdx::WEB_MAX_MEMORY`), read in pieces of 8 MiB into memory asked for with `try_reserve`, and put in a store of at most 64 files and 768 MiB that the process's memory ledger counts. **Handing over** is a Blob and a link with a `download` name (the page makes no request and its policy needs no change), or, for a file chosen with the File System Access API, a write in place; a write that fails is downloaded instead, and said. The check after a save, the save card, the macro question and the save note are the desktop's. **Print:** a page cannot reach a printer, and the browser's own print would print the canvas and not the drawing, so the Print view offers Save as PDF (the PDF a printer would be given) and says so in its own words.

with a changed drawing shows DiaCraft's question (the handler is still on while it is up, so closing the window by another way would ask), Cancel keeps the window and the handler, and **Don't Save closes the window with no
dialog**; as a control, a handler for `beforeunload` that nothing takes off, put on the page first, made the browser open the `beforeunload` dialog when `window.close()` ran, which is the second question the page's
clearing prevents. **A close the browser keeps** (a tab with a second history entry, Ctrl+W delivered to the page through the DevTools protocol, a real click on Don't Save): the handler was off right after, `window.close()`
was refused, the status bar said "The browser keeps this window open: close it with the browser's own button or key.", the handler was on again, and F5 opened the dialog. **Firefox 160, a tab:** a new drawing reloads with no
prompt; a changed one makes Firefox open its own `beforeunload` prompt ("This page is asking you to confirm that you want to leave ..."), Stay keeps the page, Leave reloads; an edit undone reloads with no prompt. **Not
measured:** Safari, Edge, a phone or tablet (a browser may show no box there), Windows and macOS, a real keyboard, and the window of an app installed from the install prompt (the `--app` window is the same
kind).

**Notices.** `cargo xtask licenses` also writes `THIRD-PARTY-LICENSES-WEB.txt`: the crates `diacraft-web` is built from for `wasm32-unknown-unknown` (`policy::OUTPUTS`). The app's licences window (File, About, Third-party licences) shows it, **fetched** from the app's `assets/` when the window first opens (it was built into the module before), and `browser.html` links the repository's copy like the home page links the desktop list. The copy in the app's `assets/` is held to the site's name check, **except the lines that `cargo xtask brands` keeps as the licences have them** (`xtask::brands::NAME_EXCEPTIONS`: a copyright line of a licence is not ours to change).

**Release workflow.** The `site` job of `.github/workflows/release.yml` installs trunk, `wasm-bindgen` and `wasm-opt` from their release archives (each checked against the SHA-256 written in the workflow), runs `cargo xtask site` and `cargo xtask site --web --out site-dist --app-out app-dist`, and keeps `site-dist` (the pages) as the workflow artifact `diacraft-site-<name>` and `app-dist` (the app) as `diacraft-app-<name>`. The `deploy` job, which runs last for a pushed tag that is not a pre-release and only when the builds and the checksums have succeeded, downloads the two artifacts, installs wrangler from the lock in `packaging/cloudflare` and deploys the two folders, one to each Pages project ("Deploy to Cloudflare Pages").

## Check a change

Run `cargo test -p xtask`, `cargo xtask site`, `cargo xtask assets` and `cargo xtask brands`. After a change to the web app, also run `cargo xtask site --web` (the app's files, links, sizes and headers, and the pages' copy) and open `dist/site` and `dist/app` with a server that applies `_headers`. After a deploy, run `cargo xtask deploy-check <PAGES_URL> <APP_URL>`. The site check also runs in `cargo xtask ci` and parses each HTML page in Rust. A parsing error reports the page and line. Close elements explicitly and quote attribute values. Use numeric character references or the built-in XML escapes where needed.

The checker resolves local links, fragments, picture sources, manifest icons and stylesheet resources. It checks page titles, descriptions, canonical and social URLs, the `twitter:*` tags and the structured data (each block must parse as JSON-LD, and each page's must be the generated one), the dates of the sitemap, image descriptions and dimensions, allowed hosts, public text and the Cloudflare security headers. **Public text names no vendor but in the places the owner allowed.** Every page's footer has the notice: one paragraph, `.foot-inner .legal`, that says the trademark line of the product the VSDX types are named after, that OpenDocument Format (ODF) is an OASIS Standard, that LibreOffice is a registered trademark of The Document Foundation and OpenOffice and Apache OpenOffice of The Apache Software Foundation, that ArchiMate is a registered trademark of The Open Group and UML and BPMN are trademarks of the Object Management Group (the owner, 2026-11-25: the architecture page names the three), and that DiaCraft is not affiliated with or endorsed by Microsoft, OASIS, The Document Foundation, The Apache Software Foundation, The Open Group or the Object Management Group. The names after its first sentence are none that `cargo xtask brands` refuses, as LibreOffice is none, so a page may say them anywhere and the notice says whose they are. It is an exact text of `PRODUCT_USES` in `xtask/src/brands.rs`, listed for each page, and the one place a page may name the company. **A page may name the product of the VSDX types anywhere** (the owner, 2026-11-25: "Yes use it for SEO with no restrictions", for the site's pages only; on 2026-11-23, it was named only in the lists of the formats and in the notice): in an `.html` page of `site/` its name is no hit of `cargo xtask site` or of `cargo xtask brands` (`SITE_PAGE_NAMES` in `xtask/src/brands.rs`), in the text, the attributes and the head and read through character references, and the export keeps each page whole by a `free` entry of its allowlist, which lets the product's name through on every line of that one file and nothing else (a test holds the entries to the pages of the tree, and to the gate's list of them, `SITE_PAGES`). The company's name and the other vendors' names are refused in a page outside the notice, and the product's name is refused in the site's other text files (its style, script and data) and in any file's name, which is why the page about the product's files is `vsdx-editor.html`. What a page says of the product's files rests on the docs ("Editorial sources"). It totals each page and the assets it references, including both theme screenshots, icon variants, the social image and the fonts its stylesheet names, against 1,000,000 bytes (the home page is about 909,000, and the largest of the other fourteen, the flowcharts page with its two captures in both colour schemes, about 853,000, counted on 2026-11-25 by a script that follows the same files). **A font is a `.woff2` in `assets/hashed/`** and no other file: the check reads it as bytes, refuses any other kind of font or any other folder, and refuses a site that has fonts while the policy of `/*` in `_headers` does not say `font-src 'self'` ("Fonts"). `cargo xtask export-public --check-only` checks the committed public tree at HEAD.

**Measuring a page.** Lighthouse (`npx lighthouse`, with a headless Chrome) gives the SEO, accessibility and best-practices scores of a page. Run it against the folders `cargo xtask site --web` made, served by a server that applies each `_headers` file and answers as Pages does (a link ending in `.html` is a 308 to the address without it, and text is sent compressed): a plain file server sends no content security policy and no compression, and the scores are not the site's. Serving the two folders as `diacraft.dev` and `diacraft.app` over HTTPS with a certificate of your own, and starting Chrome with `--host-resolver-rules` and `--ignore-certificate-errors`, gives the canonical addresses their real hosts. A page's performance is the part of the score that moves with the machine: run each page more than once.

## Fonts

The site has two typefaces of its own, both under the SIL Open Font License 1.1 and neither with a Reserved Font Name: **Besley** (text and headings, upright and italic; The Besley Project Authors, version 2.001) and **Martian Mono** (labels, navigation and code; The Martian Mono Project Authors, version 1.000). This is the owner's exception for the website (2026-11-23) to the rule that no font is in the repository: the programs bundle neither, AGENTS.md's asset rule says what the exception allows, and NOTICE names the two typefaces, their licence and where its text is. They are three subset WOFF2 files in `site/assets/hashed/`, named by the first twelve digits of their SHA-256 as the pictures are and kept for a year like them, 81,576 bytes together. `styles.css` loads them with `@font-face` and `font-display: swap`, and every page preloads the upright Besley. **The guides' index preloads the italic and Martian Mono too**: its head is short, so on a phone its first section is on the first screen, and the swap of the label's and the heading's faces moved it (Lighthouse's cumulative layout shift 0.19 on the mobile run, 0 with the two preloads, 2026-11-25); the other pages' heads keep their first section below the first screen. Each has a row in [ATTRIBUTION.md](../ATTRIBUTION.md); the licence texts are [`Besley-OFL.txt`](licenses/fonts/Besley-OFL.txt) and [`MartianMono-OFL.txt`](licenses/fonts/MartianMono-OFL.txt), and the files keep the copyright and licence fields of their name tables. `_headers` says `font-src 'self'`, and `cargo xtask site` holds both ("Check a change").

The sources are the variable fonts of `ofl/besley` (commit `c13390277dfb`) and `ofl/martianmono` (commit `c8bba5c4a691`) of the Google Fonts repository, whose SHA-256 begin `71f352d8859c7876` (`Besley[wght].ttf`), `de502a1ab6b06a63` (`Besley-Italic[wght].ttf`) and `c3467843ec1c2574` (`MartianMono[wdth,wght].ttf`). To make the files again (fontTools 4.68.0 with Brotli 1.2.1):

```sh
U="U+0020-007E,U+00A0-00FF,U+2013,U+2014,U+2018,U+2019,U+201C,U+201D,U+2022,U+2026,U+2212,U+2039,U+203A,U+2032,U+2033"
fonttools varLib.instancer "Besley[wght].ttf" wght=400:700 -o besley-roman.ttf
fonttools varLib.instancer "Besley-Italic[wght].ttf" wght=400:600 -o besley-italic.ttf
fonttools varLib.instancer "MartianMono[wdth,wght].ttf" wdth=85 wght=400:700 -o martian-mono.ttf
for f in besley-roman besley-italic; do pyftsubset $f.ttf --unicodes="$U" --layout-features='kern,liga,calt,onum,tnum,ss01' --name-IDs='*' --name-languages='*' --flavor=woff2 --output-file=$f.woff2; done
pyftsubset martian-mono.ttf --unicodes="$U,U+2190-2193,U+2116" --layout-features='kern,calt,case,ccmp' --name-IDs='*' --name-languages='*' --flavor=woff2 --output-file=martian-mono.woff2
```

Besley has no arrows, and Martian Mono no north-east arrow, so every page draws the arrows of its links in the stylesheet (`.arrow`, a line with a filled head, as a connector ends); the arrow characters inside a sentence (File → Open) fall back to a system face.

## Design

`site/styles.css` is the design system, in ten parts that its first comment lists: fonts, tokens, base, layout, masthead, components, the home page's sections, the footer, the article pages, motion. There is no build step and no script.

- **Idea.** The page is the editor's drawing area: a faint grid, a ruler under the masthead, the editor's picture selected with eight handles as the editor selects a shape, and the file types joined to it by right-angle connectors with connection points and filled arrowheads. Arrows, section labels, the plate's numbered pins, the file names of the three sheets and the connector of the guides are drawn in the stylesheet in the same hand. Nothing is drawn in SVG: the check refuses it, in a page and as a file.
- **The grid and the ruler.** The grid is the editor's quarter inch (`--grid-step`), with a heavier line every five, and it is drawn from a point a whole number of heavy lines to the left of the content's edge, so that a heavy line runs down that edge at any width (the hero, and the band of the downloads, whose sheet lies on it). The home page's ruler is a real one: an inch is six rems (`--inch`, 96 CSS pixels), with a tick every eighth, numbered from zero at the content's left edge as the editor's ruler starts at the sheet's. It is under the masthead and again over the footer, and on a screen at least 60rem wide and 40rem high the masthead stays in place while the page moves under it. Every page has it. **The columns:** the sections of two columns are seven parts and five with one space between them (`--split-gap`), so that their second columns begin on one edge down the page; Formats is eight and four, and its heading keeps to the same two; the note of the download sheet stands over the sheet's third column.
- **The sections of the home page,** each with a composition of its own:
  - the hero (`.hero`, `.flow`, `.window`);
  - Formats (`.formats`): one drawing on three sheets, each under its file's name and joined to the next by what made it (`.triptych`, `.sheet`, `.sheet-tab`, `.sheet-via`), beside the list of the formats (`.ledger`, `.format-list`);
  - the editor (`.editor`): the plate at the page's full width with four pins (`.plate`), its four notes under it (`.legend`) and two more with a drawing each (`.extras`, `.doodle`);
  - automation (`.automate`): a terminal and a settings file as two windows of one height (`.consoles`, `.console`, `.term`);
  - privacy (`.slab`): an ink band, with the three facts as the rows of a table (`.slab-facts`);
  - downloads (`.get`): one sheet (`.get-sheet`) with the app's icon, the state of the release (`.release-state`, which `download.js` writes the version into), a column for each platform with what it needs, its files and how it is installed (`.platform`, `.spec`), the main button, alone (`.get-main`), every download as a row for each CPU (`.cpus`), and the browser as the last row;
  - guides (`.route`): five stops on one connector (`.stop`), which runs down the left edge on a narrower screen;
  - the questions beside the project's note (`.duo`, `.faq`, `.community`);
  - the closing band (`.closing`), which runs into the octopus's own teal;
  - the footer (`.foot-block`): the name and what it is, then four lists: Product (with the page about the product's files), Diagrams (the flowcharts, org charts and architecture pages), Guides (with the index first) and Project, two to a row on a screen under 40rem.
- **Tokens.** Every colour, size and space is a custom property of `:root`. The identity is fixed (`--brand-ink` `#0b0b0c`, `--brand-paper` `#efe9dc`, `--brand-teal` `#007a8c`); the light and dark schemes each set the working tokens (`--paper`, `--paper-raised`, `--paper-sunk`, `--sheet` for a sheet of a drawing, `--ink`, `--ink-body`, `--ink-muted`, `--line`, `--teal` for text, `--teal-fill` for buttons, `--teal-wash` for a tinted band, `--wire` for connectors, `--signal` for the pins, the `--slab` set of the ink band and of the terminal, and three shadows). Text passes WCAG AA in both schemes: the screenshots' script measures every text node against its background.
- **Type.** Besley for text and headings (`--font-serif`; old-style figures in running text), Martian Mono for labels in small capitals, navigation and code (`--font-mono`). The scale is `--text-xs` to `--text-4xl`, fluid at the display sizes. A heading's second phrase is in italic, in teal (`h2 em`), as the main heading's is.
- **Components.** `.btn` and `.btn-ghost`, `.text-link`, `.arrow` (`-down`, `-out`), `.label` and `.label-wire`, `.pin`, `.node`, `.term`, `.band`, `.section-head` and `.head-split` (a heading with its paragraph beside it), `.ruler`, and the parts of the sections above.
- **The other fourteen pages** (the nine of phase 2, then the guides' index and the four pages about kinds of diagram and file) are one layout in the same parts:
  - a head on the drawing area (`.page-head`): where the page is (`.crumb`), its title with the second phrase in the italic, its first paragraph (`.lead`), and beside them what suits the page: the five guides as a route with the one on view filled in (`.head-route`), a title block of three or four facts (`.title-block`, on the privacy page, the four pages about kinds of diagram and file, and the changelog, where the facts are the release, its date and the platforms it is for: `0.2.0`, 25 November 2026, and Linux, Windows, macOS and the browser (the date said `Unreleased` and the third fact said the notes were a draft until they were settled for the release); a test of `cargo xtask` holds the release equal to the workspace version), a capture of the editor in a browser's frame drawn in the stylesheet (`.frame`), or a connector whose end is glued to nothing (`.unglued`, on the page that is not found);
  - a body of two columns (`.doc`): the text (`.prose`, at most 40rem to a line, `--measure-read`) and a rail that stays beside it (`.rail`) with the list of the page's sections (`.toc`);
  - in the text: numbered sections, lists whose mark is a connection point, steps as numbered points on one connector (`ol`), terminals and files (`.console`, `.term`, with `.term-keep` for a file that keeps its lines), tables that scroll sideways on a narrow screen (`.table-scroll`), a note to keep in mind (`.note`), a request to hand to an agent (`.ask`), a capture of the editor (`.shot`) and one sheet of a drawing (`.sheet-fig`; with `.sheet-fig-wide`, a chart or an architecture that takes the text's whole width, inside a `.sheet-scroll` that scrolls sideways on a narrow screen, and a `.sheet-hint` in the caption that says so there);
  - a row to the next page and the way back (`.pager`), and the closing band at a lower height (`.closing-slim`), which the privacy page and the changelog have without the link to the app, and the page that is not found does not have.
  - The page that is not found has the guides' route with four stops in place of a body. **The guides' index** (`guides/index.html`, at `/guides/`) has the head with no picture beside it, then the five guides as the home page's route (`.route`) and the four pages about kinds of diagram and file as a second route of four stops (`.route-4`, as the page that is not found has), each under a heading (`.lost-way`, the second with no space above it), and the short closing band. The masthead's Guides, a guide's place (`.crumb`) and its way back ("All guides", `.pager`) go to it (they went to the home page's guides section, `/#guides`, while `/guides` was an address with no page). The shared parts (the head's tags, the masthead, the footer) are the same text on all fifteen pages; a change to one is a change to fifteen files.
- **Motion,** in CSS alone. On load: the copy settles, the three file types appear, the connector draws itself into the editor, the editor is selected, and the connector runs on to what it writes (about two seconds). Down the page, where the browser can tie an animation to the scroll (`animation-timeline: view()`, asked for with `@supports`): the three sheets come together as they enter the view, and the line of the guides draws itself through its stops. On the other pages the list of sections marks the one being read: each section is a named timeline seen through a band a third of the way down the screen (`view-timeline`, lifted to the two columns' parent by `timeline-scope`), and its row takes the teal, with the point at its end filled, while the section crosses the band; nothing moves, so this is for every reader, in a browser that has both (`@supports`), and the list is a plain list elsewhere. Under the pointer: a sheet is lifted, a platform's column shows its four connection points as a shape does in the editor, a note of the plate makes its pin larger (`:has`), and a guide's stop is filled. `prefers-reduced-motion: reduce` shows the finished state at once, and so does a browser that runs no animation.
- **Widths.** Below 68rem the hero stacks, the list of formats goes under the sheets, the plate's notes are two columns, the two windows stack and the guides run down the page; below 52rem a heading's paragraph goes under it, the platforms are rows and the questions and the note stack; below 46rem the plate keeps a readable size (44rem) and scrolls sideways from its right end, where the drawing is, and its caption says so; below 40rem the masthead wraps and the lists become one column. On the other pages the list of sections goes above the text and the guides' route leaves the head below 68rem, the two links of the pager stack below 52rem, the first guide's picture is the part with the drawing below 46rem, the wide sheets of the org charts and architecture pages keep a width of 36rem and scroll sideways below 46rem, and the short closing band has no picture below 40rem.
