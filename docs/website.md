## Prepare a release

Edit [site/site.json](../site/site.json). This is the source of the publication settings.

| Field | Value to supply |
|---|---|
| `domain` | The HTTPS origin of the pages, with the hostname that readers should see: `https://diacraft.dev`. |
| `app_url` | The HTTPS origin of the web app, a site of its own: `https://diacraft.app`. The pages' "Open DiaCraft in your browser" links go to it, and it is the one other site (beside GitHub's) the pages may name. It is never the pages' own origin. |
| `repository` | The public GitHub owner and repository name, as `owner/name`. |
| `linux_asset`, `windows_asset`, `macos_asset` | The asset filename of each platform from the release workflow (`release.yml`; [Releasing](releasing.md)). Use the exact name, or use `{tag}` for the release tag and `{version}` for that tag without a leading `v` before a digit. They are `diacraft-{tag}-linux-x86_64.tar.gz`, `diacraft-{tag}-windows-x86_64.zip` and `diacraft-{tag}-macos-universal.zip`, and a change to a name there is a change here. |

Run these commands after choosing the settings.

```sh
cargo xtask site --write
cargo xtask site --release
```

The first command writes canonical and social URLs, GitHub links, the pages' links to the app (each is written `<a data-app="" href=...>`, and takes `app_url` and a slash; a link that names the app without the mark is refused, since it would keep the old address when the setting moves) and the address in the picture of the browser's window (`data-app-host`: the host of `app_url`), each download card’s asset name (a card names its platform in `data-platform`: `linux`, `windows` or `macos`), `sitemap.xml` and `robots.txt`. Keep those generated changes with the settings. The release check also rejects the draft domain, repository and an empty asset name for any of the three platforms. The ordinary CI check accepts the draft settings and checks that every generated value matches them.

The static download link goes to the repository’s latest-release page. When configured, the script makes one request to the GitHub release API, without credentials or a referrer, with a 3.5-second timeout. A matching asset switches that platform’s link to the exact GitHub download, so a release that lacks one platform’s file leaves that card on the release page. Keep a release-page link as the fallback when editing a card. The home page’s first button goes to the download section, which holds one card each for Linux, Windows and macOS. Settle the release notes in `changelog.html` and update the development status text in `index.html` when publishing 0.2. Linux and one Intel Mac are the desktop builds recorded as run (the macOS universal download was made on that Mac and its Intel half ran, `hardware-parity.md`); the Windows download is built by the release workflow and has not run yet, and the cards claim nothing of either beyond saying that the downloads are unsigned. [Releasing](releasing.md) · [Platform evidence](hardware-parity.md)

**After the deploy.** Run `cargo xtask deploy-check https://<the domain of site.json> https://<its app_url>` once after the first deploy, and after any change to `site/_headers` or `apps/diacraft-web/_headers` ("Deploy to Cloudflare Pages", step 7; "The web app", "Caching"). It asks each deployed site what it sends for its start page and every file that loads, and fails on a wrong `Cache-Control`.

## Deploy to Cloudflare Pages

The two sites are deployed from the artifacts the release workflow's `site` job makes (`diacraft-site-<name>`, the pages, and `diacraft-app-<name>`, the app), and not from the Git integration. **Why:** Cloudflare's own build image has neither Rust nor the time for the app's build, and a Git-connected project that builds nothing and serves `site/` has no app, so the "Open DiaCraft in your browser" link would lead to a site with nothing in it. **Why two projects:** a Pages project has one `_headers` file and one set of custom domains, and the two sites differ in what they must send: the app's policy allows WebAssembly (`'wasm-unsafe-eval'`) and connects to its own address only, the pages' allows neither and connects to GitHub's API, and the app keeps its hashed files for a year under paths of its own. The repository does not do any of the following; they are for the owner (nothing was set up in Cloudflare or GitHub when this was written):

1. In Workers & Pages, create two Pages projects, each as a **Direct Upload** project (no Git connection), or run `npx wrangler pages project create diacraft-site` and `npx wrangler pages project create diacraft-app`. Choose the production branch name, which `--branch` of the deploy steps must match (`main`). The project names are the owner's to choose; the workflow's comments name `diacraft-site` and `diacraft-app`, and a name that is taken on Cloudflare needs another there.
2. In the repository's secrets, add `CLOUDFLARE_API_TOKEN` (a token that may edit Cloudflare Pages on the account) and `CLOUDFLARE_ACCOUNT_ID` (shown on the Workers & Pages overview page). One token and one account serve both projects.
3. In `.github/workflows/release.yml`, at the end of the `site` job, remove the comment marks of the two steps "Deploy the pages to Cloudflare Pages" and "Deploy the web app to Cloudflare Pages" and give each `--project-name` its project's name. The steps run only for a pushed tag (`needs.plan.outputs.publish`), so a run by hand on a branch builds the artifacts and deploys nothing.
4. To deploy by hand instead: `cargo xtask site --web --out dist/site --app-out dist/app`, then `npx wrangler pages deploy dist/site --project-name diacraft-site --branch main` and `npx wrangler pages deploy dist/app --project-name diacraft-app --branch main`. The two folders are the two deploys; neither holds a file of the other.
5. In each project's Custom domains settings, add its hostname and follow the DNS instructions: **`diacraft.dev` to the pages' project and `diacraft.app` to the app's.** For an apex domain, use the Cloudflare zone in the same account (both domains are the owner's, registered on 2026-11-23). **`www.`** (recommended for the pages, not needed for the app): add `www.diacraft.dev` to the pages' project as a second custom domain and give it a redirect to `https://diacraft.dev` (a Redirect Rule), so that the pages have one address and each page's canonical URL is the one that answers; `www.diacraft.app` is left out, since nothing links it.
6. Check the home page, a guide, an unknown URL, the app's start page (`https://diacraft.app/`), the response headers of both (the app's page has the policy with `'wasm-unsafe-eval'` and no page of the pages does), that the "Open DiaCraft in your browser" link of the home page opens `https://diacraft.app/`, and the static release link. Keep Cloudflare Web Analytics and other script-injection features off in both projects to preserve the privacy policy and the content security policies: a script Cloudflare adds to the app's page would be blocked by its policy, and a change to the app's files would fail their integrity checks.
7. Run `cargo xtask deploy-check https://<the pages project>.pages.dev https://<the app project>.pages.dev`, with the addresses Pages gives the projects, and again `cargo xtask deploy-check https://diacraft.dev https://diacraft.app` once the custom domains are attached (one address checks one site; the run fails if either site has a failure). It prints, for each file, the status, `Cache-Control`, `Content-Encoding`, `ETag` and whether a second request with `If-None-Match` got `304`; it fails on a wrong `Cache-Control` and warns when a `.wasm` part comes back uncompressed. A failure on the glue, the style or the icon of the app, with `max-age=0`, means Pages did not read the splat in the middle of a path in the app's `_headers`: write it in a gaps row, and the fix is to move those three files into `assets/` (which `/assets/*` keeps) and name them in the manifest. A warning on a `.wasm` part means Pages did not compress it: the 17.35 MiB module would then be sent as it is, where a Brotli edge at quality 5 sends 5.82 MB of it (the measurement), and that is for the owner to see.

Pages serves extensionless canonical URLs and uses the top-level `404.html` for missing files. Links in the HTML include the file extension so they also work on an ordinary static file server (the link to the app is to the other site's root, `https://diacraft.app/`). Neither site needs redirect rules (but the optional `www.` one), runtime services or Pages Functions. A file over 25 MiB is refused by Pages and the app holds itself to a budget below that (see "The web app"). ## The web app

`apps/diacraft-web` is the editor window, `DiacraftApp`, started on a canvas by eframe's web runner (WebGPU where the browser has it, WebGL 2 where not). `cargo xtask site --web` builds it, makes it into a folder of its own with the app at its root, which is `https://diacraft.app/` (it was the pages' `/app/` folder before, and the measurements below were made so, with the app's block of `site/_headers`, which is the app's `_headers` now: its files, bytes and headers are the same and its paths lose the `/app` prefix), and checks the result. A person reaches it from the home page's "Open DiaCraft in your browser" link, card button and answer, which go straight to the app's address (`app_url` of `site.json`; each link is written `<a data-app="" href=...>` and `cargo xtask site --write` keeps it there; each carries the label "Open DiaCraft in your browser", which is true of the link). The page about it, `browser.html` (what the browser version needs, keeps and cannot do), is linked from the home page's Features section (the item "Runs in your browser"), from the answer to "Can I try DiaCraft without installing it?" and from the footer of every page ("In your browser"), and its own button goes to the app; a test of `xtask` (`web_site.rs`) holds every link that says "Open DiaCraft in your browser" to the app's address, marked `data-app`, and the footer's link to `browser.html` on all ten pages (owner, 2026-11-23). The module is not one file: it is served in parts, and the data it does not need for its first frame is fetched after it (below).

**Build and check.** `cargo xtask site --web [--dist DIR] [--out DIR] [--app-out DIR] [--app-url URL]` runs `cargo xtask site` on the pages first, copies `site/` into the pages' folder (`dist/site`, or `--out DIR`) with the links to the app at the address of this build (`app_url` of `site.json`, or `--app-url` / `DIACRAFT_APP_URL` for a preview on this machine: an HTTPS address, or `http://localhost:PORT` or `http://127.0.0.1:PORT`, and no other http address; the copy's `site.json` and the address in the browser picture follow it, and `site/` is not touched) and checks the copy as it checks `site/`, then runs `trunk build --release --locked` in `apps/diacraft-web` (or takes the finished build in `--dist DIR`), makes the app's folder from it (`dist/app`, or `--app-out DIR`) and checks that. The two folders are two deploys: neither may be the other or inside it, a folder under `dist/` that an earlier run made is cleared, and any other full folder is refused. The tools are `trunk` 0.22.2, `wasm-bindgen` at the version of the `wasm-bindgen` crate in `Cargo.lock` (trunk reads the lock and downloads the matching program when none of that version is on the `PATH`) and binaryen's `wasm-opt` at the version `Trunk.toml` names (`version_133`: a program on the `PATH` is used only at exactly that version, else trunk downloads one). To install them: `cargo install --locked trunk@0.22.2` and `cargo install --locked wasm-opt@0.133.0` (binaryen version 133), which put both in `~/.cargo/bin`; the release workflow installs the release archives instead, each checked against a SHA-256. A test in `xtask/tests/it/web_site.rs` holds the workflow's versions to the lock and `Trunk.toml`. The command is no step of `ci`: the app's compile check there is `cargo xtask wasm`, and the pages' check is `cargo xtask site`. A warm build takes about 40 seconds, a cold one a few minutes (fat LTO).

**One change to trunk's page.** trunk starts the app with an inline `<script type="module">`, and the app's content security policy has no `'unsafe-inline'`. The command moves that script, unchanged, into `start.js` of the app's folder and has the page load it by `src`. The page's styles are `apps/diacraft-web/page.css`, copied by trunk, for the same reason (no inline style). That script is no longer kept as trunk wrote it: `start.js` is the loader below.

**Loading in parts.** The module is not served as one file. `cargo xtask site --web` cuts it into parts of at most 8 MiB, near equal in size and in order (`parts/diacraft-web-N-<the first 16 digits of its SHA-256>.wasm`: the `.wasm` ending is what makes a CDN compress them, and Cloudflare compresses `application/wasm` and not `application/octet-stream`), copies the data the module does not carry into `assets/` under names with their hashes (next paragraph), and writes `manifest.json`: its version (1), the name of the program's start script (the glue trunk made), the module's size and SHA-256, each part's file, size and SHA-256, and each asset's file, size and SHA-256. The unsplit file is not in the site. `start.js` is `apps/diacraft-web/loader.js`, the site's one script that is not generated (about 280 lines, no `npm`): it reads the manifest, fetches the parts in parallel, counts the bytes that arrive, joins the parts in order into one `ReadableStream`, wraps it in a `Response` of type `application/wasm` and has the browser compile it with `WebAssembly.compileStreaming` while the bytes are still arriving (and while the glue is fetched), then starts the program from the compiled module. **Each part is held to its length and, where the browser has `crypto.subtle` (every https page and `localhost`), to its SHA-256, while the next part comes, and the program is not started until every part has passed**: a bad part stops the stream, and bytes that failed a check are compiled (which harms nothing) and never run. A part that is missing, has the wrong length or digest, comes with an HTML page for a body, or stops coming (nothing for 30 seconds) is told on the page in words with a "Try again" button, never a hang or a blank; a missing or bad manifest or glue the same. The loader reads the manifest to a bound (64 KiB), takes at most 16 parts of 8 MiB and 64 MiB in all, accepts only plain file names of `parts/` and the app's own folder, and has no address in it but the manifest's. The page preloads the manifest and each part (`<link rel="preload" as="fetch" crossorigin>`, so that the loader's fetch of the same address is answered from the preload and each file is requested once: 11 requests at the load, all to the app's own address) and shows how many bytes of the parts have arrived, in a `<progress>` and a line of words in the page's own colours (the theme tokens of the app's text, top bar and canvas, light and dark), until the program has drawn its first frame and takes the element away. The policy is unchanged (`connect-src 'self'`).

**The data the module does not carry.** The splash picture (`diacraft-splash.png`, 0.20 MiB), the cover (2.29 MiB, which no compression makes smaller) and the licence list (`THIRD-PARTY-LICENSES-WEB.txt`, 0.21 MiB) were 2.84 MB of the module, and none is needed for the first frame. They are files of the app's `assets/` (hashed names, cached for good), and the window asks for them through an `AssetHost` (`crates/ui-egui/src/asset_host.rs`; the page's side is `apps/diacraft-web/src/web_assets.rs`, with `assets.rs` for what needs no browser): the splash picture as the page starts the program (the loader asked for it a moment before, so it is in the browser's cache), the cover when the File view first shows its Home page, and the list when its window first opens. While one is on its way the window shows a placeholder with a short wait in it (the splash panel at its size, in the picture's paper colour, with its text; a tile in the File view; the licence card with its words); one that could not be had is said in words (the status bar for the pictures, the card for the list, with a way to try again) and the window works without it. Each is fetched from the app's own folder: the manifest's text names it (a plain file of `assets/`, a size of at most the window's limit for it, a SHA-256), the room is asked for with `try_reserve_exact` before a byte is read, the body is read in pieces and stops at the size, and the whole is held to its digest. The desktop programs keep them inside (`include_bytes!`, now `cfg(not(target_arch = "wasm32"))`). **The icon** is the page's own (`<link rel="icon">`: the module never held it). **Fonts:** Ubuntu Light and Hack (0.67 MB, 3.7% of the module) stay inside. Ubuntu Light draws every word of the first frame and must be there. Hack is drawn by two dialogs only (Insert Symbol and the licence list), so it could be fetched when one opens; it is not, because its bytes are in a crate's source and not a file of this repository (the build tool would have to read them out of the cargo checkout), the window would have to install the faces again after the first frame, and what it saves is 0.31 MB, 1.7% of the module.

**The size, and the 25 MiB limit.** Cloudflare Pages refuses any single file over 25 MiB (26,214,400 bytes). The module was the only large file; it is served in parts, so the limit is held to each part and the budget below is for the module as a whole. So the build before this task was over the limit (25.63 MiB), `wasm-opt` alone only just brought it under, and the `web` profile (`[profile.web]` in `Cargo.toml`, which `index.html` asks trunk for with `data-cargo-profile-release`) and `-Oz` (`data-wasm-opt`) left 5.3 MiB, and 5.0 MiB is left with the file features of and the work merged with them (the file features alone grew the `.wasm` by 242,303 bytes). **Rejected:** `wasm-opt --all-features` gives 19,814,467 bytes, but it declares every proposal (atomics, SIMD, garbage collection, memory64) in the module and lets the optimiser use any of them; the shipped module is optimised with the features Rust enabled (bulk memory, multivalue, reference types, sign extension, non-trapping float conversion) and nothing more. `--converge` saved 15 KB and took minutes. The code is 16 MB of the file and the data 4.9 MB; no crate is more than 8% of it (the engine, the `.odg` and VSDX readers and writers, egui, wgpu's shader translator, the font stacks), so a smaller file would take leaving the readers out of the web build, which is a change of the engine's features and not of the build. Before a change the whole app folder was 21.3 MB and a browser was sent the `.wasm` compressed: 7.1 MB with Brotli (`brotli -q 11`; 8.4 MB at quality 5, which is what the harness's server uses to stand in for an edge's own compression) and 9.3 MB with gzip. Now the app's folder is 21.3 MB in 13 files (the module 18.2 MB in three parts, the cover 2.4 MB, the splash picture 0.21 MB, the licence list 0.23 MB, the icon 0.12 MB, the glue 0.16 MB, the loader 12 KB, the manifest 1.4 KB), and a browser is sent 4.98 MB (4,976,108 bytes: the three parts; 5.19 MB with the splash picture, which the first frame needs) with Brotli (`brotli -q 11`: the three parts and the splash picture, which a first frame needs; the cover and the licence list are fetched only when they are shown).

`cargo xtask site --web` fails for a file over 25 MiB, for a part of the module over **8 MiB**, for the module over **19 MiB** in all (1.65 MiB over what it was when set it, and 1.24 MiB over the 17.76 MiB of the build, so that growth is seen when it happens and not when a deploy is refused or a visitor waits for it), and for any other file of the app over **4 MiB**. If the module outgrows its budget: take features out of the web build (a reader or a writer the browser version can do without), move to opt-level `s` for speed at the cost of size, or tell the owner; the budget is time to load, not the limit of a file (a module past 25 MiB still deploys, in more parts, up to 16).

**What the check holds** (`xtask/src/site/app.rs` and `parts.rs`; tests in `app_tests.rs` and `parts_tests.rs`): the start page and every file it loads exist, and nothing leaves the folder; nothing is inline (no script, style element or style attribute); no file is over the limit or its budget (a part 8 MiB, the module 19 MiB in all, any other file 4 MiB); the manifest is the version the loader reads and agrees with the folder (each part is a file of `parts/` of the size it says, named by the first 16 digits of its hash, and its bytes have that hash; the parts joined are the module whose hash it gives; each asset is there by its name and hash and within its limit; nothing else is in `parts/` or `assets/`); the page preloads the manifest and each part and nothing else, `as="fetch"` with `crossorigin` so that the loader's fetch is answered from them; the parts joined are a WebAssembly module whose memory is not shared (**the build uses no threads and no `SharedArrayBuffer`, so no cross-origin isolation headers are sent**, and the check refuses a module that would need them); the JavaScript has no `XMLHttpRequest`, `WebSocket`, `sendBeacon`, `EventSource`, `eval` or `new Function` and no string that is another site's address; the page, script and style name no vendor; no link or special file is in the folder; and `_headers` is the app's own (`headers::check_app`: for every path the app's policy and the three headers every page has, the rules that cache the parts, the data, the glue, the style and the icon for good, and no other route, no other header and no detach) and, read as Pages applies it, keeps for a year the files named by the SHA-256 of their own bytes and no others ("Caching", below). The module's own text is not scanned for names: it carries the namespace addresses and content types of the file formats it reads (names `AGENTS.md` allows for interoperability) and the licence texts of its libraries with their copyright lines, as the desktop downloads do (`docs/gaps.md`, J6).

**Headers.** Each site has a `_headers` file. The pages' is `site/_headers`: the strict policy and the three headers under `/*`, and the rule for the pictures named by their hash; it has nothing of the app's, and `cargo xtask site` refuses a rule for a path of the app (`/app/...`), a policy under any route but `/*`, and a detach. The app's is `apps/diacraft-web/_headers`, which `cargo xtask site --web` puts in the app's folder; its policy is for every path of its site: `default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; connect-src 'self'; img-src 'self'; style-src 'self'; manifest-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`. It differs from the pages' policy in two places (`manifest-src 'self'`, only names the web app manifest, which `default-src` allowed already): `'wasm-unsafe-eval'` (WebAssembly may be compiled and nothing else evaluated) and `connect-src 'self'` (the page fetches its own `.wasm` file; the pages' policy allows only GitHub's API, for the release lookup the app does not have). The app's file had been a block of the pages' (`/app/*`), which had to take the pages' policy off before it set its own (`! Content-Security-Policy`, since Pages applies every rule that matches a path and joins a header that is set twice); as a file of its own it has no such detach, and the check refuses one. **Five more rules**, `/parts/*`, `/assets/*`, `/diacraft-web-*.js`, `/page-*.css` and `/diacraft-icon-256-*.png`, set `Cache-Control: public, max-age=31536000, immutable` and nothing else: a file they match is named by the hash of its own bytes and never changes under its name, so a returning visitor asks about none of the module's 18 MB, the glue (0.16 MB), the style or the icon (0.12 MB); the page, the loader, the manifests and the snippets of the glue keep Pages' own revalidation, one small conditional request each, and "Caching" says why; `cargo xtask site --web` refuses a folder whose `_headers` lacks them. The other headers (`X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`) are the pages' as they are. The app is not cross-origin isolated and needs no isolation. `Referrer-Policy: no-referrer` on the pages means the app is not told which page of the pages a visitor came from.

**Caching.** The owner asked that everything be kept in the visitor's browser as long as it safely can, so that Cloudflare sends as few bytes as possible. **What Cloudflare documents** ("Serving Pages" and "Headers", read 2026-11-23): requests for static assets are free and unlimited on every plan; Pages always sends an `ETag` and answers `304 Not Modified` to a matching `If-None-Match`; a cacheable asset gets `Cache-Control: public, max-age=0, must-revalidate` unless `_headers` says otherwise; it serves Gzip and Brotli whenever possible; and a path that several `_headers` rules match gets all their headers, a header set twice being joined with a comma. **The rule the site follows:** a file is kept for a year (`public, max-age=31536000, immutable`) if its name is the hash of its own bytes, and no other file is kept at all, so a release reaches a visitor on the next visit and a file that did not change is never sent twice. A name is a hash when it is `<stem>-<16 digits>.<ext>` (the parts and the data of the app, and the glue, style and icon Trunk makes) or `<stem>.<12 digits>.<ext>` (the pictures of `assets/hashed/`) and the digits are the first of the SHA-256 of the file. Trunk hashes the glue, the style and the icon with its own function, whose digits nothing here can recompute, so `cargo xtask site --web` names them again by the SHA-256 of their bytes (`rehash` in `xtask/src/site/app.rs`: the page and the module's manifest follow, and the `integrity` attributes stay, being of the bytes).

**What is not kept.** The page, the loader (`start.js`), `manifest.json`, the web app manifest and its two icons, the site's pages, `styles.css`, `download.js`, `icon-512.png` and `social.jpg` have no hash in their names, so each is one small conditional request on a visit, a `304` with no body when it did not change. **The snippets of the glue** (`snippets/eframe-<hash>/inline0.js` of the app, 280 bytes) are asked about too, and this is where the task found something its brief did not expect: the hash in their folder's name is of the crate's name and version (`wasm-bindgen`'s crate identifier) and not of the file, so a rule that kept them would keep a changed file under the same name, and the page's `integrity` attribute would then refuse it for a year. Making them cacheable would mean rewriting the glue's imports and naming the glue again, for one request of 280 bytes. `styles.css` and `download.js` could be hashed into `assets/hashed/` as the pictures are, which the site check could hold; they are not, since every edit would rename them and rewrite every page, to save 13 KB of conditional requests.

**The check** (`xtask/src/site/cache.rs`, run by `cargo xtask site` over every file of `site/` and by `site --web` over every file of each of the two folders, each a site of its own: the pages or the app). It reads `_headers` as Pages applies it: every rule that matches a path, in order; a pattern with one splat (`*`, any characters, a slash too) and any number of placeholders (`:name`, one or more characters but a slash); `! Name` taking away what earlier rules set; a header set twice joined; at most 100 rules and 2,000 characters in a line, as Pages takes. A pattern for a host, and a value that refers to `:splat` or a placeholder, are refused, since nothing here substitutes them and the site uses none. For each file and each address it is served at (`/` and `/index.html`; `/privacy` and `/privacy.html`) it fails: (1) a file whose name is not a hash of its own bytes (or whose hash is another file's) that is given `immutable`, or a `max-age` or `s-maxage` above 0; (2) a file named by the hash of its own bytes that is not given `immutable` and a year; (3) a file that two rules give two `Cache-Control` values (they would be sent as one joined value, which a browser reads as it likes); (4) a page that has no content security policy, or two (joined, a browser applies both), or one that is not the one the site holds (the pages' own for the pages, the app's own for the app's folder). The tests give each rule a `_headers` that breaks it (`xtask/src/site/cache_tests.rs`, `app_tests.rs`). **Not verified:** that Pages reads a splat in the middle of a path (`/page-*.css` of the app's file) as the check does. Its documentation shows a splat at the end of a path only, and says that a splat "greedily" matches all characters; the check, and the local server of the run below, follow that sentence. A rule that Pages ignored would leave the glue, the style and the icon (0.29 MB) asked about on every visit, and would not break the app: the check after the deploy is where it would show.

**The check after a deploy: `cargo xtask deploy-check <BASE_URL> [<BASE_URL>]`** (`xtask/src/site/live.rs`, tested in `live_tests.rs`). Each `BASE_URL` is a site, `https://host`, or `http://host:port` for a server of one's own: the pages' first and the app's second, or one of them alone; each is checked on its own, from its start page `/`, and the run fails if either has a failure (the same address twice is refused). A link from one site to the other (the pages' to the app) is not followed: that site has its own check. It runs `curl` (as `site --web` runs trunk) and fetches the start page (the home page, or the app's page), the pages it links to, and every file they load: the style, the pictures (`<img>`, `srcset`, the share picture, a style's `url()`), the web manifests and their icons, the app's script, glue and snippets, and, from the module's `manifest.json`, the parts and the data. Each is asked for with `Accept-Encoding: br, gzip`, as a browser asks (the answer is not decoded), and again with `If-None-Match` and the `ETag` it was given. It prints, for each, the status, `Cache-Control`, `Content-Encoding`, `ETag`, the status of the second request (`304` is the right one) and the bytes that came. **It fails** (exit status 1) on a status that is not 200 and on a wrong `Cache-Control`: a file named by its hash must be `immutable` for a year, any other must not be kept. **It warns** when a `.wasm` part, or another text file of 1 KiB or more, comes back uncompressed, when a file has no `ETag` or the second request does not get `304`, and when a file that must be asked about says nothing about asking. It is a command of xtask and not a script because the project's tools are Rust, are tested with the rest, and share what they know: it uses the same shape of hashed name as the offline check, so the two hold one rule. The owner runs it once after the first deploy, and after any change to `site/_headers` or `apps/diacraft-web/_headers`. **Run here** (before the app was a site of its own: one site with the app in a folder; the check is the same for each of the two now) against a local server that applies `_headers` as the documentation says (a Python script outside the repository, written independently of the Rust reader, with brotli at quality 5): 39 URLs, 0 failures, 0 warnings; and against the same site with the rule for the style turned into a rule for the loader, and no compression: 2 failures (the style not kept, the loader kept), 18 warnings (the three `.wasm` parts and fifteen other text files uncompressed), exit status 1. What Pages itself sends, which `_headers` rules it applies and how it compresses a `.wasm` file is not known until that first run.

**What the browser version lacks.** Measured in the app (what it does with files is in "Files in the browser", below):

  and is not built). A press calls `requestFullscreen({navigationUI: "hide", keyboardLock: "browser"})` and then `navigator.keyboard.lock()` (Chrome's Keyboard Lock works only in a full screen the page asked for,
  and the press is the click it needs), says "Full screen. Hold Esc to leave it." in the status bar (and, where the browser gave full screen and no lock, that it kept its keys), and a second press leaves; the

  `onbeforeunload` (`eframe/src/web/events.rs`, `install_window_events`; read from the source the lock pins, 0.37), which no browser fires (the event is `beforeunload`, and the debugger's list of the window's
  listeners names it `onbeforeunload`). That handler does nothing but `Context::on_exit` (the plugins' exit hook, which DiaCraft has none of) and `AppRunner::save`, which saves nothing here: the `persistence` feature

  leaving".** While the drawing has unsaved changes (the engine's `Session::is_dirty`: an edit and its undo leave it clean) the window tells the page (`PageHost::guard_leaving`, in the frame that made the edit, the
  save or the new drawing) and `src/web_page.rs` puts a handler for `beforeunload` on the window, which calls `preventDefault()` and sets `returnValue` (what a browser before the standard needs). **The browser then shows its own
  standard "Leave site?" box** when the tab is closed or reloaded or the page navigates away; the words are the browser's (a page cannot give the box any), and the browser shows it only for a page the person
  has used, which a changed drawing is. **A saved drawing, a new one and a page with nothing in it close or reload with no question, and have no handler on the page at all** (`LeaveGuard`, `src/page.rs`, decides it

## Check a change

Run `cargo test -p xtask`, `cargo xtask site`, `cargo xtask assets` and `cargo xtask brands`. After a change to the web app, also run `cargo xtask site --web` (the app's files, links, sizes and headers, and the pages' copy) and open `dist/site` and `dist/app` with a server that applies `_headers`. After a deploy, run `cargo xtask deploy-check <PAGES_URL> <APP_URL>`. The site check also runs in `cargo xtask ci` and parses each HTML page in Rust. A parsing error reports the page and line. Close elements explicitly and quote attribute values. Use numeric character references or the built-in XML escapes where needed.

The checker resolves local links, fragments, picture sources, manifest icons and stylesheet resources. It checks page titles, descriptions, canonical and social URLs, image descriptions and dimensions, allowed hosts, public text and the Cloudflare security headers. **Public text names no vendor but in the places the owner allowed on 2026-11-23** ("Labels + site/docs format lists"): the lists of the formats DiaCraft opens and saves on the home page, the browser page and the file format guide name the product of the VSDX types, and every page's footer has the notice: one paragraph, `.foot-inner .legal`, at most 90 characters wide, that says the trademark line of the product the VSDX types are named after, that OpenDocument Format (ODF) is an OASIS Standard, that LibreOffice is a registered trademark of The Document Foundation and OpenOffice and Apache OpenOffice of The Apache Software Foundation, and that DiaCraft is not affiliated with or endorsed by Microsoft, OASIS, The Document Foundation or The Apache Software Foundation. Each is an exact text of `PRODUCT_USES` in `xtask/src/brands.rs`, allowed in its own page only; `cargo xtask site` and `cargo xtask brands` (which reads the site's text files too) hold the pages to them, and the export's allowlist keeps their lines. The home page's main message names that product too (the owner, 2026-11-23, as a format statement): its title, its description, the two social tags that repeat them and its heading all hold one phrase of `PRODUCT_USES`, the words that follow "Open, edit and convert", and the page names the product nowhere else but in its format list and its footer. It totals each page and the assets it references, including both theme screenshots, icon variants, the social image and the fonts its stylesheet names, against 1,000,000 bytes (the home page is 898,163, and the largest of the other nine, the first guide, 690,581). **A font is a `.woff2` in `assets/hashed/`** and no other file: the check reads it as bytes, refuses any other kind of font or any other folder, and refuses a site that has fonts while the policy of `/*` in `_headers` does not say `font-src 'self'` ("Fonts"). `cargo xtask export-public --check-only` checks the committed public tree at HEAD.

## Fonts

The site has two typefaces of its own, both under the SIL Open Font License 1.1 and neither with a Reserved Font Name: **Besley** (text and headings, upright and italic; The Besley Project Authors, version 2.001) and **Martian Mono** (labels, navigation and code; The Martian Mono Project Authors, version 1.000). This is the owner's exception for the website (2026-11-23) to the rule that no font is in the repository: the programs bundle neither, AGENTS.md's asset rule says what the exception allows, and NOTICE names the two typefaces, their licence and where its text is. They are three subset WOFF2 files in `site/assets/hashed/`, named by the first twelve digits of their SHA-256 as the pictures are and kept for a year like them, 81,576 bytes together. `styles.css` loads them with `@font-face` and `font-display: swap`, and the home page preloads the upright Besley. Each has a row in [ATTRIBUTION.md](../ATTRIBUTION.md); the licence texts are [`Besley-OFL.txt`](licenses/fonts/Besley-OFL.txt) and [`MartianMono-OFL.txt`](licenses/fonts/MartianMono-OFL.txt), and the files keep the copyright and licence fields of their name tables. `_headers` says `font-src 'self'`, and `cargo xtask site` holds both ("Check a change").

The sources are the variable fonts of `ofl/besley` (commit `c13390277dfb`) and `ofl/martianmono` (commit `c8bba5c4a691`) of the Google Fonts repository, whose SHA-256 begin `71f352d8859c7876` (`Besley[wght].ttf`), `de502a1ab6b06a63` (`Besley-Italic[wght].ttf`) and `c3467843ec1c2574` (`MartianMono[wdth,wght].ttf`). To make the files again (fontTools 4.68.0 with Brotli 1.2.1):

```sh
U="U+0020-007E,U+00A0-00FF,U+2013,U+2014,U+2018,U+2019,U+201C,U+201D,U+2022,U+2026,U+2212,U+2039,U+203A,U+2032,U+2033"
fonttools varLib.instancer "Besley[wght].ttf" wght=400:700 -o besley-roman.ttf
fonttools varLib.instancer "Besley-Italic[wght].ttf" wght=400:600 -o besley-italic.ttf
fonttools varLib.instancer "MartianMono[wdth,wght].ttf" wdth=85 wght=400:700 -o martian-mono.ttf
for f in besley-roman besley-italic; do pyftsubset $f.ttf --unicodes="$U" --layout-features='kern,liga,calt,onum,tnum,ss01' --name-IDs='*' --name-languages='*' --flavor=woff2 --output-file=$f.woff2; done
pyftsubset martian-mono.ttf --unicodes="$U,U+2190-2193,U+2116" --layout-features='kern,calt,case,ccmp' --name-IDs='*' --name-languages='*' --flavor=woff2 --output-file=martian-mono.woff2
```

Besley has no arrows, and Martian Mono no north-east arrow, so every page draws the arrows of its links in the stylesheet (`.arrow`, a line with a filled head, as a connector ends); the arrow characters inside a sentence (File → Open) fall back to a system face.

## Design

`site/styles.css` is the design system, in ten parts that its first comment lists: fonts, tokens, base, layout, masthead, components, the home page's sections, the footer, the article pages, motion. There is no build step and no script.

- **Idea.** The page is the editor's drawing area: a faint grid, a ruler under the masthead, the editor's picture selected with eight handles as the editor selects a shape, and the file types joined to it by right-angle connectors with connection points and filled arrowheads. Arrows, section labels, the plate's numbered pins, the file names of the three sheets and the connector of the guides are drawn in the stylesheet in the same hand. Nothing is drawn in SVG: the check refuses it, in a page and as a file.
- **The grid and the ruler.** The grid is the editor's quarter inch (`--grid-step`), with a heavier line every five, and it is drawn from a point a whole number of heavy lines to the left of the content's edge, so that a heavy line runs down that edge at any width (the hero, and the band of the downloads, whose sheet lies on it). The home page's ruler is a real one: an inch is six rems (`--inch`, 96 CSS pixels), with a tick every eighth, numbered from zero at the content's left edge as the editor's ruler starts at the sheet's. It is under the masthead and again over the footer, and on a screen at least 60rem wide and 40rem high the masthead stays in place while the page moves under it. Every page has it. **The columns:** the sections of two columns are seven parts and five with one space between them (`--split-gap`), so that their second columns begin on one edge down the page; Formats is eight and four, and its heading keeps to the same two; the note of the download sheet stands over the sheet's third column.
- **The sections of the home page,** each with a composition of its own:
  - the hero (`.hero`, `.flow`, `.window`);
  - Formats (`.formats`): one drawing on three sheets, each under its file's name and joined to the next by what made it (`.triptych`, `.sheet`, `.sheet-tab`, `.sheet-via`), beside the list of the formats (`.ledger`, `.format-list`);
  - the editor (`.editor`): the plate at the page's full width with four pins (`.plate`), its four notes under it (`.legend`) and two more with a drawing each (`.extras`, `.doodle`);
  - automation (`.automate`): a terminal and a settings file as two windows of one height (`.consoles`, `.console`, `.term`);
  - privacy (`.slab`): an ink band, with the three facts as the rows of a table (`.slab-facts`);
  - downloads (`.get`): one sheet (`.get-sheet`) with the app's icon, the state of the release (`.release-state`, which `download.js` writes the version into), a column for each platform with what it needs, its file and how it is installed (`.platform`, `.spec`), and the browser as the last row;
  - guides (`.route`): five stops on one connector (`.stop`), which runs down the left edge on a narrower screen;
  - the questions beside the project's note (`.duo`, `.faq`, `.community`);
  - the closing band (`.closing`), which runs into the octopus's own teal;
  - the footer (`.foot-block`): the name and what it is, then three lists.
- **Tokens.** Every colour, size and space is a custom property of `:root`. The identity is fixed (`--brand-ink` `#0b0b0c`, `--brand-paper` `#efe9dc`, `--brand-teal` `#007a8c`); the light and dark schemes each set the working tokens (`--paper`, `--paper-raised`, `--paper-sunk`, `--sheet` for a sheet of a drawing, `--ink`, `--ink-body`, `--ink-muted`, `--line`, `--teal` for text, `--teal-fill` for buttons, `--teal-wash` for a tinted band, `--wire` for connectors, `--signal` for the pins, the `--slab` set of the ink band and of the terminal, and three shadows). Text passes WCAG AA in both schemes: the screenshots' script measures every text node against its background.
- **Type.** Besley for text and headings (`--font-serif`; old-style figures in running text), Martian Mono for labels in small capitals, navigation and code (`--font-mono`). The scale is `--text-xs` to `--text-4xl`, fluid at the display sizes. A heading's second phrase is in italic, in teal (`h2 em`), as the main heading's is.
- **Components.** `.btn` and `.btn-ghost`, `.text-link`, `.arrow` (`-down`, `-out`), `.label` and `.label-wire`, `.pin`, `.node`, `.term`, `.band`, `.section-head` and `.head-split` (a heading with its paragraph beside it), `.ruler`, and the parts of the sections above.
- **The other nine pages** (phase 2) are one layout in the same parts:
  - a head on the drawing area (`.page-head`): where the page is (`.crumb`), its title with the second phrase in the italic, its first paragraph (`.lead`), and beside them what suits the page: the five guides as a route with the one on view filled in (`.head-route`), a title block of three facts (`.title-block`, on the privacy page and the changelog, where the facts are the release, its date and the state of the notes: `0.2.0`, `Unreleased` until the release is tagged, and a draft; a test of `cargo xtask` holds the release equal to the workspace version), a capture of the editor in a browser's frame drawn in the stylesheet (`.frame`), or a connector whose end is glued to nothing (`.unglued`, on the page that is not found);
  - a body of two columns (`.doc`): the text (`.prose`, at most 40rem to a line, `--measure-read`) and a rail that stays beside it (`.rail`) with the list of the page's sections (`.toc`);
  - in the text: numbered sections, lists whose mark is a connection point, steps as numbered points on one connector (`ol`), terminals and files (`.console`, `.term`, with `.term-keep` for a file that keeps its lines), tables that scroll sideways on a narrow screen (`.table-scroll`), a note to keep in mind (`.note`), a request to hand to an agent (`.ask`), a capture of the editor (`.shot`) and one sheet of a drawing (`.sheet-fig`);
  - a row to the next page and the way back (`.pager`), and the closing band at a lower height (`.closing-slim`), which the privacy page and the changelog have without the link to the app, and the page that is not found does not have.
  - The page that is not found has the guides' route with four stops in place of a body. The shared parts (the head's tags, the masthead, the footer) are the same text on all ten pages; a change to one is a change to ten files.
- **Motion,** in CSS alone. On load: the copy settles, the three file types appear, the connector draws itself into the editor, the editor is selected, and the connector runs on to what it writes (about two seconds). Down the page, where the browser can tie an animation to the scroll (`animation-timeline: view()`, asked for with `@supports`): the three sheets come together as they enter the view, and the line of the guides draws itself through its stops. On the other pages the list of sections marks the one being read: each section is a named timeline seen through a band a third of the way down the screen (`view-timeline`, lifted to the two columns' parent by `timeline-scope`), and its row takes the teal, with the point at its end filled, while the section crosses the band; nothing moves, so this is for every reader, in a browser that has both (`@supports`), and the list is a plain list elsewhere. Under the pointer: a sheet is lifted, a platform's column shows its four connection points as a shape does in the editor, a note of the plate makes its pin larger (`:has`), and a guide's stop is filled. `prefers-reduced-motion: reduce` shows the finished state at once, and so does a browser that runs no animation.
- **Widths.** Below 68rem the hero stacks, the list of formats goes under the sheets, the plate's notes are two columns, the two windows stack and the guides run down the page; below 52rem a heading's paragraph goes under it, the platforms are rows and the questions and the note stack; below 46rem the plate keeps a readable size (44rem) and scrolls sideways from its right end, where the drawing is, and its caption says so; below 40rem the masthead wraps and the lists become one column. On the other pages the list of sections goes above the text and the guides' route leaves the head below 68rem, the two links of the pager stack below 52rem, the first guide's picture is the part with the drawing below 46rem, and the short closing band has no picture below 40rem.
