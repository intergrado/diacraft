Everything is a command in `crates/engine/src/cmd/`, and menus, CLI, control channel and MCP all reach the same registry. `cargo xtask layers` enforces the layers. Evidence rules and where code may come from are in `AGENTS.md`.

The layer table in `xtask/src/layers.rs` and in `AGENTS.md` also names crates that have no folder in `crates/` yet: `dxf`, `data`, `pathops`, `plugins`, `vsd`, `vdx`, `pptx`, `emf`, `cadimport`, `interchange` and `tools`. They are planned, and a crate is added to the table before it is built. There is no `diacraft-pathops`: the shape operations run on `craft-pathops` and snapping on `craft-snap`, two engines shared with the other Craft apps through craft-libs (from a fork pinned by revision until their pull requests merge), which `diacraft-engine` uses directly. No crate has L4 today.

The model holds the data of both file formats, each tagged, in `crates/doc` (`package.rs`, `odf.rs`, `stamp.rs`): an object that can carry more has one extension slot, a held value keeps a construct one format has and the cells cannot say exactly beside the stand-in cells, and the writer of that format uses it only while the stamp of those cells still matches, so a held value never overrides a cell. The VSDX reader (`crates/vsdx`, `held.rs` and `unheld.rs`) fills the VSDX side of it: every part of a package that no field of the model rebuilds is a `Part` of `Document::parts`, the relationship rows and content-type rows no field says, the rest of the property parts and `windows.xml` are `Document::vsdx`, the part names of pages and masters are `Page::part_name` and `Master::part_name`, and what each typed element has that no field reads is in its owner's slot, so that nothing a read leaves out is only in the file's bytes; all of it is charged to the read's memory budget before it is kept, but for the bytes of the held parts, which are the package's, moved into the document when the read is done and not held beside it (a save's check of the file it made reads it without moving the parts, so the baseline a save hands back holds the model's own bytes, and the check and the read of the file a save splices into share those bytes where an entry of the package holds them: `diacraft-opc`'s `Package::read_knowing` and `diacraft-container`'s `Archive::holds`, by the size and the checksum, the data read and kept nowhere). The VSDX writer (`crates/vsdx`, `write/held.rs` and `write/model.rs`) has two paths: a save into a file patches the file's own bytes, and a model that holds anything of a VSDX package is written from the model alone, with no file, from the held parts, rows, slots and names the reader gave it: every name the model goes by is reserved before the writer names a part, a part has the rows of its own name, and the rows between pages and masters are made from the model. **Both paths carry the data of the other format** (`crates/vsdx/src/carry.rs`): the `odf` and `native` sides of the slots, the parts and custom properties of the other format are items in DiaCraft's solution part (one for the document, one for its parts, one for each page, master, style and shape that holds some), the bytes are parts of DiaCraft's own, and the reader judges each item against what the file now says. **An object frame of an `.odg`** that holds a compound file and a picture in a format a VSDX file draws is written by both writers as an embedding instead (`crates/vsdx/src/write/objects.rs`: the object part, its relationship part with the picture, a relationship of the type `oleObject` from the page and a shape that says `Object`, the rows made by `write/page_rows.rs`), and the carrier leaves out the part that went natively and the frame's object element.

The `.odg` reader (`crates/odg`, `read/held.rs`, `read/keep.rs` and `read/odfdoc.rs`) fills the ODF side: the markup of each shape, group and page in its `odf` slot, the held values of a shape with their stamps, the named definitions, the layer set, the style elements no style sheet is made of, the units, the font faces, `meta.xml`, `settings.xml`, the roots of the parts, `mimetype`, the manifest's rows and the package entries no field reads, so that a drawing opened from an `.odg` is saved as `.diacraft` and loses nothing of what the `.odg` held.

`.diacraft` is DiaCraft's own file format, the default from 0.2: the package of the model, with the data of VSDX and OpenDocument drawings beside the cells. Its public specification, for programs that read and write it, is [`diacraft-format.md`](diacraft-format.md). The whole-model codec is in `diacraft-sheetxml` (`model`); the package, a zip of the codec's parts, is read and written by `diacraft-native`, and the engine opens and saves it (`file.open`, `file.save` and `file.save_as`, `crates/engine/src/nativefile`: a drawing is saved in its own format unless the name says another, and a `.diacraft` drawing is saved as a VSDX type or an `.odg` from the model alone). The window's file dialogs offer it first (its Save dialog selects it for a new drawing, and its Open dialog lists it first), and it is the engine's default for a new drawing. **A save across the VSDX and OpenDocument formats** (`crates/engine/src/across/`) is the model writer of the target writing the model, with what the target cannot say in its carrier; `across::hold` finds the macro projects and objects in the model (`drop_macros` and `drop_objects` leave them out of the copy the writer is given), `across::onto` makes that copy (and gives an `.odg`'s picture the cells of its box), `across::classes` names what is carried in plain words, and `across::note` is the structured `carried` field and the design's 5.6 words.

**The allocator.** `apps/diacraft` and `apps/diacraft-cli` set mimalloc as their global allocator (`#[global_allocator]` in each `main.rs`, the `mimalloc` crate as a target dependency for every target but `wasm32`), the one C library in the build (owner, 2026-11-21): opening, saving and re-reading a large drawing is mostly small allocations and frees, and a 12,000-shape drawing took 20 to 25 percent less CPU time with mimalloc than with the system allocator (measured: median of ten runs, 4.03 s to 3.02 s through a VSDX, 9.86 s to 7.77 s through `.diacraft`, the files written byte for byte the same, the resident peak 0.5 to 1.5 percent higher). The web build and the library crates keep Rust's default allocator, and the memory budgets of the engine count its own allocations, not the allocator's overhead, so they do not change. **Address space:** mimalloc reserves 1 GiB of address space, not memory, when the process first allocates (it adapts when `ulimit -v` leaves no room for it), so a process under `ulimit -v 3000000` has about a gibibyte less to work in than the budgets assume, and the child tests of `crates/engine`, `native`, `odg` and `container` that run under that limit keep the default allocator, since they check peaks of the process that mimalloc moves. None of them aborted when run on mimalloc: each ended as before or as a refusal in words, and nine of 120 checks that measure the peak or expect a save to fit were off; the seven children of `crates/render` (a frame drawn on 31 threads under the same limit) pass on it (report). Building the two apps needs a C compiler (see `development.md`).

## Threads

The heavy work of a frame runs on the machine's cores, by `std::thread::scope` and nothing else (no thread pool crate; `vello_cpu` is built without its own threads, which abort on a panic and do not blur). **A frame is the same bytes at any thread count**: the pixels and the list of what it left out. The count is the caller's: `Renderer::set_parallel(Parallel::with_threads(n))`, and `diacraft_render::default_threads()` is what an app takes, the machine's cores less one (one is left for the window), at least 1 and at most 64; the environment variable `DIACRAFT_THREADS` (a whole number) overrides it, and 1 is the single-threaded way, which is also the renderer's own until it is told otherwise. The window's render worker (the page and the Print view's sheets), the PNG export (`file.export` and `diacraft-cli export`) and the thumbnail an `.odg` or `.diacraft` is saved with set it; SVG and PDF are written by one thread. The web build (`wasm32`) draws on one thread whatever is said and starts none. A frame of a few shapes (under `Parallel::min_shapes`, 200) or a few pixels (`min_pixels`, 512 by 512) is drawn on one thread: the threads would cost more than they save.

**What is shared out.** The walk of a page, which reads the cells of every shape and is four fifths of a frame of thousands of shapes, is cut into **shares** of neighbouring top shapes (two for each thread), each walked on a thread in a frame of its own onto a recording (`crates/render/src/record.rs`: the steps a walk tells its target, with the box each reaches), and the recordings are joined in order (`share.rs`). The pixels are then drawn in **bands** of rows (`par.rs`), one context for each band **in the frame's own coordinates** and cut off below the band: a context moved up by whole pixels rounds the paths differently and 25 pixels of a 2,000-shape frame came out one step off. A step that cannot reach a band is not drawn in it, and a blur that reaches it is drawn whole, in a context that goes on past the band by the blur's reach.

**When a frame is walked in order on one thread instead** (drawn straight onto the canvas as on one thread: written down to draw its bands, an in-order walk cost 13% more on a page of 12,000 shapes whose walk is four fifths of its frame): the page holds a picture or a placeholder (decoded and laid out through caches the shapes share, in order); the shares together reached a budget (the shapes, the rows of geometry, the characters of text, the cap on blurred shadows and their pixels, the steps of the evaluator) or could have (the walk in order spends no more than the shares' sum, so a frame whose sum is within a budget is the one the walk in order makes); a theme answer could not be had; a share met a bug (it is caught, and the walk in order meets the same bug and is caught by the frame's net). The frame's time budget is the one thing that cannot be the same at any count: it stops the frame at a shape that depends on the machine's speed, at one thread too.

**What holds the threads to the frame's memory.** The shares say what they spend every few steps to one tally and **all stop when the sum passes a budget**, so a page that passes one costs about one budget's work before the walk in order and not one for each thread; the steps of the evaluator are cut into a part for each share; each share keeps its own part of the kept layouts and outlines (the same caps in all). The recordings are capped together (`Parallel::max_steps`, 250,000 steps, about 140 MB; a page of 12,000 shapes writes some 80,000): past it the shares stop, are let go, and the walk is done in order straight onto a canvas, which holds no recording (once: a frame is never walked a second time to draw it). The threads are held to the address space the process has (`ulimit -v`) by the rule a save and an open are held by (`diacraft_container::spare::threads_fit`: each thread counted at 192 MiB, for its stack, its arena and the heaps the arena keeps after it, in an eighth of what the limit leaves beside the address space in use and what the threads of a frame may hold, `Parallel::room`, about 400 MB), so a limited process draws on fewer threads, and neither the frame nor a save after it aborts (`Parallel::usable_threads`; half of what was left at 80 MiB a thread let the thumbnail of an `.odg` of 50,000 shapes take twelve threads whose arenas the save after it needed). The threads of the bands hold the rows of their contexts (the rows above the band too) against `Parallel::scratch_bytes` (128 MiB: a window's frame is drawn by fifteen threads, a 4K screen's by three, one past 64 MiB by one) and the layers of the blurs their bands meet against `Parallel::blur_pixels` (32 million pixels, the cap one frame's layers have on one thread): `ParStats::most_band_threads` says how many drew at once. `crates/render/tests/it/memory.rs` draws the biggest frames of its scenarios on 31 threads in a child under an address-space limit that the rule leaves 31 threads room in (`ulimit -v 52000000`) and holds them to what one thread's frame adds; without the two budgets those children abort.

A save may use the machine's cores too. Nothing in the workspace is a thread pool: the engine chooses a count and the writers take it as a parameter (`diacraft_vsdx::write_with_threads`, `diacraft_native::write_threads`; `write_with` and `write` are one thread). The count is the one a frame and an open take, from one function (`diacraft_container::par::default_threads`; a test reads the three in child processes): by default, the cores less one (a core is left to the window), at least 1 and at most 64; the environment variable `DIACRAFT_THREADS` sets it for tests and measurement, and 1 is the single-threaded path, which makes no thread. On the web build the count is always 1 and no thread is made. The container's lane (`diacraft_container::par`, on `std::thread::scope`) runs tasks on workers that it starts only when a task is given and more tasks wait than workers are free to take them (a worker is free from when it is started until it takes a task, and again as its result is seen, so the workers are never more than the most tasks in flight at once, whatever order the system runs the threads in), and gives the results back in the order the tasks were given, so a caller that writes each result as it comes writes the same bytes at one thread as at thirty-one. **A file saved is the same bytes at any count**: each of `.vsdx` and `.diacraft` is saved at 1, 2, 7 and 31 threads in tests and compared byte for byte, over generated drawings with pictures, masters, parts nothing models and a previous package to copy from.

- **What runs apart.** VSDX: the page and master parts that an edit touched are patched together (a part of the file is parsed, patched and written out, which is the cost of an edit to a drawing of many shapes), and the parts of the package are deflated on workers (`PackageWriter::add_all`). `.diacraft`: the codec makes the pages and masters of the first pass of a save together, each by a thread with an encoder of its own, and holds the ones that fit for the second pass so that they are not made again; the entries are deflated on workers while the next part is made. The check that an open would take each part (the second pass) is on one thread, since the budget of an open is spent from one part to the next. `.odg` and the VSDX writer that writes from the model alone are one thread: a splice into an `.odg` is one `content.xml`, which is one deflate stream, and the entry is not cut into pieces (that would change the bytes).
- **Memory.** What a worker holds is charged before it is made, to the budget that the single-threaded save is held to: the compressed copy of an entry in flight and the bytes of a part the codec has made and not yet written are taken from the `.diacraft` writer's meter (an entry the meter cannot afford beside the ones in flight waits for them, and is made as it always was when none is in flight), the trees of the VSDX parts patched together are held to a window, and the compressions in flight are held to another. A worker that panics is an error of the save, in words, in the place of its entry.
- **Address space.** A thread of a process on Linux takes address space for as long as the process lives (its stack, the allocator's arena and the heaps the arena keeps after the thread), which a process under `ulimit -v` spends from what it may map. Where the system says there is such a limit, a save is held by the rule of an open and a frame (`diacraft_engine::threads`, `diacraft_container::spare::threads_fit`): the threads that fit at 192 MiB each in an eighth of what the limit leaves beside the address space in use and what the save may hold (a VSDX save: its peak figure less the session's hold; a `.diacraft` save: the writer's meter), which is one for a drawing near the edge of what a save may hold; a process with no limit makes the threads it was asked for.

## Threads of an open

A file opens on the machine's cores, and **an open is the same document, report and refusal at any count of threads**: in tests each of `.vsdx`, `.odg` and `.diacraft` is read at 1, 2, 7 and 31 threads and compared by value, report and error, over generated drawings and over files that are damaged or that pass a budget at each edge. The engine chooses the count (`diacraft_engine::open_threads`: by default the cores less one, `DIACRAFT_THREADS` sets it, 1 is the single-threaded path and makes no thread, and on the web it is always 1) and each reader takes it in its limits (`Limits::threads`, 1 by default). The thread helpers are the container's (`diacraft_container::par` is the lane that the saves use, on `std::thread::scope`, and no pool is added).

- **What runs apart.** The entries of the package are inflated on threads (`Archive::inflate_many` and `inflate_each`: each thread reads an entry no further than the size its row states, an entry that holds more is read again in its turn on the calling thread, so the bytes, the counts of work and the first error are those of one at a time). The VSDX reader then **parses the page and master parts ahead of its turn for them** and drops their trees on the threads (`crates/vsdx/src/ahead.rs`): about half of what a read costs on a drawing of many pages is the parse of a part, the figures of its tree and its drop, a pure function of the part's bytes. The `.odg` reader inflates the files its drawing names or keeps (pictures, parts nothing reads) on threads, each held to the media budget in the order of the directory, with what a damaged one gives back. The `.diacraft` reader inflates the pictures the document names on threads into the buffers its pool was charged for, and gives each to the decode when it asks, counted as if inflated then.
- **What does not.** **The model is built on one thread, in the order of the file.** The reader charges its budgets as it builds (the table of what is shared charges a unit by what was read before it, and enters it only if the budget has the bytes of its entry), so the same charges, in another order or from another thread, would make a different model of the same memory or refuse another place: a part read on a thread of its own would have to give up the sharing of equal sheets across parts, or merge its table into the others exactly, which is a task of its own. So the speed-up of an open is the share of the read that is not the build (the parse, the drop of the trees, the inflate): about 1.6 times for a `.vsdx` of many pages, and the most for a file with large pictures (about 1.9 times); an `.odg` with no pictures is the single-threaded read. A single page of tens of thousands of shapes is parsed by the read (a part has one tree).
- **Memory.** A thread holds no more than the budget the single-threaded read is held to. The memory a tree parsed ahead will hold is **set aside from the budget** before the part is asked for (`SheetReader::set_aside`: not charged, so no figure of the report moves) at the dearest the parse of the part can make it, and the parse is bounded to it; **what is set aside goes back to the budget only when the memory is gone**: a tree the read takes is charged by its real size in the place of its set-aside, a tree given to a thread to drop stays set aside until it is dropped, and a charge that the rest of the budget cannot pay, a parse of the read's own that the memory in flight could make too small, and the end of the parts of an index end the work first (the threads finish, every tree made and not taken is dropped) and only then are the bytes paid out. A test build counts, at every change of what is set aside, that the memory of the trees in flight is never more than it. The pictures a thread inflates go into buffers the caller made of the size the directory states, which the budget was charged for before anything was inflated.
- **Address space.** A thread of a process on Linux takes 66 MiB of address space for its stack and its allocator arena, and the arena keeps the heaps that held the trees the thread parsed after the thread is gone (66 to 150 MiB for each thread was measured): a process under `ulimit -v` spends that from what it may map, and aborts when it cannot, in the save that follows an open as much as in the open. A read holds its threads to the few that keep up with the one that builds (three work ahead on the trees, eight inflate) and to an eighth of the address space the process has left beside the memory the read may hold, at 192 MiB a thread (`diacraft_container::spare::threads_beside`, the rule a save and a frame are held by too, `threads_fit`), which is none at the reader's own budget under `ulimit -v 3000000`: the largest drawing the budget admits is read as the single-threaded read, in the same address space, and a read with a budget that leaves room uses the threads that fit. A process with no limit makes the threads it was asked for, up to those counts. A thread that fails is an error in words (`read_worker_failed` for a VSDX read), never a panic of the read.
