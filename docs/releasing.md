# Releasing DiaCraft

The first release is 0.2 (`docs/roadmap.md`). A pushed tag `vMAJOR.MINOR.PATCH` runs `.github/workflows/release.yml`, which builds DiaCraft in release for **Linux and Windows, each for Intel/AMD (x86_64) and for ARM64, and for macOS (a build for Apple silicon and one for Intel; no universal build: the owner, 2026-11-25)** and uploads fourteen downloads (archives and installers), six MCP bundles (`.mcpb` files, one for each of the six builds) and a `SHA256SUMS.txt` file to a **draft** GitHub release of the tag. The owner reads the notes and the files, then presses Publish. **The same tag deploys the two websites** (`diacraft.dev`, the pages, and `diacraft.app`, the web app) to Cloudflare Pages, when it is not a pre-release: the `deploy` job, which waits for every build and the checksums, sends each to the Pages project of its own ("The websites" below; `docs/website.md`, "Deploy to Cloudflare Pages"). The workflow has run by hand on GitHub three times, on the branch that became 0.2.0, and the third run (45521917111) passed: every build, the two ARM64 ones included, and every installer and archive, built and smoke tested on its own runner. A run by hand uploads and deploys nothing; what only a tag does has run on the tag `v0.2.0`, twice: the runs made the draft release, uploaded the fourteen files and the checksums and deployed the two websites, and 0.2.0, the first public release, was published on 2026-11-25. The workflow ran for the tag `v0.2.1` the same day, the first release whose files have the names below, and for the tag `v0.2.2` that evening, the first with the six MCP bundles; 0.2.2 is the latest published release, and 0.2.3 is the version on `main` (see "What was checked, and what was not"). The reference app was not inspected, and the downloads have not been opened in it by the project.

**The workflow is DiaCraft's own, and the one exception to the rule that workflows call the shared ones** (`AGENTS.md`, "CI workflows"): the shared `release.yml` needs org signing secrets and runners. It uses no action but GitHub's own `actions/checkout`, `actions/upload-artifact` and `actions/download-artifact` (the last only in the `deploy` job, to take the two sites the `site` job kept; all pinned by commit); the GitHub CLI (`gh`) that every runner has uploads the files. Every tool it downloads, besides the Rust toolchain, is pinned by version and by the SHA-256 of the file (the `site` job's trunk, `wasm-bindgen` and binaryen, the Linux job's `appimagetool` and AppImage runtime, the Windows job's WiX), and the workflow checks it before it runs it. The one tool that is not a download, wrangler (the `deploy` job's deploy to Cloudflare Pages), is pinned by an exact version and a lock that holds the SHA-512 of each of its packages ("The websites").

`<version>` is the tag without its `v` (`0.2.3` for the tag `v0.2.3`), which the workflow takes from the tag (`version=${tag#v}` in the `plan` job) and the packaging scripts are given: the names are the ones an app launcher reads, `diacraft-<version>-<system>-<cpu>[-portable].<extension>`, with a version that starts with a digit. **The CPU is written as the launchers write it:** `x86_64` and `aarch64` for Linux (the ARM build is `aarch64` in a name and `arm64` in the `.deb`'s own architecture field), `x64` and `arm64` for Windows, `arm64` and `x86_64` for macOS; **the Windows zip ends in `-portable`** (it needs no installer; its folder inside is `diacraft-<version>-windows-<cpu>`) and no other file does. The tag and the release's address keep the `v`: `https://github.com/<repository>/releases/download/v0.2.3/diacraft-0.2.3-linux-x86_64.AppImage`. The checksums file is `SHA256SUMS.txt`, which the launchers look for by that name. A rehearsal's version is its `dev-<commit>`, which starts with no digit, as it is no release. The file names follow one pattern, which the site's fourteen asset names in `site/site.json` (`assets`, one for each download) are, and `cargo xtask site --release` refuses an empty one; a test holds `site.json`, the checksums job's list of the downloads (its six MCP bundles are named apart), the draft's notes and the home page to the same fourteen (each once in the CPU rows of the cards, whose every row lists all its formats: the three main buttons repeat a link of their card's rows), and `cargo xtask site` holds every link of the pages to a file of that list. **Names that a format has its own convention for** (`diacraft_0.2.0_amd64.deb` for a Debian package, `Name-Version-x86_64.AppImage` for an AppImage) are not used: nothing reads a file name, since apt and dpkg read the fields inside the package and an AppImage's own tools its entry, so one pattern for every file is what a person reads in the release. `packaging/package.sh` makes the archives (and the macOS image); `make-deb.sh`, `make-appimage.sh` and `make-msi.sh` make the installers; the checks they share (a name's characters, the licence files, the CPU read from a program's own header) are in `packaging/common.sh`. The release workflow and the CI workflow run the same scripts, so what a release would make is made, and for Windows and macOS tried, on every push too.

**The MCP bundles** (the owner, 2026-11-25) are the same release's other six files: an app or a directory of MCP servers installs one, and the official MCP Registry's entry names them. They are no download of the website (no button shows one; `site.json` names none, and the release workflow's list of the downloads for the site is the fourteen), and the checksums job lists all twenty files. **The names** are the downloads' with `mcp` after `diacraft` (`diacraft-mcp-0.2.2-linux-x86_64.mcpb`): the registry wants "mcp" in the address of a bundle, and the CPU is written as the downloads write it. **One bundle for each system and CPU**, not one for all: the format's `compatibility.platforms` and `platform_overrides` name a system (`linux`, `win32`, `darwin`) and have no word for a CPU, and a launcher script would be handwritten JavaScript or a shell script that every host would have to run. The list of the six is `BUNDLES` in `xtask/src/mcp.rs`, which a test holds equal to the workflow's list. `packaging/mcp-bundle.sh` makes one (the manifest is `packaging/mcp/manifest.json` with the version, the system, the program and the repository of `Cargo.toml` filled in; the manifest's keys are the format's, which a test holds to the published schema's, since the format refuses a key it does not know), and `packaging/mcp-bundle-check.sh` unpacks it and runs it. A Windows runner has no `zip` or `unzip` in Git Bash, so both scripts use PowerShell there, as `package.sh` does.

**The websites.** The `site` job builds the two sites of the website and keeps each as an artifact. The `deploy` job, the last of the workflow, takes the two artifacts and sends them to Cloudflare Pages with `wrangler pages deploy`: the pages (`site-dist`) to the project `diacraft-site`, which serves `diacraft.dev`, and the web app (`app-dist`) to `diacraft-app`, which serves `diacraft.app`, as production deployments. It `needs` the plan, the `site` job, the three build jobs and the checksums, and runs only when all of them succeeded and the tag is not a pre-release (the owner, 2026-11-24: the deploy waits for all the builds): a build that fails, a job cancelled, a run by hand on a branch and a tag with a suffix (`v0.2.0-rc1`) deploy nothing. The steps read two repository secrets, `CLOUDFLARE_API_TOKEN` (an account token that may edit Cloudflare Pages and nothing else) and `CLOUDFLARE_ACCOUNT_ID`, and only the two deploy steps see them. **A site or app fix between releases** is deployed by hand with `.github/workflows/deploy-site.yml` ("Deploy the website": Actions, Run workflow, on `main` only), which builds the two sites as the `site` job does, builds no download, deploys them as this job does, and is in the same concurrency group (`deploy-site`), so that it never deploys while a release does; its download links still point at the release in `Cargo.toml` (`docs/website.md`, "Deploy to Cloudflare Pages"). The two projects must exist before the first tag (`docs/website.md`, "Deploy to Cloudflare Pages", step 1), or the deploy steps fail at the end of the run. **The tool is pinned like the others,** but it is an npm package with 132 packages under it, so the pin is a lock: `packaging/cloudflare/package.json` names the one exact version and `package-lock.json` holds each of the 133 packages with the SHA-512 of its file; the step runs `npm ci --ignore-scripts --engine-strict` on the runner's Node (22.23.5 on the `ubuntu-24.04` image of 2026-11-16, and wrangler needs 22.12 or later) and stops unless the program reports the version asked for. To move it, see `docs/website.md`; a test holds the version of the manifest, the lock, `WRANGLER_VERSION` in the workflow and this row to one value, and every package of the lock to the npm registry and a SHA-512.

**The one licence exception: a CI-only deploy tool, never shipped** (the owner, 2026-11-24; named in `AGENTS.md`, "Clean-room", rule 4, and in the public rules). wrangler's dependencies include a library for resizing pictures (`sharp`, for its local development emulator, which a deploy never runs), whose Linux build carries the image library libvips under the LGPL (`@img/sharp-libvips-linux-x64`). `npm ci` installs it on the runner: it is an optional package of `sharp`, and `--omit=optional`, which would leave it out, leaves out wrangler's `workerd` program too, and wrangler then stops when it starts (tried). The tool runs only on the release build machine, in the `deploy` job: it is not a dependency of DiaCraft's programs, is not linked into or shipped with any download, and no source of it is read here. The exception covers that tool and nothing in the Cargo dependencies, which `cargo xtask deny` still holds to its licence list.

**The licence files.** Every download holds these five files, and `packaging/package.sh` stops when one is missing or empty: `LICENSE-MIT` and `LICENSE-APACHE` (the two licences DiaCraft is offered under), `NOTICE` (the credits and the notices of the two fonts and of the mimalloc C library), `ATTRIBUTION.md` (where each picture comes from) and `THIRD-PARTY-LICENSES.txt`. The last is the notice that the licences of the Rust crates ask for: it lists every crate `diacraft` and `diacraft-cli` are built from on Linux, Windows and macOS (Apple silicon and Intel), with its licence and the licence DiaCraft uses it under (MIT where a crate offers a choice), and gives each licence and NOTICE text once, with the crates that carry it. The Linux `install.sh` puts the five under `share/doc/diacraft`. The window carries the same text built in: File, About, Third-party licences (`app.licenses`) shows it in a list that scrolls, so it is there wherever the program is.

`THIRD-PARTY-LICENSES.txt` is made by `cargo xtask licenses` and kept in the repository, so that a download, the window and the site's link (`site/index.html`, to the file on GitHub) all say the same. **When a dependency changes** (`Cargo.lock`, a version, a feature or a new crate), run `cargo xtask licenses` and commit the file: `cargo xtask licenses --check` is a step of `cargo xtask ci`, and the Linux job of the release workflow runs it before it builds, so a tag whose file is stale or whose dependency has no licence text stops there. It fails for a crate with no licence text, for a licence (or a licence file inside a crate) that `deny.toml` does not allow, for a crate that compiles C code that `xtask/src/licenses/policy.rs` does not name, and when the file is not what the lock says. Two things it cannot know: the C and other native code of a crate that has no build dependency on `cc` or `cmake`, and a licence text that a crate's sources do not carry. It needs the sources of every platform's crates; cargo fetches them (with a network) the first time. The number of crates each program is built from on each platform is in the first lines of the file. The programs link no TLS stack and no `ring` or `aws-lc` (the print library's Windows build script does, on the build machine, and that is in no program); the one C library they compile in is mimalloc, whose crate carries its licence text. **Open question for the owner (`docs/gaps.md`):** the Linux build includes `wayland-protocols-plasma`, an MIT crate whose protocol description files come from KDE and say LGPL-2.1-or-later; the file lists the LGPL text and says so, and `AGENTS.md` says no LGPL code is depended on.

**The version.** `--version` of both programs prints the version in `[workspace.package]` of `Cargo.toml`, so the workflow stops at once when the tag and that version differ (`v0.2.3` needs `version = "0.2.3"`). The build's own identity, the build line that the splash, the About panel and `app.version` show under the version, is the tag's version: the workflow sets `DIACRAFT_BUILD_GIT` to the tag and `DIACRAFT_BUILD_YEAR` to the year of the tagged commit (`apps/diacraft/build_info.rs`; the clock is never read), and a build of the tag `v0.2.3` says plain `0.2.3`. Before the tag exists a build says `0.2.3-dev+<commit>` (and `0.2.3+12.<commit>` twelve commits after it), whatever the last tag is called, so a build made for the release does not read as the one before. `packaging/smoke.sh` checks the versions and the line in the built programs and again in the unpacked download. The macOS app's `Info.plist` says the tag's version, and the workspace's for a name that holds none (a rehearsal's `dev-<commit>`; `packaging/package.sh` reads `[workspace.package]`).

## Cut a release (the owner's steps)

1. **Settle the site** (`docs/website.md`). `site/site.json` names the public domain and repository (`https://diacraft.dev` and `intergrado/diacraft`, both set). Settle the release notes in `site/changelog.html` (the title block's release and date, and a section "New in <version>" at the top) and the release's state in `site/index.html` (`.release-state`, the version and its day, as "0.2.3, released 27 November 2026"); both are settled for 0.2.3 (and again with the features merged after it), as they were for 0.2.0, 0.2.1 and 0.2.2. **Read the Features page again** (`site/features.html`, at `/features`; the owner, 2026-11-26: it is updated with every release): it says, area by area, every feature that works in the release and only what ships, with no list of what comes next and no section of limits, each claim true to the docs it rests on (`docs/website.md`, "Editorial sources"); add what the release brings, change what it changed, and move its version (the title block's release, the lead's and the description's "DiaCraft <version>"), which `xtask/tests/it/version.rs` holds to the workspace's. **Read the feature comparison page again** (`site/feature-comparison.html`): its DiaCraft column is computed from `docs/parity-checklist.md`, so re-score the checklist's rows that the release changed first (`cargo xtask parity`), read the seven rows that name no checklist row (`diacraft = { rule = "manual" }` in `docs/parity-matrix.toml`: the file formats and the platforms) again from `docs/file-format-parity.md` and `docs/hardware-parity.md`, check that the three features only DiaCraft has still ship and that no other tool has gained one, and read again the cells of the other tools whose pages changed (a cell names its sources and the day it was read; the page's "As of" line takes the days from the data). Run `cargo xtask site --write`, then `cargo xtask site --release`, and keep the generated changes in the commit (the comparison page's tables, the footers and the sitemap are among them) (the pages' download links are the files of the release of `Cargo.toml`'s version, so run `cargo xtask site --write` again after step 2 changes it).
2. **Set the version.** Run `cargo xtask version set 0.2.3`: it sets `version` in `[workspace.package]` of `Cargo.toml` to the release and refreshes `Cargo.lock` (the release builds with `--locked`); commit both. It is 0.2.3, and the programs read the version from there; the site's download links and the home page's structured data (`softwareVersion` and the release page) are made from it, so a changed version is followed by `cargo xtask site --write` (the gate's `site` step fails on pages made for another version). **Three places write the version out and are changed by hand,** and their tests fail until they are (the release of 0.2.1 found the first two): the two examples of the answer of `ui.inspect` in `docs/control-protocol.md` (`"version":"0.2.3"`; `xtask/tests/it/version.rs` holds them to the workspace version), the Features page's title block, lead and description (step 1; the same test holds them), and the changelog's head in `site/changelog.html`, whose `<title>`, description, `og:title` and `og:description` name the release (`og:title` is the `<title>`, and the description is 140 to 160 characters: `xtask/tests/it/seo.rs`); after them, `cargo xtask site --write` makes the `twitter:*` tags and the structured data of the page from those four. The sitemap's `<lastmod>` dates are the last commits' own: run `--write` again after the commit that changes a page to move its date (`docs/website.md`, "Search engines and social cards").
3. **Pass the full gate** on that commit (`cargo xtask ci`, which includes `cargo xtask licenses --check`: run `cargo xtask licenses` first if a dependency changed) and push `main`. The `windows` and `macos` jobs of `ci.yml` build and smoke test both platforms on that push: do not tag a commit they have not passed.
4. **Tag and push the tag:** `git tag -a v0.2.3 -m "DiaCraft 0.2.3"`, then `git push origin v0.2.3`. A tag with a suffix (`v0.2.0-rc1`) makes a pre-release.
5. **Watch the Release workflow** (the Actions tab). `Plan` checks the tag against `Cargo.toml`; `Draft release` makes the draft; `Linux (x86_64)`, `Linux (arm64)`, `Windows (x86_64)`, `Windows (arm64)` and `macOS` build, smoke test, package, smoke test the unpacked archive, make the installers, smoke test each installer (below) and upload the files (the two CPUs of a system run side by side, and one that fails does not stop the other); `SHA256SUMS.txt` checks that exactly the twenty files (the fourteen downloads and the six MCP bundles) are there, writes the sums, checks the file in `sha256sum`'s own format and uploads it. The run's summary lists the sums. `Website and web app` builds the two sites; `Deploy the websites`, the last job, deploys them to Cloudflare Pages once every job before it has succeeded (the sites are live when it ends, before the draft is published, and a tag whose build failed deploys nothing).
6. **Publish.** Open the draft release, write the notes (the draft holds a short text with the file names), look at the files, and press Publish. The site's download buttons are the addresses of the files of that release already (`cargo xtask site --write` makes them from the version), so they answer once the release is published; `site/download.js` only moves them to a newer published release.

7. **Publish the MCP server to the registry** once the release is published (the next section). It is not a step of the workflow.

**Before the first tag,** make the two Cloudflare Pages projects `diacraft-site` and `diacraft-app` (Direct Upload, production branch `main`) and attach `diacraft.dev` to the first and `diacraft.app` to the second (`docs/website.md`, "Deploy to Cloudflare Pages", steps 1 and 5); the two secrets are in the public repository. After the first deploy, run `cargo xtask deploy-check` against the two sites by hand (step 7 there).

**A rehearsal costs nothing.** Run the workflow by hand on a branch (Actions, Release, Run workflow): it builds, smoke tests and packages everything, uploads nothing to a release, deploys nothing to Cloudflare Pages, and names the files `diacraft-dev-<commit>-...`; look at the names in the artifacts: each is the pattern above, with `dev-<commit>` as the version. **Every package of the run is kept as an artifact for 7 days** (one for each job: `diacraft-dev-<commit>-linux-x86_64`, `-linux-arm64`, `-windows-x86_64`, `-windows-arm64` and `-macos`, which holds the two macOS downloads), so that the installers can be downloaded from the run's page and tried on real machines before a tag is pushed; a run on a tag keeps them too. Or push a pre-release tag and delete the draft and the tag afterwards (the tag must match `Cargo.toml`'s version, so a pre-release tag needs `version = "0.2.0-rc1"`); a pre-release tag deploys no website, so it leaves the live sites as they are.

**How each installer is checked on its runner**, before anything is uploaded:

- **`.deb`**: `dpkg-deb --info` and the package's architecture against `dpkg --print-architecture`; `sudo apt-get install --no-install-recommends`; both programs there, the entry and the icon; `ldd` finds every library; `packaging/smoke.sh` on `/usr/bin` with the licences in `/usr/share/doc/diacraft`; `sudo apt-get remove`; nothing left behind.
- **AppImage**: run with `--appimage-extract-and-run`, since a runner has no FUSE: `--version`, and `--cli --version` for the command line; then `--appimage-extract`, the AppDir looked at, and `packaging/smoke.sh` on its `usr/bin` with the licences.
- **`.msi`** (`packaging/windows/check-msi.sh`): `msiexec /i ... /qn` for the user; both programs and the five licence files in `%LocalAppData%\Programs\DiaCraft`; `packaging/smoke.sh` on them there; the shortcut; the folder on the user's `PATH`; each of `.diacraft`, `.vsdx` and `.odg` listing DiaCraft in `OpenWithProgids` and none with DiaCraft as its default value; `msiexec /x ... /qn`; the folder, the shortcut, the `PATH` entry and every registry entry gone. It stops at once if DiaCraft is installed already, so as not to remove a person's own.
- **`.dmg`**: attached read only with `-nobrowse` and no window, looked at as the unpacked zip is (both architectures in both programs, `Info.plist`, the icon, the licences, the signature, both programs run), the link to Applications, the README; detached.

**A failed run.** `Re-run failed jobs` resumes where it stopped: an upload uses `--clobber`, and `Draft release` finds the draft it made. To start over, delete the draft and the tag and tag again.

## Publish the MCP server to the registry

After the release is **published**, the owner or the coordinator lists the server in the official MCP Registry (registry.modelcontextprotocol.io) as `app.diacraft/diacraft`. Nothing in the workflow does it: the entry names the files of the release by their addresses (a draft has none that answers), and a version that is published to the registry cannot be changed, so it is made by hand once for each release. The first release with the bundles is the first that can be published.

1. **See that the site proves the domain.** The registry trusts a name `app.diacraft/...` to whoever controls `diacraft.app`, and asks for `https://diacraft.app/.well-known/mcp-registry-auth` (a `200`, no redirect, the record as text; [`website.md`](website.md), "The registry's proof of the domain"). The tag's deploy sends it with the web app; check it: `curl -si https://diacraft.app/.well-known/mcp-registry-auth` says `200`, `content-type: text/plain` and the record of `apps/diacraft-web/mcp-registry-auth`, or run `cargo xtask deploy-check https://diacraft.dev https://diacraft.app`, which asks for it too. **If it answers the app's page,** the deploy left the file out (a name that starts with a dot): that is what to look at first. The registry has a second way to prove the domain, the same record as a DNS `TXT` record at the apex of `diacraft.app` (the owner sets it in Cloudflare's DNS), which is the one to use if Pages will not serve the folder.
2. **Make the entry** on the checkout of the release's tag, in a folder of its own outside the repository (the file is not committed: it holds the release's hashes):

   ```
   gh release download v0.2.2 --repo intergrado/diacraft --pattern SHA256SUMS.txt --dir ~/projects/diacraft-run/mcp-publish
   cargo xtask mcp-server-json ~/projects/diacraft-run/mcp-publish/SHA256SUMS.txt --out ~/projects/diacraft-run/mcp-publish/server.json
   ```

   It refuses sums that miss a bundle, name one twice, name one that `BUNDLES` does not list, or are of another version than the checkout's. Read the file: the name, the description, the version, and one `mcpb` package for each of the six bundles with the address of its file and its SHA-256.
3. **Log in as the domain and publish**, with `mcp-publisher` (a release of `modelcontextprotocol/registry`; `brew install mcp-publisher` or its tarball). The login signs a challenge with the private key of the pair whose public half is the record on the site. The private key is the file `~/.config/diacraft/mcp-registry-ed25519.pem` (mode 600; it is **never** in the repository and is not copied anywhere); the login takes its 32 bytes as hex, which the environment carries and the command line would show in the process list:

   ```
   cd ~/projects/diacraft-run/mcp-publish
   MCP_PRIVATE_KEY="$(openssl pkey -in ~/.config/diacraft/mcp-registry-ed25519.pem -noout -text | sed -n '/priv:/,/pub:/p' | sed '1d;$d' | tr -d ' :\n')" mcp-publisher login http --domain diacraft.app
   mcp-publisher publish
   ```

   (`--private-key <hex>` or `--private-key-file <file>` does the same.) `publish` reads `server.json` in the current folder.
4. **Look at it:** `curl -s 'https://registry.modelcontextprotocol.io/v0.1/servers?search=app.diacraft'` lists the entry with its six packages. `mcp-publisher status --status deleted` hides a version that was a mistake.

**The key pair** was made once with `openssl genpkey -algorithm ed25519`. The public half is the record `v=MCPv1; k=ed25519; p=<32 bytes, base64>` in `apps/diacraft-web/mcp-registry-auth`, which is in the repository and on the site; the private half is only the file named above. If the private key is lost or leaked: make another pair, replace the record, deploy the site again (`deploy-site.yml`), and log in with the new key.

## Opening an unsigned download

0.2 is **unsigned**: the programs carry no certificate of a publisher. Each download's `README.txt` says what follows, and the site's download cards say a confirmation may be asked. Checking the file against `SHA256SUMS.txt` is how to know it is the one that was released (`sha256sum --check --ignore-missing SHA256SUMS.txt` on Linux, `shasum -a 256 FILE` on macOS, `Get-FileHash FILE` in PowerShell).

- **Linux.** Nothing to confirm. The `.deb` installs with `sudo apt install ./diacraft-<version>-linux-<cpu>.deb` (and `sudo apt remove diacraft` removes it); the AppImage runs after `chmod +x` (where FUSE is not installed, `--appimage-extract-and-run` runs it with no mount); the archive unpacks and runs `./diacraft`, or `./install.sh` adds it to the application menu for the user (it needs no administrator rights, and `./install.sh --uninstall` removes it).
- **Windows.** SmartScreen may say "Windows protected your PC" for a program or an installer it does not know. Choose "More info", then "Run anyway". Unblocking the `.msi` or the zip first (right-click, Properties, Unblock) avoids the question for everything in it. The `.msi` installs for the user alone, so it needs no administrator rights; Settings, Apps removes it.
- **macOS.** The first opening is refused with a message that Apple cannot check the app. Either open System Settings, Privacy & Security, scroll to the line about DiaCraft and choose "Open Anyway" (macOS 15 and later; on macOS 14 and earlier, Control-click the app, choose Open, then Open); or remove the quarantine mark in Terminal: `xattr -dr com.apple.quarantine /Applications/DiaCraft.app`. The same goes for `diacraft-cli`. Both programs carry an ad hoc signature, which an Apple silicon Mac needs to run a program at all; it says nothing about who made them. The disk image is not signed or notarised either, and opens normally.

## Signing

The hooks are in place and switched off. Each is a commented block in `release.yml` that names the secrets it reads.

- **macOS** (Developer ID, Apple Developer Program). Secrets: `MACOS_CERTIFICATE` (the "Developer ID Application" certificate and key as a `.p12`, in base64), `MACOS_CERTIFICATE_PASSWORD`, `MACOS_SIGN_IDENTITY` (`Developer ID Application: Name (TEAMID)`), `APPLE_ID`, `APPLE_TEAM_ID` and `APPLE_APP_PASSWORD` (an app-specific password). Uncomment the step "Import the signing certificate" and the step "Notarise the disk image" of the `macos` job, and add `MACOS_SIGN_IDENTITY` to the environment of "Make the download": `packaging/package.sh` then signs the CLI, the app's program and the app with the hardened runtime and a timestamp, where without it they are signed ad hoc, and signs the disk image too. The notarising step submits the `.dmg` and staples the ticket to it, so that a person who opens it with no network gets no question; a zip has no place for a ticket, so the app in the zip is checked online.
- **Windows** (Authenticode). Secrets: `WINDOWS_CERTIFICATE` (a `.pfx`, in base64) and `WINDOWS_CERTIFICATE_PASSWORD`. Uncomment the step "Sign the programs" of the `windows` job, which runs `signtool` on both programs before they are smoke tested and packaged, and the step "Sign the installer" after "Make the .msi", which signs the `.msi` before it is installed and smoke tested (a signed installer is what Windows shows a publisher's name for). The x64 `signtool` runs on the ARM runner too, under emulation, and signs programs of either CPU. SmartScreen's reputation comes at once with an EV certificate or a cloud signing service, and over time with an ordinary one.
- **Linux.** Nothing is needed. A detached GPG signature of `SHA256SUMS.txt` can be added to the `SHA256SUMS.txt` job; an AppImage can carry a signature of its own (`appimagetool --sign`), which no tool needs to check.

## Not done, and what it would take

- **A wizard for the `.msi`** (a licence page, a folder to choose): the WiX UI extension, one more package to pin. The installer is per user, into a fixed folder, and shows Windows' progress bar.
- **MCP bundles are unsigned and were not installed in a host**. The macOS program is signed ad hoc and the Windows one is not signed; the bundle itself carries no signature of the format's (`mcpb sign`). The format's own validator (`mcpb validate`, an npm package) was not run, and no app that installs bundles was available: the manifest was held to the keys of the format's published schema, and the program was run as the manifest says. The registry's entry has six packages and no field that says a system or a CPU, so a client tells them by name.
- **Update channels.** No apt repository, no AppImage update information (`zsync`), no `winget` or Homebrew entry: each is a download of a person's own choosing, from the release page.
- **Manual pages** for `diacraft` and `diacraft-cli` in the `.deb` (lintian warns of it), and MIME types in the launcher entry, so that a Linux file manager offers DiaCraft for `.diacraft`, `.vsdx` and `.odg` (the entry names none: a type name of the reference format holds its product's name, which the site and the sources leave out outside the lists the owner allowed).
- **An icon on `diacraft.exe`.** The window's icon is set at run time, so the taskbar and the title bar show it, but the file in Explorer has the default icon. Embedding one needs a resource compiler in the build (a `build.rs` with `winresource` or `embed-resource`, a new dependency) and an `.ico` made from the icon master.
- **File associations.** The macOS app does not claim `.diacraft`, `.vsdx` or `.odg` (opening a file by double-click arrives as an Apple event, which the window layer does not handle yet), the Windows `.msi` lists DiaCraft in "Open with" and no more, and the Linux entry names no MIME types. Opening a file from the command line (`diacraft FILE`) works everywhere, and the window's File, Open does too.
- **`diacraft.exe` in a terminal.** It is built for the GUI subsystem so that no console window opens behind it, which means it prints nothing in a terminal: `--version` and `--help` are read with `diacraft-cli.exe`. A program cannot attach to its parent's console without `unsafe` code, which the project forbids.
- **Other targets:** FreeBSD, and Linux or Windows on other CPUs (32-bit, RISC-V). None is built.
- **The web build is no download.** It is the second site of the website (`diacraft.app`, with the pages on `diacraft.dev`), made by the `site` job: the pages (`diacraft-site-<name>`) and the app at the root of its own site (`diacraft-app-<name>`) in two artifacts, each of which the `deploy` job downloads and deploys, for a pushed tag that is not a pre-release and when every build has succeeded, to a Pages project of its own (`docs/website.md`, "The web app" and "Deploy to Cloudflare Pages"). Its notices are `THIRD-PARTY-LICENSES-WEB.txt`, made by `cargo xtask licenses` beside the downloads' file (the policy's `OUTPUTS` say which platforms each file covers; `diacraft-web` is the program of the `wasm32-unknown-unknown` target) and checked by `licenses --check`, which the Linux job runs. The app's licences window shows that list, and the app's page links the repository's copy; the file is not in the artifact, since its licence texts hold copyright lines that the site's own name check refuses. The `site` job was first run on Linux with the tools it installs, by hand, and it passed in the third run of the workflow on GitHub, which deploys nothing; the deploy steps of the `deploy` job were tried against a stand-in of the Pages API first, and on the tags of 0.2.0 the job deployed both sites ("What was checked").

## Building by hand

```
cargo build --release --locked -p diacraft -p diacraft-cli                                   # the machine's own target: the programs are in target/release
cargo build --release --locked --target x86_64-pc-windows-msvc -p diacraft -p diacraft-cli   # on Windows: --target applies the flags of .cargo/config.toml
bash packaging/smoke.sh target/release                                                       # runs both programs once
bash packaging/package.sh linux 0.2.3 dist target/release                                    # or windows, or macos (one folder for each architecture; macOS also makes the .dmg)
bash packaging/linux/make-deb.sh 0.2.3 dist target/release                                   # the .deb (on Debian or Ubuntu: dpkg-deb)
APPIMAGETOOL=... APPIMAGE_RUNTIME=... bash packaging/linux/make-appimage.sh 0.2.3 dist target/release   # the AppImage, with the pinned tool and runtime
bash packaging/windows/make-msi.sh 0.2.3 dist target/x86_64-pc-windows-msvc/release          # the .msi (on Windows, in Git Bash, with wix on the PATH)
bash packaging/windows/check-msi.sh dist/diacraft-0.2.3-windows-x64.msi                      # installs it for you, runs it and removes it: not on a machine where DiaCraft is installed
bash packaging/mcp-bundle.sh linux 0.2.3 dist target/release                                # the MCP bundle of the command line (dist/diacraft-mcp-0.2.3-linux-x86_64.mcpb); only diacraft-cli is read
bash packaging/mcp-bundle-check.sh dist/diacraft-mcp-0.2.3-linux-x86_64.mcpb                 # unpacks it and runs the server as the manifest says
cargo xtask mcp-server-json SHA256SUMS.txt --out server.json                                 # the registry's entry, from the sums of a published release
```

`DIACRAFT_BUILD_GIT` and `DIACRAFT_BUILD_YEAR` set the build's own identity for a tree that has no `.git`, such as the public export; without them git describes the commit.
