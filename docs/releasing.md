# Releasing DiaCraft

The first release is 0.2 (`docs/roadmap.md`). A pushed tag `vMAJOR.MINOR.PATCH` runs `.github/workflows/release.yml`, which builds DiaCraft in release for **Linux and Windows, each for Intel/AMD (x86_64) and for ARM64, and for macOS (one universal build)** and uploads twelve downloads, archives and installers, and a `SHA256SUMS` file to a **draft** GitHub release of the tag. The owner reads the notes and the files, then presses Publish. Nothing here has run on GitHub yet: the workflows were written and checked on Linux, Windows and macOS machines of the project's, none of them an ARM one (see "What was checked, and what was not"). The reference app was not inspected, and the downloads have not been opened in it by the project.

**The workflow is DiaCraft's own, and the one exception to the rule that workflows call the shared ones** (`AGENTS.md`, "CI workflows"): the shared `release.yml` needs org signing secrets and runners. It uses no action but GitHub's own `actions/checkout` and `actions/upload-artifact` (both pinned by commit); the GitHub CLI (`gh`) that every runner has uploads the files. Every tool it downloads, besides the Rust toolchain, is pinned by version and by the SHA-256 of the file (the `site` job's trunk, `wasm-bindgen` and binaryen, the Linux job's `appimagetool` and AppImage runtime, the Windows job's WiX), and the workflow checks it before it runs it.

`<tag>` is the tag, `v0.2.0`. The file names follow one pattern, `diacraft-<tag>-<system>-<cpu>.<kind>`, which the site's twelve asset names in `site/site.json` (`assets`, one for each download) are, and `cargo xtask site --release` refuses an empty one; a test holds `site.json`, the checksums job's list, the draft's notes and the home page to the same twelve. **Names that a format has its own convention for** (`diacraft_0.2.0_amd64.deb` for a Debian package, `Name-Version-x86_64.AppImage` for an AppImage) are not used: nothing reads a file name, since apt and dpkg read the fields inside the package and an AppImage's own tools its entry, so one pattern for every file is what a person reads in the release. `packaging/package.sh` makes the archives (and the macOS image); `make-deb.sh`, `make-appimage.sh` and `make-msi.sh` make the installers; the checks they share (a name's characters, the licence files, the CPU read from a program's own header) are in `packaging/common.sh`. The release workflow and the CI workflow run the same scripts, so what a release would make is made, and for Windows and macOS tried, on every push too.

**The tools the installers need, pinned.** Each is downloaded in the workflow and checked against the SHA-256 written there before it is used. To move a version, change the version and the checksums together; a test holds the checksums to 64 lowercase hex digits and the two workflows' WiX to one value.

The AppImage checksums are the ones the projects' releases list (the `digest` of each asset), and the runtime is a dated release, since `type2-runtime`'s `continuous` is rewritten from day to day; `appimagetool` is given the runtime file, and would otherwise fetch the newest one itself. WiX 5.0.2 is the last release under the MS-RL licence: 6 and later come under the Open Source Maintenance Fee EULA, which asks for a fee of some users. Its package's SHA-512 is the one nuget.org lists for it. The workflow installs it as a .NET tool from a folder that holds that one file, with a `nuget.config` that names no other source, so that nothing else is fetched; the tool runs on the .NET SDK of the runner image (its `rollForward` is `Major`, so it runs on the SDK's newer runtime). The Windows job installs WiX for ARM64 on the ARM runner and builds that CPU's installer there; the tool builds an installer of either CPU on any.

**The licence files.** Every download holds these five files, and `packaging/package.sh` stops when one is missing or empty: `LICENSE-MIT` and `LICENSE-APACHE` (the two licences DiaCraft is offered under), `NOTICE` (the credits and the notices of the two fonts and of the mimalloc C library), `ATTRIBUTION.md` (where each picture comes from) and `THIRD-PARTY-LICENSES.txt`. The last is the notice that the licences of the Rust crates ask for: it lists every crate `diacraft` and `diacraft-cli` are built from on Linux, Windows and macOS (Apple silicon and Intel), with its licence and the licence DiaCraft uses it under (MIT where a crate offers a choice), and gives each licence and NOTICE text once, with the crates that carry it. The Linux `install.sh` puts the five under `share/doc/diacraft`. The window carries the same text built in: File, About, Third-party licences (`app.licenses`) shows it in a list that scrolls, so it is there wherever the program is.

`THIRD-PARTY-LICENSES.txt` is made by `cargo xtask licenses` and kept in the repository, so that a download, the window and the site's link (`site/index.html`, to the file on GitHub) all say the same. **When a dependency changes** (`Cargo.lock`, a version, a feature or a new crate), run `cargo xtask licenses` and commit the file: `cargo xtask licenses --check` is a step of `cargo xtask ci`, and the Linux job of the release workflow runs it before it builds, so a tag whose file is stale or whose dependency has no licence text stops there. It fails for a crate with no licence text, for a licence (or a licence file inside a crate) that `deny.toml` does not allow, for a crate that compiles C code that `xtask/src/licenses/policy.rs` does not name, and when the file is not what the lock says. Two things it cannot know: the C and other native code of a crate that has no build dependency on `cc` or `cmake`, and a licence text that a crate's sources do not carry. It needs the sources of every platform's crates; cargo fetches them (with a network) the first time. The number of crates each program is built from on each platform is in the first lines of the file. The programs link no TLS stack and no `ring` or `aws-lc` (the print library's Windows build script does, on the build machine, and that is in no program); the one C library they compile in is mimalloc, whose crate carries its licence text. **Open question for the owner (`docs/gaps.md`):** the Linux build includes `wayland-protocols-plasma`, an MIT crate whose protocol description files come from KDE and say LGPL-2.1-or-later; the file lists the LGPL text and says so, and `AGENTS.md` says no LGPL code is depended on.

**The version.** `--version` of both programs prints the version in `[workspace.package]` of `Cargo.toml`, so the workflow stops at once when the tag and that version differ (`v0.2.0` needs `version = "0.2.0"`). The build's own identity, the build line that the splash, the About panel and `app.version` show under the version, is the tag's version: the workflow sets `DIACRAFT_BUILD_GIT` to the tag and `DIACRAFT_BUILD_YEAR` to the year of the tagged commit (`apps/diacraft/build_info.rs`; the clock is never read), and a build of the tag `v0.2.0` says plain `0.2.0`. Before the tag exists a build says `0.2.0-dev+<commit>` (and `0.2.0+12.<commit>` twelve commits after it), whatever the last tag is called, so a build made for the release does not read as the one before. `packaging/smoke.sh` checks the versions and the line in the built programs and again in the unpacked download. The macOS app's `Info.plist` says the tag's version, and the workspace's for a name that holds none (a rehearsal's `dev-<commit>`; `packaging/package.sh` reads `[workspace.package]`).

## Cut a release (the owner's steps)

1. **Settle the site** (`docs/website.md`). Set `domain` in `site/site.json` to the public one (`repository` is `intergrado/diacraft` already), settle the release notes in `site/changelog.html`, and replace "0.2 is in development" in `site/index.html`. Run `cargo xtask site --write`, then `cargo xtask site --release`, and keep the generated changes in the commit.
2. **Set the version.** Run `cargo xtask version set 0.2.0`: it sets `version` in `[workspace.package]` of `Cargo.toml` to the release and refreshes `Cargo.lock` (the release builds with `--locked`); commit both. It is 0.2.0 already, and every place that says the version reads it from there.
3. **Pass the full gate** on that commit (`cargo xtask ci`, which includes `cargo xtask licenses --check`: run `cargo xtask licenses` first if a dependency changed) and push `main`. The `windows` and `macos` jobs of `ci.yml` build and smoke test both platforms on that push: do not tag a commit they have not passed.
4. **Tag and push the tag:** `git tag -a v0.2.0 -m "DiaCraft 0.2.0"`, then `git push origin v0.2.0`. A tag with a suffix (`v0.2.0-rc1`) makes a pre-release.
5. **Watch the Release workflow** (the Actions tab). `Plan` checks the tag against `Cargo.toml`; `Draft release` makes the draft; `Linux (x86_64)`, `Linux (arm64)`, `Windows (x86_64)`, `Windows (arm64)` and `macOS` build, smoke test, package, smoke test the unpacked archive, make the installers, smoke test each installer (below) and upload the files (the two CPUs of a system run side by side, and one that fails does not stop the other); `SHA256SUMS` checks that exactly the twelve files are there, writes the sums and uploads them. The run's summary lists the sums.
6. **Publish.** Open the draft release, write the notes (the draft holds a short text with the file names), look at the files, and press Publish. The site's download buttons point at the files themselves once the release is the latest (`site/download.js` reads it), and at the release page till then.

**A rehearsal costs nothing.** Run the workflow by hand on a branch (Actions, Release, Run workflow): it builds, smoke tests and packages everything, uploads nothing to a release, and names the files `dev-<commit>`. **Every package of the run is kept as an artifact for 7 days** (one for each job: `diacraft-dev-<commit>-linux-x86_64`, `-linux-arm64`, `-windows-x86_64`, `-windows-arm64` and `-macos-universal`), so that the installers can be downloaded from the run's page and tried on real machines before a tag is pushed; a run on a tag keeps them too. Or push a pre-release tag and delete the draft and the tag afterwards (the tag must match `Cargo.toml`'s version, so a pre-release tag needs `version = "0.2.0-rc1"`).

**How each installer is checked on its runner**, before anything is uploaded:

- **`.deb`**: `dpkg-deb --info` and the package's architecture against `dpkg --print-architecture`; `sudo apt-get install --no-install-recommends`; both programs there, the entry and the icon; `ldd` finds every library; `packaging/smoke.sh` on `/usr/bin` with the licences in `/usr/share/doc/diacraft`; `sudo apt-get remove`; nothing left behind.
- **AppImage**: run with `--appimage-extract-and-run`, since a runner has no FUSE: `--version`, and `--cli --version` for the command line; then `--appimage-extract`, the AppDir looked at, and `packaging/smoke.sh` on its `usr/bin` with the licences.
- **`.msi`** (`packaging/windows/check-msi.sh`): `msiexec /i ... /qn` for the user; both programs and the five licence files in `%LocalAppData%\Programs\DiaCraft`; `packaging/smoke.sh` on them there; the shortcut; the folder on the user's `PATH`; each of `.diacraft`, `.vsdx` and `.odg` listing DiaCraft in `OpenWithProgids` and none with DiaCraft as its default value; `msiexec /x ... /qn`; the folder, the shortcut, the `PATH` entry and every registry entry gone. It stops at once if DiaCraft is installed already, so as not to remove a person's own.
- **`.dmg`**: attached read only with `-nobrowse` and no window, looked at as the unpacked zip is (both architectures in both programs, `Info.plist`, the icon, the licences, the signature, both programs run), the link to Applications, the README; detached.

**A failed run.** `Re-run failed jobs` resumes where it stopped: an upload uses `--clobber`, and `Draft release` finds the draft it made. To start over, delete the draft and the tag and tag again.

## Opening an unsigned download

0.2 is **unsigned**: the programs carry no certificate of a publisher. Each download's `README.txt` says what follows, and the site's download cards say a confirmation may be asked. Checking the file against `SHA256SUMS` is how to know it is the one that was released (`sha256sum --check --ignore-missing SHA256SUMS` on Linux, `shasum -a 256 FILE` on macOS, `Get-FileHash FILE` in PowerShell).

- **Linux.** Nothing to confirm. The `.deb` installs with `sudo apt install ./diacraft-<tag>-linux-<arch>.deb` (and `sudo apt remove diacraft` removes it); the AppImage runs after `chmod +x` (where FUSE is not installed, `--appimage-extract-and-run` runs it with no mount); the archive unpacks and runs `./diacraft`, or `./install.sh` adds it to the application menu for the user (it needs no administrator rights, and `./install.sh --uninstall` removes it).
- **Windows.** SmartScreen may say "Windows protected your PC" for a program or an installer it does not know. Choose "More info", then "Run anyway". Unblocking the `.msi` or the zip first (right-click, Properties, Unblock) avoids the question for everything in it. The `.msi` installs for the user alone, so it needs no administrator rights; Settings, Apps removes it.
- **macOS.** The first opening is refused with a message that Apple cannot check the app. Either open System Settings, Privacy & Security, scroll to the line about DiaCraft and choose "Open Anyway" (macOS 15 and later; on macOS 14 and earlier, Control-click the app, choose Open, then Open); or remove the quarantine mark in Terminal: `xattr -dr com.apple.quarantine /Applications/DiaCraft.app`. The same goes for `diacraft-cli`. Both programs carry an ad hoc signature, which an Apple silicon Mac needs to run a program at all; it says nothing about who made them. The disk image is not signed or notarised either, and opens normally.

## Signing

The hooks are in place and switched off. Each is a commented block in `release.yml` that names the secrets it reads.

- **macOS** (Developer ID, Apple Developer Program). Secrets: `MACOS_CERTIFICATE` (the "Developer ID Application" certificate and key as a `.p12`, in base64), `MACOS_CERTIFICATE_PASSWORD`, `MACOS_SIGN_IDENTITY` (`Developer ID Application: Name (TEAMID)`), `APPLE_ID`, `APPLE_TEAM_ID` and `APPLE_APP_PASSWORD` (an app-specific password). Uncomment the step "Import the signing certificate" and the step "Notarise the disk image" of the `macos` job, and add `MACOS_SIGN_IDENTITY` to the environment of "Make the download": `packaging/package.sh` then signs the CLI, the app's program and the app with the hardened runtime and a timestamp, where without it they are signed ad hoc, and signs the disk image too. The notarising step submits the `.dmg` and staples the ticket to it, so that a person who opens it with no network gets no question; a zip has no place for a ticket, so the app in the zip is checked online.
- **Windows** (Authenticode). Secrets: `WINDOWS_CERTIFICATE` (a `.pfx`, in base64) and `WINDOWS_CERTIFICATE_PASSWORD`. Uncomment the step "Sign the programs" of the `windows` job, which runs `signtool` on both programs before they are smoke tested and packaged, and the step "Sign the installer" after "Make the .msi", which signs the `.msi` before it is installed and smoke tested (a signed installer is what Windows shows a publisher's name for). The x64 `signtool` runs on the ARM runner too, under emulation, and signs programs of either CPU. SmartScreen's reputation comes at once with an EV certificate or a cloud signing service, and over time with an ordinary one.
- **Linux.** Nothing is needed. A detached GPG signature of `SHA256SUMS` can be added to the `SHA256SUMS` job; an AppImage can carry a signature of its own (`appimagetool --sign`), which no tool needs to check.

## Not done, and what it would take

- **A wizard for the `.msi`** (a licence page, a folder to choose): the WiX UI extension, one more package to pin. The installer is per user, into a fixed folder, and shows Windows' progress bar.
- **Update channels.** No apt repository, no AppImage update information (`zsync`), no `winget` or Homebrew entry: each is a download of a person's own choosing, from the release page.
- **Manual pages** for `diacraft` and `diacraft-cli` in the `.deb` (lintian warns of it), and MIME types in the launcher entry, so that a Linux file manager offers DiaCraft for `.diacraft`, `.vsdx` and `.odg` (the entry names none: a type name of the reference format holds its product's name, which the site and the sources leave out outside the lists the owner allowed).
- **An icon on `diacraft.exe`.** The window's icon is set at run time, so the taskbar and the title bar show it, but the file in Explorer has the default icon. Embedding one needs a resource compiler in the build (a `build.rs` with `winresource` or `embed-resource`, a new dependency) and an `.ico` made from the icon master.
- **File associations.** The macOS app does not claim `.diacraft`, `.vsdx` or `.odg` (opening a file by double-click arrives as an Apple event, which the window layer does not handle yet), the Windows `.msi` lists DiaCraft in "Open with" and no more, and the Linux entry names no MIME types. Opening a file from the command line (`diacraft FILE`) works everywhere, and the window's File, Open does too.
- **`diacraft.exe` in a terminal.** It is built for the GUI subsystem so that no console window opens behind it, which means it prints nothing in a terminal: `--version` and `--help` are read with `diacraft-cli.exe`. A program cannot attach to its parent's console without `unsafe` code, which the project forbids.
- **Other targets:** FreeBSD, and Linux or Windows on other CPUs (32-bit, RISC-V). None is built.
- **The web build is no download.** It is the second site of the website (`diacraft.app`, with the pages on `diacraft.dev`), made by the `site` job: the pages (`diacraft-site-<name>`) and the app at the root of its own site (`diacraft-app-<name>`) in two artifacts, each of which the owner deploys to a Pages project of its own (`docs/website.md`, "The web app" and "Deploy to Cloudflare Pages"). Its notices are `THIRD-PARTY-LICENSES-WEB.txt`, made by `cargo xtask licenses` beside the downloads' file (the policy's `OUTPUTS` say which platforms each file covers; `diacraft-web` is the program of the `wasm32-unknown-unknown` target) and checked by `licenses --check`, which the Linux job runs. The app's licences window shows that list, and the app's page links the repository's copy; the file is not in the artifact, since its licence texts hold copyright lines that the site's own name check refuses. The `site` job has not run on GitHub: it was run on Linux with the tools it installs, by hand.

## What was checked, and what was not

On Linux (2026-11-22): both programs build in release; `packaging/smoke.sh` passes on them (the versions, the tag in `app.version`, a drawing saved as `.vsdx`, converted to `.diacraft` and back with the same content, drawn as PNG, SVG and PDF, and the MCP server answering); `packaging/package.sh` makes the Linux archive, and its `install.sh` installs and removes cleanly; the Windows and macOS archives were staged with the platform tools stood in for. For `x86_64-pc-windows-msvc` and `x86_64-apple-darwin`, `cargo check` passes for both programs from Linux **with the C allocator replaced by a stand-in**: mimalloc's C build needs the target's SDK, which the Linux machine does not have. So the C build of mimalloc, the link, the signing, the icon tools and everything that runs on those two systems are first tried by the CI jobs. **On the first run of the `windows` and `macos` jobs and of the release workflow, look at:**

- **The link on Windows** with `crt-static` and the 8 MiB stack (`.cargo/config.toml`), and mimalloc's C build there (it is compiled as C++ for MSVC).
- **`diacraft.exe --version`** in `smoke.sh`: a program for the GUI subsystem may print nothing in a terminal, and the script then warns and checks only the exit status.

## Building by hand

```
cargo build --release --locked -p diacraft -p diacraft-cli                                   # the machine's own target: the programs are in target/release
cargo build --release --locked --target x86_64-pc-windows-msvc -p diacraft -p diacraft-cli   # on Windows: --target applies the flags of .cargo/config.toml
bash packaging/smoke.sh target/release                                                       # runs both programs once
bash packaging/package.sh linux v0.2.0 dist target/release                                   # or windows, or macos (one folder for each architecture; macOS also makes the .dmg)
bash packaging/linux/make-deb.sh v0.2.0 dist target/release                                  # the .deb (on Debian or Ubuntu: dpkg-deb)
APPIMAGETOOL=... APPIMAGE_RUNTIME=... bash packaging/linux/make-appimage.sh v0.2.0 dist target/release   # the AppImage, with the pinned tool and runtime
bash packaging/windows/make-msi.sh v0.2.0 dist target/x86_64-pc-windows-msvc/release         # the .msi (on Windows, in Git Bash, with wix on the PATH)
bash packaging/windows/check-msi.sh dist/diacraft-v0.2.0-windows-x86_64.msi                  # installs it for you, runs it and removes it: not on a machine where DiaCraft is installed
```

`DIACRAFT_BUILD_GIT` and `DIACRAFT_BUILD_YEAR` set the build's own identity for a tree that has no `.git`, such as the public export; without them git describes the commit.
