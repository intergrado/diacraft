# Development

Read [`AGENTS.md`](../AGENTS.md) first: it binds every contributor.

## Tools

Rust 1.95 or newer (declared; 1.99.1 and 1.100.0 have been run), `rustup target add wasm32-unknown-unknown`, `cargo install cargo-nextest --locked --version 0.9.150`, `cargo install cargo-deny --locked`. To build the web app for the site (`cargo xtask site --web`, optional): `cargo install --locked trunk@0.22.2` and `cargo install --locked wasm-opt@0.133.0` (binaryen version 133, which `apps/diacraft-web/Trunk.toml` names); trunk reads the `wasm-bindgen` version from `Cargo.lock` and downloads that program when none of that version is on the `PATH`. For the proofs, optional: `cargo install --locked kani-verifier --version 0.68.0` then `cargo kani setup` (see Proofs). The desktop app and the CLI also need a C compiler, since the mimalloc allocator is built from its C source by the `cc` crate (`cc` or `clang` on Linux, the Xcode command line tools on macOS, the MSVC build tools on Windows); the web build needs none. Linux builds also need the usual window-system development packages; `.github/workflows/ci.yml` lists them.

## Commands

- `cargo xtask ci` runs every gate, in this order: fmt, clippy, fuzz check, kani check, test, doctest, assets, brands, docs, help check, site, deny, licenses --check, parity --check, layers, wasm (it stops at the first failure and prints a `CI summary:` block). It is part of the full gate, which runs after every three features; before a task asks to merge, it runs only the targeted checks (`AGENTS.md`, "Quality gates and commits"). `cargo xtask help` lists every command, the ones above and `test`, `layers`, `assets`, `brands`, `docs`, `site`, `deny`, `licenses`, `parity`, `wasm`, `stats`, `version` and `export-public`.
- `cargo xtask fuzz-check` runs the `fuzz check` step alone (see below).
- `cargo xtask help check` holds the help tree, `help/`, to the rules of its format: the topics are read by `diacraft_help::parse`, the very code the program reads them with, and on top of what a topic says about itself the check holds the tree together (ids are unique, named by their file, and none that was published is lost; every `topic:` link and `#anchor` resolves; every `ctl:` names a ribbon control and every `cmd:` a registered command, read from the source by text, `Known::scan` in `xtask/src/help/check.rs`; every topic is in a section of `sections.tsv` or `unlisted`; the tips table and the help map name only controls, commands, places and topics that exist; the prefixes the program lets a link open are the ones in `site/site.json`; and `cargo xtask brands`' rules about names, with `description` and `seo_title` of a header free). It is a step of `ci`, after `docs`. `cargo xtask help --write` runs the same check and writes what is generated from the tree, which is nothing yet (the site's pages and What's New come with their tasks). `help/README.md` is the guide to writing a topic; the check prints each problem as `file:line: what`.
- `cargo xtask deny` runs `cargo deny check licenses bans sources` (no network), then `cargo deny check advisories`, which needs the RustSec database. **How the advisories run decides:** a RustSec vulnerability, or an unmaintained, unsound or yanked crate that `deny.toml` does not ignore, fails the step (cargo-deny prints `error[vulnerability]` or the like, and the step does not run the check again). A new unmaintained crate is therefore a failure until someone reads it and adds an `ignore` entry to `deny.toml` with the day and what blocks the fix; the five that stand today (the three zbus crates through egui's accessibility, `proc-macro-error` through the print fork, and `chrono`, which DiaCraft's own code no longer uses and which stays in the lock as a Windows build dependency of the print fork's `winprint`) are there, each with its reason. **When the fetch fails** (no network, `failed to fetch advisory database`), the step runs the check again with `--offline` against the copy of the database already on the machine, prints that the copy is not up to date, and passes if that copy shows nothing; if the machine has no usable copy, the step fails in words and names `cargo deny fetch`, which fetches it once. The check never passes without having looked at a database, and the licence check stays free of the network. CI has a network, so it always fetches. The step's tests (`xtask/tests/it/deny.rs`) stand in for cargo-deny with its recorded words, and a vulnerable crate was run through the real step once to see it fail (`smallvec` 1.6.0, RUSTSEC-2021-0003: `error[vulnerability]`, exit 1).
- `cargo xtask site [--write|--release|--web [--dist DIR] [--out DIR] [--app-out DIR] [--app-url URL]]` checks the static website in `site/` (links, images, metadata, hosts, names, page weight and the content security policy; it is a step of `ci`). `--write` refreshes the generated links, metadata, the `twitter:*` tags and structured data of each page, the tables of the feature comparison page (made from `docs/parity-matrix.toml` and the checklist's scores: a page that is not what they give fails the check), `sitemap.xml` (with a `<lastmod>` for each page from the last commit that touched it, left out where the history is shallow) and `robots.txt` (the pages' links to the app and the address in the browser picture take `app_url` of `site/site.json`), `--release` also checks the release settings of `site/site.json`, and **`--web`** also makes the two sites that the website is: the pages copied into `dist/site` (or `--out DIR`; with their links to the app at `app_url`, or at `--app-url` / `DIACRAFT_APP_URL` for a preview on this machine) and checked, then `trunk build --release --locked` in `apps/diacraft-web` (or the finished build in `--dist DIR`) made into `dist/app` (or `--app-out DIR`), the app at the root of a site of its own with its own `_headers`, and the app's files, links, search and social data (its title, description, canonical address, `og:*` and `twitter:*` tags, `robots.txt`, `sitemap.xml`), sizes (each file under the 25 MiB Cloudflare Pages allows, a part of the module under 8 MiB, the module under a budget of 21 MiB in all, and any other file under 4 MiB), headers and module checked (`docs/website.md`, "The web app"). `--web` needs trunk, `wasm-bindgen` and `wasm-opt` and is not a step of `ci`. Both forms also read `_headers` as Cloudflare Pages applies it (a splat, placeholders, joined headers, `! Name`) and check, for every file of the folder, that a file is kept for a year if and only if its name is the SHA-256 of its own bytes, that no file gets two cache headers, and that every page has its content security policy (`xtask/src/site/cache.rs`; `docs/website.md`, "The web app", "Caching").
- `cargo xtask version [set X.Y.Z[-pre]]` prints the workspace version or sets it. The version lives in `[workspace.package]` of the root `Cargo.toml`, every crate inherits it (`version.workspace = true`), and `set` also refreshes the workspace members' entries in `Cargo.lock`. The programs' `--version`, `app.version`, the splash, the About panel, the `written-by` of a `.diacraft` file, the generator of an `.odg` and the macOS `Info.plist` all read it from there, and `packaging/package.sh` takes it from the tag, which the release workflow checks against it; the build line under it follows it (below).
- `cargo xtask deploy-check <BASE_URL> [<BASE_URL>]` asks each deployed site (the pages, then the app) what it sends: for each it fetches the start page, the pages linked from it and every file they load, with `Accept-Encoding: br, gzip` through `curl`, and prints for each the status, `Cache-Control`, `Content-Encoding`, `ETag` and whether a second request with `If-None-Match` got `304`. It fails on a status that is not 200 and on a wrong `Cache-Control`, and warns when a `.wasm` part or another text file comes back uncompressed. Each `BASE_URL` is `https://host`, or `http://host:port` for a server of one's own, and the run fails if either site fails. It is not a step of `ci` or of the release workflow: it needs a deployed site, and is run by hand after the first deploy (`docs/website.md`, "Deploy to Cloudflare Pages", step 7).
- `cargo xtask web-dpr [DIR]` runs the built web app (`dist/app` from `cargo xtask site --web`, or DIR) in a headless Chrome or Chromium (the program on the `PATH`, or `CHROME`; `CHROME_ARGS` adds arguments) at device scale factors of 1, 1.5, 2 and 3, a 390 by 844 phone page at 3 and a running app that is resized. It serves the folder on a loopback port, drives the browser over the DevTools protocol (`Emulation.setDeviceMetricsOverride`) with a small WebSocket client of its own, and fails when the canvas does not have its CSS size times the ratio in pixels, which is a window laid out for part of the page. It needs the browser, so it is a step of neither `ci` nor the release workflow: run it after a change to the web shell. `docs/website.md`, "The canvas and the device pixel ratio".
- `cargo xtask mcp-server-json SHA256SUMS.txt [--out FILE]` makes the MCP Registry's entry (`server.json`) for a published release from its checksums file: one `mcpb` package for each of the six bundles of `BUNDLES` in `xtask/src/mcp.rs`, with the address of its file and its SHA-256. It refuses sums that miss a bundle, name one twice, name one that `BUNDLES` does not list, or are of another version than the checkout's. It is a step of neither `ci` nor the release workflow; the owner or the coordinator runs it by hand after a release is published ([`releasing.md`](releasing.md), "Publish the MCP server to the registry").
- `cargo xtask licenses [--check]` writes `THIRD-PARTY-LICENSES.txt` at the root of the repository and, `THIRD-PARTY-LICENSES-WEB.txt` for the web build (`diacraft-web` on `wasm32-unknown-unknown`, listed in `xtask/src/licenses/policy.rs` as one more target with its own program and its own output file, which the web app's window shows and `docs/website.md` describes; the lists of `policy.rs` are checked against the downloads' file alone, and `--check` looks at both files): every crate that `diacraft` and `diacraft-cli` are built from on Linux, Windows and macOS (Apple silicon and Intel), each with its licence, the licence DiaCraft uses it under (MIT where it is offered, then Apache-2.0, never one that `deny.toml` does not allow) and each licence and NOTICE text once, the standard text of the licence where a crate ships none. **The crates come from `cargo tree -p diacraft -p diacraft-cli --target T -e normal,no-proc-macro`**, and not from `cargo metadata`'s graph, which is the whole workspace's (features are unified across its members) and names about forty crates the two builds do not compile (the OpenGL backend, the PDF reader, the clipboard); `cargo metadata --filter-platform T` gives each crate's licence, authors, folder and whether it has a build dependency on `cc`. The texts are read from the sources cargo has fetched (the crate's own files, a `licenses` folder, the folders above a crate in a git checkout, and licence files nested in the crate: vendored C code, font data, ICC profiles). `--check` fails for a crate with no licence text, a licence or a nested licence file outside `deny.toml`'s list, a crate that compiles C code that `xtask/src/licenses/policy.rs` does not name (`libmimalloc-sys` and `wayland-backend` are), a stale entry in `policy.rs`, and a file that is not what the lock says now. It is a step of `ci`, after `deny`, and of the Linux job of the release workflow. **After a change to `Cargo.lock` run `cargo xtask licenses` and commit the file.** The sources of the Windows and macOS crates are fetched by cargo the first time (`cargo fetch --target <triple>`; a machine with no network and none of them fetched fails, saying so). A copy made on another machine is byte for byte the same: the text holds no path and no date.
- `cargo xtask langdata --cldr DIR --icu DIR [--i18n-source FILE] [--check]` writes the four generated tables of `diacraft_doc::lang` in `crates/doc/src/lang` (`lcid.rs`, `names.rs`, `quotes.rs`, `scripts.rs`) from two public sources, both data under the Unicode License V3: ICU4C's `source/common/locmap.cpp` at `release-79.1` (the pairs of LCID numbers and language tags, never copied from a table of the reference app's file format: design call) and Unicode CLDR 49.0.0's JSON (English names, quotation marks and likely scripts of languages). It is **no step of `ci` and fetches nothing**: it reads folders you made, after checking each (the CLDR version and licence in `cldr-core/package.json`, ICU's `LICENSE`, and `locmap.cpp` by its SHA-256). CLDR 49.0.0 is the release craft-i18n's data was generated from (`crates/i18n/data/source.txt` of the craft-libs revision DiaCraft pins; `--i18n-source` refuses another), so that the tables cannot disagree with it. `--check` writes nothing and fails naming each committed table that is not what the sources give. How to regenerate is under "The language tables" below.
- `cargo xtask kani [-j N]` proves the Kani harnesses (see Proofs). Not part of `ci`: it takes about eighteen minutes (1,052 s for the 262 harnesses of 16 crates, `-j 4` on a shared machine: see Proofs; 264 two), and needs Kani 0.68.0. The full gate runs it.
- `cargo run --release -p diacraft -- --control 7997` runs the app with its control channel. See [`control-protocol.md`](control-protocol.md).
- `cargo run -p diacraft-cli -- mcp` runs the MCP server. See [`mcp.md`](mcp.md) and [`cli.md`](cli.md).

Never build under `/tmp`. A target folder reaches about 30 GB.

## CI

`.github/workflows/ci.yml` runs the gate on every push to `main`, every pull request and by hand (`workflow_dispatch`); a newer push to a pull request's branch cancels its older run, and a push to `main` always runs to the end. **While the repository is private, the workflow runs the gate itself and uses no StepSecurity action** (owner, 2026-11-21). The shared `storytold/craft-common-actions` gate workflow it stood in for runs a StepSecurity hardening action in every job and installs the cargo tools through a StepSecurity action that refuses a private repository, so every run from 2026-11-12 on failed in the `Install cargo tools` step, with none of our code involved. The old `jobs:` block, the call to that workflow, is quoted in a comment at the top of the file; when DiaCraft goes public, the `gate` job is deleted and the call comes back (`AGENTS.md`, "CI workflows").

- **The job.** One Linux job on `ubuntu-24.04`, 90 minutes at most, with `permissions: contents: read`. Its steps, in order: check out (the whole history); free the image's unused toolchains in the background; install the apt packages (`pkg-config`, the window-system, font and Vulkan development packages: the `PACKAGES` list of the step, the same as before); install Rust 1.100.0 (the `RUST_VERSION` of the job's `env`; the channel of a `rust-toolchain.toml` wins if the repository gets one) with clippy, rustfmt and the `wasm32-unknown-unknown` target; install the two cargo tools; restore the dependency cache; `cargo xtask ci`; and a check that the gate left `Cargo.lock` as it was. It builds without craft-fonts. The environment is the shared gate's: `CARGO_TERM_COLOR=always`, `CARGO_INCREMENTAL=0`, `CARGO_NET_RETRY=10`, `RUST_BACKTRACE=1` and `CARGO_PROFILE_DEV_DEBUG=line-tables-only`. Bump `RUST_VERSION` with the release the developers run.
- **The cargo tools.** cargo-nextest 0.9.150 (the `x86_64-unknown-linux-gnu` archive of its release) and cargo-deny 0.20.2 (the `x86_64-unknown-linux-musl` archive of its release) are downloaded over HTTPS, checked against the SHA-256 written in the step (the value each release also publishes), unpacked into a folder on `PATH`, and run once to check the version they report. A checksum that does not match, or a different version, fails the step. To move a tool, change its version and its checksum together. No third-party install action is used.
- **Pins and the cache.** Every `uses:` names an action by its full commit SHA with the version in a comment (`actions/checkout` v7.0.1, `Swatinem/rust-cache` v2.9.3). The cache restores in every run and is saved only by a push to `main` or a manual run of it, and never by a failed job.
- **The Windows and macOS jobs**. Beside `gate`, `ci.yml` has a `windows` job on `windows-latest` and a `macos` job on `macos-latest`, 75 minutes at most each, with no cache and no action but `actions/checkout`. Each installs the same Rust (`RUST_VERSION`), builds `diacraft` and `diacraft-cli` in release with `--locked` (Windows with `--target x86_64-pc-windows-msvc`, so that the flags of `.cargo/config.toml`, a static C runtime and an 8 MiB main stack, reach the programs and not the build scripts; macOS for the machine's own architecture, with `MACOSX_DEPLOYMENT_TARGET=11.0`), runs `packaging/smoke.sh` on them (both versions; a drawing saved as `.vsdx`, converted to `.diacraft` and back with the same content, and drawn as PNG, SVG and PDF; the MCP server answering; no window) and makes the download package with `packaging/package.sh`. The Windows job also installs WiX (version and SHA-256 written in the job, the release workflow's) and makes the `.msi`, installs it for the user, runs the installed programs and removes it (`packaging/windows/check-msi.sh`), and the macOS job attaches the `.dmg` that `package.sh` made beside the zip, checks it and detaches it. They run no tests: the gate does, on Linux. The ARM64 builds are left to the release workflow, which a run by hand rehearses: they are the same code on a second CPU, and two more cold release builds on every push would be a high price for the link and the runner. Keep `RUST_VERSION` the same in all three workflows.
- **The release workflow.** `.github/workflows/release.yml` runs on a pushed `v*` tag and by hand: it builds Linux and Windows for x86_64 and for ARM64 (each on a runner of its own CPU) and macOS (Apple silicon and Intel, each on its own: no universal build), smoke tests the programs and each download, makes the installers (`.deb`, `.rpm`, AppImage, `.msi`, `.dmg`), installs or mounts and runs each, and uploads sixteen files, named `diacraft-<version>-<system>-<cpu>[-portable].<extension>` as an app launcher reads them (the version is the tag without its `v`), and six MCP bundles (`diacraft-mcp-<version>-<system>-<cpu>.mcpb`), with `SHA256SUMS.txt` over the twenty-two, to a draft GitHub release; a run by hand uploads nothing to a release and keeps every package as an artifact for 7 days. It is DiaCraft's own, the exception that `AGENTS.md` names (the shared one needs org secrets and runners). The scripts are in `packaging/` (`package.sh`, `smoke.sh`, `mcp-bundle.sh`, `mcp-bundle-check.sh`, `common.sh`, and `make-deb.sh`, `make-rpm.sh`, `check-rpm.sh`, `rpm-in-fedora.sh`, `make-appimage.sh`, `make-msi.sh`, `check-msi.sh` in the folders of their systems) and are tested in `xtask/tests/it/packaging*.rs`, with stand-ins for `appimagetool` and WiX (the `.deb` tests need `dpkg-deb` and are skipped without it, and use a copy of `true` as the program of the machine's own CPU, which the machine's `strip` can read; the `.rpm` tests need a Fedora's `rpmbuild` and `rpm` with the package `desktop-file-utils` installed (the spec's build requirement), are skipped without them, and build the package of that same program; `packaging/linux/check-rpm.sh` and `rpm-in-fedora.sh` run in a Fedora container and are not run by the tests). How to cut a release, the signing hooks and what to watch on the first run: [Releasing](releasing.md).
- **CodeQL**. `.github/workflows/codeql.yml` runs GitHub's CodeQL code scanning as an **advanced setup** (owner, 2026-11-26) on every push to `main`, every pull request to it, every Monday and by hand: one job each for `rust`, `actions` (the workflows) and `javascript-typescript` (the scripts of the site and of the web app), none of them with a build (`build-mode: none`; for Rust the runner needs `rustup` and `cargo`, which its image has). Its token uploads results and reads the repository and nothing more, and its actions are pinned by commit like the others (`github/codeql-action` v4.39.5). **What is skipped, and why.** The default setup scanned every file and flagged 34 alerts, all in test and fuzz code (25 cleartext logging, 7 hard-coded cryptographic values, 2 unsafe deserialization); each was reviewed and dismissed as "used in tests" on 2026-11-26. `.github/codeql/codeql-config.yml` now skips every `tests` and `fuzz` folder, the test modules inside `src` that are named `tests.rs` or `*_tests.rs` or are a `tests` folder (each is declared under `#[cfg(test)]`), `crates/testkit` and `proptest-regressions`; `crates/*/src`, `apps/*/src`, `xtask/src`, the scripts and the workflows stay scanned. A path cannot skip a `#[cfg(test)] mod tests { }` block inside a shipped file, or a test module with another name: an alert there is read, and dismissed as "used in tests" when it is. `xtask/tests/it/codeql.rs` holds the rules. The default setup (repository settings, Code security) must stay off: while it is on, GitHub refuses the results of an advanced setup.
- **Reviews of pull requests.** CodeRabbit reviews pull requests to the public repository, as `.coderabbit.yaml` at the root sets it up. A pull request is reviewed when it is not a draft and its base is `main`; a public repository with fewer than 10 stars gets no automatic review, so a maintainer starts it by commenting `@coderabbitai review`. **The review is advice only and never blocks a merge:** the file asks for no request for changes and no automatic approval, a review that fails ends its check as neutral, and the checks of a title, a description and a linked issue are off. Do not make the CodeRabbit check a required status in the branch protection of `main`. The path filters all start with `!`, so they can only take files out of a review: the lists written by `cargo xtask licenses` and `cargo xtask site --write`, the site's and the branding pictures, the licence texts and the test data; CodeRabbit already skips lock files, fonts and generated code. The reviewer reads `AGENTS.md` and this page for the project's rules, and has instructions for the Rust sources, the `Cargo.toml` files and the workflows. `xtask/tests/it/coderabbit.rs` holds the file to this (no filter without `!`, each filter naming something in the tree, no setting that blocks). CodeRabbit's command line has no check for a configuration file: to check a change to the file, validate it against the JSON schema at `https://coderabbit.ai/integrations/schema.v2.json`. Each finding is checked, and a real one is fixed in the source tree and published again, not on the public branch (`AGENTS.md`, "CI workflows").
- **Not part of this.** A feature or a fix does not change CI (`AGENTS.md`). The Kani steps are not in the workflow (see Proofs).

## Fuzz targets in the gate

The fuzz crates (`crates/calc/fuzz`, `crates/container/fuzz`, `crates/doc/fuzz`, `crates/help/fuzz`, `crates/mxfile/fuzz`, `crates/native/fuzz`, `crates/odg/fuzz`, `crates/prefs/fuzz`, `crates/route/fuzz`, `crates/sheetxml/fuzz`, `crates/vsdx/fuzz`) are workspaces of their own: cargo-fuzz wants nightly and sanitizer flags, and a real fuzz run is built by hand (`cargo-fuzz` itself is not installed here). No other step compiles them, so a target that did not compile went unnoticed (a raw string closed early by `"#`). The `fuzz check` step of `cargo xtask ci`, also `cargo xtask fuzz-check`, type-checks every one of them:

- **What it checks.** Every `Cargo.toml` in a folder named `fuzz`, or marked `cargo-fuzz = true`, or with a dependency on `libfuzzer-sys` (so a fuzz crate in a folder of any name is found), that is not a member of the workspace: `cargo check --all-targets --all-features --keep-going` on the stable toolchain, with `--cfg fuzzing` as a libFuzzer build has it (so a bin behind `required-features` and code under `#[cfg(fuzzing)]` are checked too; the flags are those of this one command, added to what `RUSTFLAGS` already holds), on the crate's own manifest, one crate after another, into `<target dir>/fuzz-check` (inside the target directory the gate's cache keeps); the step passes `--cfg fuzzing` through `CARGO_ENCODED_RUSTFLAGS`, which cargo reads in place of `CARGO_BUILD_RUSTFLAGS` and of any `[build]` or `[target.*]` `rustflags` of a cargo configuration file, so for that one command those flags are not used (`RUSTFLAGS`, when set, is carried into it). A failure names the crate and each target that does not compile (``crates/odg/fuzz: does not compile: `diacraft-odg-fuzz` (bin "canon_compare")``) and the compiler's errors are above it. It also fails for a `.rs` file directly in `fuzz_targets/` that is not a `[[bin]]` of the manifest (nothing would build it), for a fuzz crate that lists no target, and for **any other `Cargo.toml` that is not the root's, not a workspace member and not part of a fuzz crate's own workspace**: a crate that no step builds, named in the error, to be made a member or a fuzz crate. The repository has no `vendor/` folder and documents no use of `cargo vendor`, so the rule exempts none; if `cargo vendor` is ever used, the rule needs a `vendor/` exemption, since every vendored crate's manifest would otherwise be named as a crate that no step builds.
- **The earlier namespace in the targets (APPID).** The VSDX targets' fragments (`SNIPPETS`) include DiaCraft's namespace as builds before the id moved to `diacraft.app` wrote it, and the type of the relationship it made, so that a recipe can put either in a part; `odg_read` and `odg_tier2` read one input in two with every part's DiaCraft namespace spelled that way (`spelled_as_before`, chosen by the parity of the input's bytes), under the laws they hold of the other spelling.
- **What it does not check.** That a target runs, finds anything or links with the sanitizer; a target that needs a nightly feature fails here, on stable. Warnings are not errors.
- **The twenty-five targets.** `crates/calc/fuzz`: `cell_reference` (any bytes read as text, by lossy UTF-8; `cell_address` gives a cell or a refusal in words, and a cell it gives has a `reference_name` that is at most `MAX_REFERENCE_BYTES` and reads back as the same cell; then, behind a first byte that picks the sheet and the cell, `evaluate_text` tries the rest as a formula with a budget of 20,000 steps and never passes it, gives a parse error whose offset is inside the text, and writes nothing; and, the same text goes to `reference_spans`, which gives the parser's own error or spans inside the text, on character boundaries, in the order the references begin, each covering text that read alone is the reference it holds, and to `Locator::locate`, which finds the cell each of the first references names on the target's document within the same budget and writes nothing) and `row_refs` (a first byte picks the shape asked for and whether a reference with no qualifier is its, and the rest is read as text by lossy UTF-8; `find` never panics and is charged exactly the bytes of the text, its references are in order, apart and on character boundaries; a map that names every row as it is, or none, changes no byte; the map that raises each row's number by one leaves the same number of references, the shape's one higher and every other as it was, byte for byte; a budget too small for the text is the refusal in words and gives no text). `crates/container/fuzz`: `canon_compare`. `crates/doc/fuzz`: `lang_tag` (any bytes read as text, by lossy UTF-8; `parse` gives a language tag or a refusal in words, refuses a text past `MAX_TAG_BYTES` as too long and nothing else as that, and a tag it gives is as long as the text, at most `MAX_TAG_BYTES`, the same letters in another case and its own canonical form, with a script and a region that are subtags of it, and the text in capitals is read or refused as the text is; behind a first byte, `effective` reads the text as a `LangID` value in a drawing in Turkish, English or Chinese and gives a language that is no word for none, the document's own for a text that is no tag or a number but 0, and none for the words for none and for 0, and `document_language` reads it as `DocLangID` and as the core language and gives a tag that is well formed and no word for none, `en-US` or the preferred language when neither is usable; - **How a target is run by hand (the recipe).** Make the crate's `Cargo.lock` as the check does (the workspace's, then `cargo update --workspace --offline`), then in the crate's folder `RUSTFLAGS="--cfg fuzzing -Cpasses=sancov-module -Cllvm-args=-sanitizer-coverage-level=4 -Cllvm-args=-sanitizer-coverage-inline-8bit-counters -Cllvm-args=-sanitizer-coverage-pc-table -Cllvm-args=-sanitizer-coverage-trace-compares -Cdebug-assertions -Cno-vectorize-loops -Cno-vectorize-slp" cargo +nightly build --release --offline --target x86_64-unknown-linux-gnu --bin <target>`, with a `CARGO_TARGET_DIR` of its own (not the workspace's), and run the binary it makes as `<target dir>/x86_64-unknown-linux-gnu/release/<target> <corpus dir> -max_total_time=600 -timeout=10 -rss_limit_mb=2048 -artifact_prefix=<artifact dir>/`: **the fuzz corpus and the artifact folders are outside the worktree** (the check fails on an untracked folder with a `Cargo.toml` in it, and an artifact is a crash input that is never committed). A crash or a hang the fuzzer finds is a bug: minimise the artifact, rebuild the input in code in a regression test, fix the cause. libFuzzer's own limit on the length of an input starts at 4 bytes and grows by a byte for each new unit (`lim:` in its lines), so a target whose input is a recipe of a few dozen bytes explores well from the start, and one that needs more starts at once with `-max_len=4096 -len_control=0`.
- **The VSDX targets (`crates/vsdx/fuzz`).** The VSDX reader, the format of most files, had none: the crate had only proptest properties (`crates/vsdx/tests/it/fuzz.rs`). The three targets share the crate's library (`src/`): the seeds (`seeds.rs`: the packages the tests of `crates/vsdx` build, made again in code: a plain one with a little of everything the reader reads, and one whose solution part carries the data of the other format in every place it rides, written by the model writer, so that its items, stamps and parts of DiaCraft's own are the writer's and the judge goes past the stamp; `package.rs` is the package builder of `crates/testkit` included by its path, since the testkit itself brings the engine), the recipes that turn a target's bytes into a package (`inputs.rs`, `plan.rs`), and the properties (`checks.rs`). **No corpus file is used and none is committed:** every seed is built in code, and a target replaces or splices into one part of a seed and packs the archive again with right checksums, since a change of the archive's own bytes is stopped by its checksums nearly always (the container's fuzz covers that).

A read is a document or a refusal in words, and never panics, aborts or passes the fuzzer's timeout; a document passes the model's caps, its held parts are the package's bytes exactly, the parts of the other format that the carrier brought are sound (below), and a second read gives the same document; a read in a pool of any size is a read or a refusal for memory in words and holds every tree it made in the pool.

The properties: a refusal and a warning are in words and name no entry of the other format; **nothing outside `/diacraft/` is taken as a blob** (the bytes of each part of the other format and of each definition are the bytes of a part under `/diacraft/`, and none is one planted outside); **no macro part reaches a type that allows none**, by the role or by the name in any case; every name is one an `.odg` entry may have, once by case, and none that a package makes itself; **the judge's work stays under its budget** (an item judged once, a record looked at once, and, when the read did not say it left items out for the work, twice the steps of stamping plus the nodes copied are at most `max_carry_steps`: the counts are those of `diacraft_vsdx::work`).
  - **`vsdx_roundtrip`**: read, splice-save unedited, read again. The input is the recipe of `vsdx_read`, or, for a first byte that is 3 modulo 8, a plan of `vsdx_carry`, or, for one that is 5 modulo 8, a model that a program made (see the last property). The unedited save into the file (`write_with` with the original bytes and the model as baseline) reads again, **the second read equals the first** (but for `Application` of the extended properties, which every save sets to `DiaCraft`, edited or not, and for the content type of a part that had none, which every save gives one, R22: so `docProps/app.xml` is the one part an unedited save may write; **a file whose extended properties name `DiaCraft` is the exception**: the save gives the `Value` of its `User` and `Field` rows that hold a text the unit `STR`, so it may rewrite pages, masters and the document part, and the second read is the first read with those units), the save wrote no other part, rewrote, added or took out nothing else (**it never writes a part the first read refused**) and left every other part with its bytes. Three more properties, each on two inputs in three or on its own kind of input: a save from the model alone (what a `.diacraft` file saved as a package gets) reads, is the same bytes twice, and, for a package whose solution part the first read took for DiaCraft's, holds the parts of the other format that the first read kept and no other, and the judge refuses nothing of it (none of the carrier's words of refusal; a part left unread for what its relationships are is written as the package had it, and the model writer keeps the first of two rows of one `Id`, so a save may make it readable, which is not a part the first read refused); a save into the file of a model whose DiaCraft data changed (the solution part is written again) takes out no part that is not DiaCraft's; and a model that a program made (the seed's, with parts of the other format added: a name that reaches outside, one that differs only by case, a control character, a name at the cap and past it, a role the name does not say, a macro project written as a type that allows none, and object frames of an `.odg` that name those parts or name nothing, or show a picture no reader draws) is written as a package that reads, whose parts are the parts that ride (a part an object frame carried back is its embedding instead, byte for byte and a compound file at its head, and nothing is lost or made), or is refused in words. A refusal of a save is in words and is not a self-check or a mismatch of the original.

The writer now keeps the part as it is and says so, as it does for a part that is not XML, and, for another part's relationships, takes them to name a part of DiaCraft's, as the reader does (`crates/vsdx/src/write/diacraft.rs`; two regression tests in `tests/it/carry.rs`).

- **The content check's targets (`canon_compare` of `crates/container/fuzz` and of `crates/odg/fuzz`).** The container's target compares two mutated copies of a package under every rule of the container's check, each with a list that a small input reaches. Its input and its properties are the crate's library (`src/lib.rs`), which the container's tests include (`crates/container/tests/it/canon_fuzz.rs`): an input the target crashed on is replayed there through the same law, and 3,000 generated packages that hold the oriented namespace in every place are held to it in every test run. The odg target compares drawings built from the fuzzer's choices, as a package and as a flat file (structured modes), and the fuzzer's own bytes (raw modes). **The count is symmetric where nothing orients it.** Two rules orient the check, `Rules::ignored_when_extra` (in an `.odg`, DiaCraft's own markup counts as nothing when only the second file has it) and `Rules::twinned` (in an `.odg`, an `xml:id` counts as nothing when only the second file has it, beside an equal `draw:id`; the container's target lists none). So the container's target asks for `count(a, b) == count(b, a)` under every other rule. With that rule as well, it asks for the same count wherever neither package declares the rule's namespace. And it asks for the orientation itself where it plants it: an attribute and an element of the namespace on a part's root are no difference when only the second package has them, and one when only the first does. The odg target asks its raw inputs for symmetry only where neither file can hold DiaCraft's markup or an `xml:id` (a package of the fuzzer's is not looked into), and its structured drawings, which hold none, for every pair. The container's target also plants `xmlns=""` where a rule reads a name: a child that counts as nothing under a parent of a namespace is no difference, and the same child with the default namespace undeclared, on itself or on its parent, is one; an empty relationships part whose root's child undeclares the default namespace is a part. The container's target lists `identified_by` (the attributes `id` and `urn:a`'s `k`) and `doctype_parts` (`/p0.xml`), so that it reaches the alignment of children by what they are and a part that begins with a DOCTYPE; the count's symmetry is the law that holds the alignment to the same answer whichever document is first (a match is made only where both lists say the same of it, so that swapping them swaps each pair), and the generated packages of `canon_fuzz.rs` hold the fragments that reach it.

The fault was the target's law, not the check: the target had listed the orienting rule and still asked every pair for symmetry, and without the rule the pair counts 1 either way round. The odg target had the same law, not yet reached: a crafted flat file with DiaCraft's attribute on its root stopped it at 4 against 3.
  - **Measured** on beast (2026-11-23, load about 10 to 20, one core each, libFuzzer built as the recipe says, each seeded with the full gate's corpus): the container's target about 14,300 inputs a second (the gate's run, under the old law, about 25,700), the odg target about 50. A run of 10 minutes each on the fix ran 8,575,964 and 29,909 inputs, past where the gate's had stopped: none crashed, hung or ran past the timeout.
- **No C++, no nightly.** `libfuzzer-sys`'s build script compiles LLVM's libFuzzer (26 C++ files) unless `CUSTOM_LIBFUZZER_PATH` names a library, and a check links nothing, so the step names an empty file (`libfuzzer-stub.a`, in the check folder). It needs no C++ compiler and no sanitizer flag. Measured on beast (2026-11-19, `-j 4`, machine load about 30, main 6af62f2, seven targets): the three crates take 20 s on a target directory and locks that have never been built (the check is built with `--all-features` and `--cfg fuzzing`, so nothing is shared with the workspace's own build), 1.9 s after a change to a library they use, 0.4 s after a change to a target, 0.4 to 0.6 s when nothing changed (three `cargo metadata`, three `cargo update --workspace --offline` and three `cargo check`, each answering at once); the container crate alone took 2.1 s with the stand-in and 6.4 s with libFuzzer built (measured before `--all-features` and `--cfg fuzzing` were added).
- **Lock, and the network.** Each fuzz crate's `Cargo.lock` is git-ignored. It is made from the workspace's `Cargo.lock` on a crate's first run and again whenever the workspace's changes (a copy of the one last used is kept in the check folder), so the type-check sees the dependency versions that ship, git dependencies at their pinned revisions; a lock a crate has from a run by hand is replaced once. A `Cargo.lock` that is a link to nothing counts as no lock and is replaced by a file. `cargo update --workspace` then adds `libfuzzer-sys` and `arbitrary`, **offline first** (from cargo's own cache) and online only when that fails, so a machine with the two crates in its cache needs no network and the gate does not turn red because the network is down; when neither works the error says "a network or lock problem", never "does not compile". Every fuzz manifest pins the two crates to an exact version (`=0.4.13` and `=1.5.0` today; a test checks that all the fuzz crates agree, and a crate made by `cargo fuzz init` fails it until it is pinned), so that a release upstream cannot turn the gate red; to move them, change every fuzz manifest in one commit. On a machine that has never had them the step downloads the two small crates, as the gate's own build downloads the rest; `CARGO_NET_OFFLINE=true` is inherited.

## Hostile-file sweeps

A clean fuzz run and the costs measured on a fixture have both missed hangs here (the chains); crafted inputs that were timed found them. The sweeps put such inputs in the normal test run: deterministic hostile files for each format, each case on a thread of its own with a wall-clock budget, so that a hang or a crash fails every `cargo test` and not only a fuzzer's run, and each mutant that the reader lets in goes on through the rest of the program. The fuzz targets stay (they look at random, for hours); the sweeps look at the same places every time, in seconds, and look **past** the reader.

- **Where.** `crates/testkit/src/door/` is the machinery (`seeds.rs`, `zipfile.rs`, `xml.rs`, `mutate.rs`, `pipeline.rs`, `run.rs`, `rng.rs`, with unit tests in each), and each format has a test file that builds a `Door` (its seeds and its pipeline) and calls `sweep`: `crates/vsdx/tests/it/door.rs` (`.vsdx`), `crates/odg/tests/it/door.rs` (`.odg` as a package and as one flat `.fodg`: two tests), `crates/native/tests/it/door.rs` (`.diacraft`) and `crates/mxfile/tests/it/door.rs` (draw.io, through `diacraft-mxfile`). Nothing is read from a file and no binary is committed: the seeds are made in code, the same bytes on every build (the time a save writes is pinned).
- **Seeds**, a few for each format. `.vsdx`: a small drawing, one with a little of everything the reader reads (a group, a master, a theme, a connect, a picture, a comment, a solution part), and one whose styles and masters inherit. `.odg` and `.fodg`: two drawings written by hand from the standard (a plain page; two pages with groups, a frame, an ellipse, a line and a connector glued to shapes, under styles that name their parents), as a package and as one flat document, and, packaged, one that the engine writes from a VSDX drawing. `.diacraft`: what the engine writes from the VSDX drawings above and from the `.odg` one. draw.io: a plain page, a compressed page and a file of two pages. Each seed must go through the whole pipeline unmutated, twice, before a mutant is made (the control of the sweep): a seed that fails either of its two runs, or does not end, fails the sweep, and then no mutant is made.
- **The mutations**, nineteen classes in four groups, each made from a fixed stream of random numbers (the seeds in turn, and for each round the next class that fits the seed, so that every class runs about as often as the others).
  - **Bytes:** bit flips, an overwritten run, a cut-off end, bytes put in, taken out or copied; each on the file as it is (a package's checksums refuse most of them: the container's own check) or inside one entry that is then written again with true checksums, so that the change reaches the reader above the container.
  - **Entries:** an entry written twice (equal, or with its data garbled), taken out, moved, renamed (another case, `../`, a leading slash, backslashes, a NUL, 65,535 bytes, a bidirectional override, no name) or replaced by a run of one byte (zeros, spaces or empty elements), deflated.
  - **A ZIP writer that lies:** every field of a local header and of a central record is held apart, and a mutant changes one (sizes, offsets, checksums, names, the compression method, the flags, extra fields with a Zip64 record that lies, a record the directory does not list, data that are cut or noise under true headers) or the end record (its count, the size and the place of the directory, its comment and the comment's length, junk before the first header or after the end record, a second end record).
  - **XML**, on one part of the package (or on the flat file), written again with true checksums: groups nested 64 to 3,000 levels deep (the format's own unit: `Shape` in `Shapes`, `draw:g`, the codec's `diacraft:shape`) or one element inside itself; a flood of attributes, one attribute of 64 KiB, one name written twice; copies of an element; entity references (a thousand `&amp;`, invalid character references, a billion-laughs ladder, an external entity); numbers past every range (`1e308`, `1e999`, 400 nines, `-0`, the edges of every integer width) and text that is no number (`NaN`, `Inf`, `#NUM!`, `1/0`, `0x7FFFFFFF`) in numeric attributes, three times in four in the value of a cell where the format has cells; formulas (a ring of cells that read each other, a cell that reads itself, one that reads hundreds, parentheses, signs and calls nested 100 to 5,000 deep, 10,000 additions); loops of references (a style that is its own parent, styles that name each other, shapes a connector is glued to, `parent` of draw.io cells, a master whose shape is an instance of the master, masters that are instances of each other); and a chain of linked items (100 to 4,000: shapes that take their width from the next, glued connectors, cells that are each in the one before).
- **What a case goes through.** Each case runs on a thread of 2 MiB (a test thread's stack, the one the engine's recursion limits were checked on) in the engine's files in memory (`diacraft_engine::memfs`: no disk). The engine opens the mutant (`file.open`, by what its bytes say). A mutant that is let in has its first page drawn as a PNG at 24 dpi (`file.export`), its first shape moved (`shape.move`), and is saved three times (`file.save`, `file.save_as` a `.diacraft`, and `file.save_as` a `.vsdx` or an `.odg` by the case's number); each file written is opened again, and the `.diacraft` one holds as many pages as the drawing. A step that is **refused in words** is no failure (a refusal names the trouble and no path, in at least six letters); the report counts the refusals by their words with the numbers taken out, so that what a sweep is refused for is in view, and gives the first case of each step refusal. A case **fails** on a panic; on `EngineError::Internal` (a panic the engine's guard caught); on a `Recovered` skip of the export (a frame that met a bug: the renderer catches the panic and says so, so it would otherwise pass for a refusal); on a refusal with no words; on a file the engine wrote that it will not open again, or opens with other pages; and on a case that does not end in its budget. The draw.io reader is not opened by the engine yet, so its door is the reader (`document_door`): the drawing it makes is written as a `.diacraft` file with the native writer, and that goes through the same steps.
- **The budget** is for a hang and is no measure of speed. A case is given 20 seconds, and 200 times what the unmutated seeds take on this machine now (the yardstick: the slowest of them, in a second pass) for each 64 KiB of the mutant, never more than 80 seconds, under the 120 seconds that nextest allows a test: a loaded machine is given more, a quick one is not asked to be fast, and a file that is large is given the time a large file takes (a flat drawing of 20,000 chained items, 40,000 shapes, takes 40 seconds and 1.6 GB to open, draw and save at a load of 30, and is of the heavy sizes). A case that passes its budget ends the sweep (its thread cannot be stopped and would go on using the machine), and so does a seed of the control that does not end in 80 seconds: the report is failed at once and no other run is started. The sweeps assert no other time. The work a reader does stays held to its own **counted** budgets, which each sweep checks on every mutant before the engine's open: the VSDX reader's items, cells, shapes, formula nodes, bytes of XML, depth and memory against its limits (for a read that is let in); the `.odg` reader's items and bytes of text against its limits (for a read that is let in), and the container's counts of a read for the `.odg` and `.diacraft` readers (a scan for the end record of at most 65,536 places, no more rows than 46 bytes a row leave room for, no more bytes of names than twice the file); the draw.io reader's `ReadWork::total` against `Limits::max_read_work`, whether it reads or refuses.

- **Environment.** `DIACRAFT_DOOR_CASES=n` makes n cases for each format (300 by default; a longer search runs with `cargo test -p <crate> --test it door:: -- --nocapture --test-threads=1`, not nextest, which ends a test at 120 seconds); `DIACRAFT_DOOR_SEED=n` another stream; `DIACRAFT_DOOR_BIG=1` adds the heavy sizes (nests of 20,000 and 100,000 levels, chains of 20,000 items, floods of 60,000 attributes, copies of 30,000, formulas of 50,000 and 200,000 steps, bombs of 16 MiB; it takes minutes and up to 2.7 GB); `DIACRAFT_DOOR_CASE=i` runs case `i` alone; `DIACRAFT_DOOR_BUDGET=secs` gives each case that many seconds, to let a case that was called a hang run to its end; and `DIACRAFT_DOOR_DUMP=name` writes each **distinct** failure (by its words with the numbers taken out) as a file and a note (what was done, what happened, how to replay) to `$TMPDIR/diacraft-door/name` (`1` for the folder itself), with the seeds beside them to diff a mutant against, and the file the engine wrote when it would not open it again. A failure names its case, its seed, what was done and the line that replays it, as `DIACRAFT_DOOR_CASE=192 DIACRAFT_DOOR_SEED=11 DIACRAFT_DOOR_DUMP=1`.

## Proofs (Kani)

[Kani](https://model-checking.github.io/kani/) (0.68.0, with CBMC 6.11) is a bounded model checker for Rust. A **harness**, a function marked `#[kani::proof]`, draws its inputs with `kani::any()` and asserts a property, and Kani either proves it for **every** input of those types or gives a counterexample. A unit test names a few inputs; the number code's bugs sit at NaN, an infinity, zero and the ends of a range, which a harness covers without naming them. Kani's findings so far are below ("Laws that failed on the real code").

- **Where they are.** A crate keeps its harnesses in `src/kani_proofs.rs`, declared in `src/lib.rs` as `#[cfg(kani)] mod kani_proofs;`, or, in a crate that is only a binary (`apps/diacraft-cli`), in `src/main.rs`: `cargo kani` proves the harnesses of a binary target as it does a library's; `xtask`, a library and a binary, declares its file in `src/main.rs` too, since the code it proves (the site's checks) is the binary's. `cfg(kani)` is off in every ordinary build, so no `cargo build`, `clippy` or `test` compiles the file; the workspace lint table lists the cfg (`unexpected_cfgs`) so that nothing warns, and `cargo xtask brands` and `stats` do not count the file as shipped code. - **The version pin, and CI.** Only Kani **0.68.0** (its toolchain is nightly-2026-08-21; ordinary builds stay on stable): the models and the words of the output change between releases, and a proof holds for the release it was checked with. The `kani check` step of `cargo xtask ci` runs `cargo kani -Z unstable-options --only-codegen` on each crate with harnesses (8 s with the build warm, about 1.5 minutes cold; it builds into `<target>/kani`), so a harness that no longer compiles fails the gate: clippy never sees `cfg(kani)` code, and Kani's compiler ignores clippy's lints (the crate's `deny(unwrap_used, panic, ...)` do not reach a harness, which may assert and panic). The step is **skipped, not failed**, when `cargo kani --version` fails or reports another version, and when Kani 0.68.0 was never set up on the machine, as the `fuzz check` is when there is no fuzz crate. - **What Kani models.** `f64` bit-precisely, NaN, both infinities, subnormals and the two zeros included: `kani::any::<f64>()` ranges over all 2^64 bit patterns, and `+ - * /`, comparisons and casts are IEEE's. **`sin` and `cos` are over-approximations**: `|sin(x)| <= 1` holds, `sin(1)` in (0.841, 0.842) does not, so through trigonometry only bounds and finiteness can be proved (a PoC probe of this, not kept). **`powi` and `powf` are too**: `x.powi(0) == 1.0` is the only exact case (`x.powi(1) == x` and `2.0.powi(3) == 8.0` do not hold, measured on 0.68.0), so a harness through them asserts only what holds for any result, and `Quantity::scale`, which is a `powi`, is out of reach for a length, an angle, a duration, a percent and a date (the units harnesses take the acre, the hectare and no unit). **The float remainder `%` is too** (measured on 0.68.0, 2026-11-21: `wrap_turn(x)` for every finite `x`, and `MODULUS`'s remainder for every pair, fail on a result no real `%` gives, since the model does not bound it by the divisor): the two folds that follow a remainder are proved for every remainder, and the remainder itself, the standard library's exact `fmod`, is tested. A loop is bounded: `#[kani::unwind(N)]` sets how many times Kani unrolls it, **a bound too low is reported as "unwinding assertion loop 0", which looks like a bug in the code under test**, and it also bounds loops in the harness itself (iterating a `[f64; 8]` needs 9).
- **Traps.**
  - **`--manifest-path`, not `-p`.** Kani reads a crate's `[package.metadata.kani.flags]` only for a run in or pointed at that crate: `cargo kani -p diacraft-calc` from the workspace root ignores them. `cargo xtask kani` points at each manifest.
  - **The NaN check.** By default Kani fails a harness at every operation that produces a NaN (`inf - inf`), even when the code turns it into `#NUM!` on the next line. Only `--no-overflow-checks` turns it off, and what it drops is that NaN check and no integer check: Kani still fails a harness at an integer add or shift that overflows and at a division by zero (measured on 0.68.0, 2026-11-21, with a throwaway crate: with the flag on, `u8 + u8`, `u8 << u32` and `u8 / u8` still failed, and `inf - inf` failed only with it off). `crates/calc/Cargo.toml` sets it for that crate, with the reason; a crate that needs it says so in its own `[package.metadata.kani.flags]`.
  - **A cover that Kani does not enforce.** `kani::cover!(cond, "what")` is satisfied when some input reaches it; Kani reports `N of M cover properties satisfied` and still says SUCCESSFUL when N is less than M. Put a `cover!` on every result a harness claims to check (each `Ok` branch, each error), and none inside a helper that a pair of operands of another kind calls (it is then unreachable there): collect what the calls saw and cover it once, as `Seen` does in `crates/calc/src/kani_proofs.rs`.
  - **Symbolic floats and a second circuit.** A harness that computes `a * b` itself to compare with the code's `a * b` makes the solver show two multipliers equal, which it cannot do: the proof times out (the same for a divider). State the answer from the classes of the operands instead (NaN when an operand is NaN, or `inf * 0`, `inf - inf`, `inf / inf`). Keep a harness to one to three symbolic floats and no more than one division: an eight-float property ran 3 hours without an answer, and properties of two to four floats over `clip` time out at 900 s with every solver. A round trip through a multiplication and a division ("within 2 ulp") times out too. A later batch met it twice more: a pull of a strength on the screen held to `d * zoom <= px` beside `craft_snap::Reach::within`, and a stronger pull to the weaker's reach, each ran past 150 s; a slider's width worked again beside `slider_width` took 121 s, and 0.2 s without. Another met it again: that two percents in order have hundredths in order (`format_fx::hundredths` twice, two products and two roundings) ran past 300 s, where the laws of one percent took 0.1 s.
  - **A choice of operand kind.** `if kani::any() { a } else { b }` or a pick of one of three pairs, followed by a floating-point operation on it, made the proof time out where three calls in a row (one per kind) took seconds. Comparing two currencies (`Currency`'s `==` compares the bytes of the code in a loop) never ends while the amounts are symbolic floats, even for two `None`: pick each currency by a `match` on a number (a pointer into the table chosen by a symbolic index is a loop as well), give the harness `#[kani::unwind(5)]` and leave the amounts constant.
  - **Laws of `clip`.** Calls of `clip` in one harness add their costs: six level lines in a row ran past 300 s where one takes 30 to 75 s, so give a line its own harness. A law that a carried coordinate is near the exact one makes the solver undo a division by the direction, which ran past 300 s for a direction of any significand from 1 to 2 and takes 17 to 82 s for directions whose parts are powers of two (the steps are then exact): narrow the direction, not only the point. A fixed place can miss a branch: from a place of 0 the difference of an edge is never past the largest number, so the harness of that branch starts from minus half of it. And a family has to be able to reach each cover: y = 2x crosses every window whose right side moves from -1 up, so its miss was never reached, and `cargo xtask kani` fails such a harness.
  - **Solvers.** The default is CaDiCaL. `#[kani::solver(kissat)]`, or `--solver kissat` for a run, is often 2 to 200 times faster on a hard harness (it did not help the harnesses here). Bitwuzla through CBMC 6.11 does not work (an SMT2 parse error).
  - **A harness with no loop bound.** Without `#[kani::unwind(N)]` CBMC unrolls a loop until it sees it end, and some loops it never sees end: the comparison of the words of a refusal taken out of an error (`matches!(e, CodecError::Limit { what: "...", .. })`, a byte comparison of a `&'static str`) ran 300 s with CaDiCaL and 600 s with Kissat, z3, cvc5, Bitwuzla and MiniSat alike, because no solver was reached; with `#[kani::unwind(46)]` the same harnesses took 5 s. A harness that times out whatever the solver is one to give a bound to. The same holds for a loop that does not run: `cells_bytes` of up to eleven cells, whose loop over the levels above the leaves is decided by a quotient, ran 300 s with no bound and took 0.1 s at `#[kani::unwind(2)]`.
  - **A loop inside a loop.** The bound is each loop's, and a loop that runs inside another is unrolled that many times in each of the other's: `base64_decoded`, whose loop over the characters holds the loop of `filter` that skips blanks, took 218 s for one character at a bound of 10, and 8.5 s at 3. A length that is symbolic makes the bounds symbolic too (a slice `&text[..len]` of a symbolic `len` did not finish): one harness for each length, with a bound of the length and two, as the units harnesses take one unit each. The same holds for `str::from_utf8` and `str::parse` inside a search of a text: the scan of a part for the blobs it names (`diacraft_native`, `blobs_named_bytes`) did not finish in 300 s on ten symbolic bytes, and is not proved.
  - **The standard hash map.** A harness that inserts two keys into a `HashMap` and reads one back did not finish in 300 s: code that keeps one (the reader's table of units it shares, an encoder) is not proved.
  - **The drop of a type that holds itself.** A value whose type holds a list of its own kind (a page, whose shapes hold shape lists; an XML node, whose elements hold nodes; a `RawNode`) is dropped by glue that calls itself, and CBMC unrolls that call at every level to the bound, each level with its own loops: one `diacraft_doc::Page::new` and its drop ran past 180 s alone, and a `weave` of three typed children and one unknown node past 180 s (what it does not take of the nodes is dropped, a count the solver does not know). `std::mem::forget` of a value the harness made skips its drop, and took the art of the line ends from out of memory to under 90 s; a drop inside the function under test cannot be skipped so, which leaves the pages of and the place of a typed child against `weave` itself out of reach.
  - **A text searched for a character.** `str::split_once` and `find` of a character scan the text a word at a time (`memchr`): a harness of `carry::content_type_of` (vsdx) on two to five symbolic characters took 176 to 192 s a length, where a check of the same characters byte by byte takes seconds.
  - **The harness's own panics and overflows.** An input made for a type must be one the type holds: `Duration::new(secs, nanos)` with any nanoseconds panics past the last second, which Kani reports as `This is a placeholder message; Kani doesn't support message formatted at runtime` in `option::expect_failed`; and a cover that overflows (`at + 3` at `usize::MAX`) fails the harness as an overflow of the code would. Both are the harness's, not the code's.
  - **A dependency's harnesses are compiled too.** `cargo kani` builds the crates of the workspace that a crate depends on with `cfg(kani)` as well, so a harness file that does not compile stops the runs of every crate that depends on its crate (an error in `sheetxml`'s stopped `native`'s, `vsdx`'s, `odg`'s and `engine`'s), and the future-incompatibility warning of a match arm that is a bare `assert!` is listed for each crate that holds one, in the run of any crate above it.
  - **The standard library's futex.** Making an `EvalCtx` (`diacraft_calc::EvalCtx::new`) or a `SheetReader` (`diacraft_sheetxml::read::SheetReader::new`), each of which makes a hash map, reaches `futex_wake_all` through the foreign function `syscall`, which Kani 0.68 does not support: the harness fails at once (`call to foreign "C" function syscall is not currently supported`), whatever it asserts, so the charges of an evaluation and the bytes a reader sets aside are not proved. **`HashMap::new()` alone does it** (a probe): a value that holds a map or a set made by `new` or `default`, or a `&mut` of one, is out of reach (`canon::names::Sig`, `draw::ties::Ties`). ## The window's tests and time

The window's tests (`crates/ui-egui/tests/it`) must give the same answer on a quick machine and a busy one. Two things made them not:

- **The window's own timers.** The window decides some things by how long ago something happened (a view that has stood still is drawn again in full, a drawing that failed is not asked for again for a second, an edit's outline is kept while the picture catches up, the seconds a file takes, the delay after `app.quit` before the window closes, the time a screenshot waits for its frame, the eight seconds a status-bar notice stays, `notice.rs`). They read the window's `Clock` (`clock.rs`), never the machine's: the application's is the machine's, **every test window's stands still until the test advances it** (`window.advance(duration)`, `Rest` in `tests/it/support.rs`). A test that needs time to pass says so; one that does not never meets a timer that ran out because the machine was slow. `DIACRAFT_TEST_CLOCK=real` or `tick:N` (a clock that goes N ms further each frame) is a hook for seeing which tests depend on a timer; it is not set in CI. `tests/it/clock.rs` scans the sources so that nothing else reads the time.
- **The window's threads.** A dialog, a file being read, a picture, the scan for the Font list: each answers when the machine lets it. `Rest::rest` draws a frame (so that a thread this frame starts is seen), waits while a thread has an answer to give, and then runs the window to rest. **Never `Harness::run` on a window.** A test that holds a thread on purpose uses `rest_holding`.

To see a test under a slow machine, prefer the clock hook to load: a busy-loop load takes the machine from other people, and a loop started in the shell and killed with `kill $PIDS` is **not killed in zsh** (an unquoted variable is not split into words): keep the loops in an array, give each one `timeout`, and run no more than eight.

## Characters no face draws in the window's tests

`egui_kittest` builds every test window with egui's `MissingGlyphPolicy::Panic`, so that a label of ours holding a character no face draws fails a test instead of showing a box nobody sees. **The shipped window is not like that.** egui's default is `Tofu` (a box), eframe keeps it on the desktop and in the browser, and nothing of ours sets the other policy, so a character the faces lack is a box and never a panic: found no panic in the real window (typed into and read from a file, over the control channel: arrows, box drawing, Han, emoji, Arabic and a plane beyond the first) and none in a test window laid out as shipped, in any of nine kinds of box and every panel that shows a file's names and text. In a test window the panic is caught by the window's guard, counted (`ui_panics`) and said in the status bar with the character in it, so a test that asserts `ui_panics() == 0` fails.

- **A test that gives the window a person's text lays it out as shipped.** The text is typed, pasted or read from a file, in any script. `support::as_shipped(&window)` does it to a window that is built; `support::shipped_window(app, size)` builds one that is as shipped from its first frame, which an app that already holds the text needs (a notice, a file's page name), since the harness draws frames while it builds the window, before a test can call `as_shipped`. `tests/it/glyphs.rs` holds the hostile texts (`hostile()`: emoji that join, Han, Arabic and Hebrew, Thai and Devanagari, the planes beyond the first, private use, noncharacters, marks, controls, text that turns round), types each into every kind of box, reads back what the box or the drawing held, and shows each in every panel at a narrow and a wide window; `apps/diacraft-web/tests/it/glyphs.rs` does the same for the window the web shell makes, with no browser, so what only a browser does (the canvas rasterizer eframe's web runner puts behind the faces) is not tested.
- **A word of ours stays strict.** A window test still fails on a label with a character the faces lack. The proportional chains are Ubuntu Light, then Hack (the arrows, the box-drawing and block characters Ubuntu Light lacks; it is in the module already for the monospace text), so an arrow in a notice is fine and a Han letter in a label of ours is a failing test.

## The start-up splash and the build's git release

A window made with `DiacraftApp::new` has none, so the tests of the window keep their clicks, and `tests/it/splash.rs` asks for it with `with_start_splash`.

**Third-party licences** (`crates/ui-egui/src/licenses.rs`): a line under the licence line, a link that runs the window command `app.licenses` (the panel gives way to it). The window is a modal card with a list of `THIRD-PARTY-LICENSES.txt` (in the web build `THIRD-PARTY-LICENSES-WEB.txt`: the web build's crates, and the words over the list name that file), which the desktop window carries built in (`include_str!`, 0.4 MB of the program) and the web window **fetches** when the card first opens (`asset_host.rs`: a placeholder says it is loading, and a failure is said in words in the card), broken at 100 columns and laid out a screen of rows at a time (`ScrollArea::show_rows`): the wheel, the bar, Page Up, Page Down, Home, End and the arrow keys scroll it; Escape and Close end it. The command and the state `licenses` (`rows`, `offset`, `text`, `error`) are in `docs/control-protocol.md`. The file in the repository is what `cargo xtask licenses` made; a test (`crates/ui-egui/tests/it/licenses.rs`) holds the built-in text equal to it.

**The build's two texts.** The first is the build line, the second line of the splash and the About panel under "DiaCraft 0.2.0" and the `git` of `app.version`. It is made from the output of `git describe --tags --always --dirty` (`v0.1.0-766-g106427ea`) and the workspace version, taken by a build script, never at run time (the window and the engine run no git and read no clock). `DIACRAFT_BUILD_GIT` replaces the describe text for a build from a tree with no `.git`, such as the public export, and with neither it reads `unknown`. **The line follows the version** (`identify` in `apps/diacraft/build_info.rs`, the version being the build script's `CARGO_PKG_VERSION`, which is `[workspace.package]`'s, set by `cargo xtask version set X.Y.Z`): a describe text that names the tag of the version reads as the version, without the `v` (`v0.2.0` is `0.2.0`, and `v0.2.0-12-gaab1664d` is `0.2.0+12.aab1664d`, twelve commits on); a text that names an older tag or no tag (`v0.1.0-1555-gaab1664d`, `aab1664d`) is a development build of the version, `0.2.0-dev+aab1664d`, so that a build made before the tag `v0.2.0` exists does not read as a 0.1 build; `.dirty` comes last for an edit that is not committed (`0.2.0+dirty` for the tag itself); and a text that says nothing of the version (`unknown`, `nightly`, the release rehearsal's `dev-<commit>`) is the line as it stands. A version that has a pre-release already takes `.dev` (`0.3.0-rc.1.dev+aab1664d`). `DIACRAFT_BUILD_GIT` goes through the same rule: the release workflow names the tag (`v0.2.0`), and the line is `0.2.0`, as for a build of the tag with git. Git is believed only for this checkout (or a linked worktree of it): a tree unpacked inside another repository, whose top folder is not this workspace, is a tree with no git, so it is not described as that repository. The year is that of the commit's date, `DIACRAFT_BUILD_YEAR` replaces it, then the year of `SOURCE_DATE_EPOCH`, and last of all 2026, so a build of one commit is the same build every time. A variable that is no good (not four digits, a newline in the release, more than 48 characters) is passed over for the next source, and a build never fails for it. Three crates have the build script (`apps/diacraft`, `apps/diacraft-cli` and `apps/diacraft-web`: the work is the one file `apps/diacraft/build_info.rs`, which the other two take with `#[path]`), each hands the texts to the engine at its start (`diacraft_engine::build_info::set`), and `app.version` answers `{app, version, git, year}` for the command line and the MCP server. **A crate that has the script is built again when the commit changes and not otherwise** (cargo watches `HEAD`, the branch it names and `packed-refs`, and so also a commit made in a linked worktree), which is why the engine and the window do not have it: they would take everything above them with them at every commit. `--dirty` is the state of the tree when the script last ran: an edit that is not committed does not run it again.

The tests: `apps/diacraft/tests/it/build_info.rs` runs the build script's own file against what git would have said, as text (the build line for each shape of describe text and each version, and both cases of against real git, in a repository the test makes in the temporary folder, where it makes the tags `v0.1.0` and `v0.2.0`: a version newer than the last tag, and the tag itself; the variables win, a tree with no git is `unknown`, the year's order of sources, the directives that keep cargo from building every time, a ref that climbs out of the folder is not followed), `crates/ui-egui/tests/it/splash.rs` drives the popup on the window's manual clock (four seconds, held while hovered, a click and Escape used up, the links asking for the pages, no repaint loop, the text inside its zone at several sizes and pixels to the point, the panel 836 × 470 points at every density and painted from the cover at two pixels to the point) and reads the picture itself and the cover (the text's zones hold only the cover's cream in both, and the two inks come from the art and read at 4.5 to 1 or better on it), `tests/it/assets.rs` holds that the web build's splash fetches no cover and uses the one the File view fetched, and the engine, the command line and the web page each test that `app.version` answers the build.

## Tests of the memory a read may use

The engine counts what is held that a read of a file must leave room for in one ledger for the process (`diacraft_engine::memory`: a `Hold` for each open drawing and stencil, and a reservation of all that is left of the budget for each read that is running, which `held()` does not include: the edit guard of a session reads `held()`). The tests of one `cargo test` binary share it, and nextest gives each test a process. **A test that asserts an exact figure of the ledger, holds a reservation (`reserve_read` takes all that is left, so a read made at the same moment in another test is refused, or waits for it, unless it is a stencil, which is given a slice beside it: `reserve_read_brief`), or reads a drawing of tens of thousands of shapes, runs its case in a child process** of the same binary, under `ulimit -v 3000000` where it is about what is not to abort (`crates/engine/tests/it/vsdx_memory.rs` is the pattern: the parent builds the files, starts the child with the case in the environment and reads what it printed). A test that peaks at 500 MB or more, or starts such a child, goes into the `memory-heavy` group of `.config/nextest.toml`. A read waits up to 30 seconds for a read that is running (`memory::read_wait`): a test that holds a reservation in the thread that then reads sets no wait (`memory::set_read_wait`), or it waits for itself. A test of a refusal asserts the words and the kind of trouble (`out_of_memory`, `too_big`), not only that the read was refused.

**What a decode is charged is held to what the model keeps, counted**. The global allocator of `crates/sheetxml`'s test binary is a counting one (`stats_alloc`, which passes every call on to the system's allocator, so the tests that measure the process measure what they did), and `tests/it/model_memory.rs` decodes each kind of element in a child, at a count one more than a power of two (where a vector that grew by doubling has room for twice what it holds), and holds the charge to the bytes and the allocations the model keeps, with 24 bytes for each allocation (the most glibc adds to one of 8 bytes or more). The growth of the child's peak resident size is checked as well, but only within twice the charge: it misses a vector's room that nothing has touched, holds the decode's transients, and moves with the platform's allocator (20,000 connects kept 118 bytes each, and the process grew by 52 to 71 bytes each on Fedora's glibc 2.44 and by 98 on GitHub's Ubuntu 24.04 runner, where the test failed against a charge of 96). A test that holds a charge to the resident size alone measures the platform, not the model.

**The VSDX reader's prices are held the same way**. The vsdx test binary's allocator counts too, and `crates/vsdx/tests/it/memory_counted.rs` reads, in a child, a file of each kind of thing a drawing repeats (52 kinds: shapes, cells, rows, sections, connects, text, kept markup, styles, masters, pages, colours, faces, pictures, and what the model holds beside its fields: parts, relationships, content-type rows, custom properties, the windows part, the properties no field reads) at a count one more than a power of two, and a file of none, and holds the charge of the units (`Stats::memory_bytes`, the difference of the two) and of each whole file to the same law. The prices were glibc's chunk to the byte (its own count of the bytes in use, `mallinfo2`, gave the same figures), and the law gives an allocation 16 bytes more than a chunk does: a string and a buffer are priced at the law's figure now (`diacraft_sheetxml::price::block`), and `memory_price.rs` keeps holding whole reads to the growth of the process (it passed the old prices and a mutant of them: a read of 500,000 connects). The app and the command line run on mimalloc, which has no header but rounds a request to one of four sizes in each doubling: a map of cells' leaf of 1,160 bytes is 1,280 there, so four kinds whose model is mostly such leaves and lists keep more under mimalloc than the law allows (a geometry section 1,488 bytes, where the law allows 1,416), and the charge still covers each, by the margin of an eighth (1.125 times at the least). A count under mimalloc is a scratch build, by hand: a counting wrapper of it needs `unsafe`, which no crate of the project has.

**The law covers the allocator the app ships with, and the `.odg` model is counted too**. The three counted tests hold a charge to the bytes kept, an eighth of them for mimalloc's size classes, and 24 for each allocation (`law_need` in `crates/sheetxml/tests/it/model_memory.rs`, `Counted::need` in `crates/vsdx/tests/it/memory_counted.rs`, `need` in `crates/odg/tests/it/memory_counted.rs`). Every VSDX kind meets it at its prices; the whole-model codec's figures of twelve kinds were short and are a quarter above the count, and its node of a map of cells is priced at the law (`cost::law_bytes`, 1,344 bytes where glibc's chunk is 1,168), which the engine weighs every drawing with, so the save's check of a `.vsdx` of diagram shapes over three pages admits 69,000 of them (76,000 before). The `.odg` test's binary counts with the same allocator, and its child reads a drawing of each of 40 kinds (shapes of every kind, text, styles, definitions, pages, master pages, layers, faces, package entries, user-defined fields and kept markup) and the same drawing with none, keeps the document and its index (which the engine holds beside it) and holds what the read says the model holds (`ReadCost::model_bytes`: its items at 64 bytes, the reader's own figure, where it was 54, and its pictures) to the law, for the units and for the whole drawing. Seven of the reader's charges were short (a user-defined field, a package entry, a page, a part of a text, a kept node's place in its list, a connector's route marker and a glued end's `Connect` row) and are charged a quarter above what they keep (`read::cost::priced`). The `.odg` save's gate, which counts the model twice, admits 308,000 rectangles of a page in a package and 302,000 in a flat document (about 349,000 and 342,000 at 54); a save the gate admitted before and refuses now is the ruling's. In `ubuntu:24.04` (glibc 2.39) the three tests pass as on Fedora (glibc 2.44), and every `.odg` kind counts the same bytes and allocations: the count is the model's, not the platform's.

**Text is charged at nine eighths of its length**. A kind made mostly of long text fails the law whatever the figure of its element, since the law's eighth of the text is the text's own: each counted test holds a cell of a formula of 10 KiB that is one string, a text of one run of 64 KiB and a kept text of 1 MiB (`long+formula`, `long+run`, `long+kept` in `model_memory.rs`; `formula_long`, `text_long`, `kept_long` in the two `memory_counted.rs`), at a count one more than a power of two. Against the old charges the whole-model codec met 0.455, 0.893 and 0.889 of the law, the `.odg` reader 0.991 for the paragraph and 0.894 for the kept text, and the VSDX reader all three (its margin of an eighth is on a price that holds the text). Both now charge every name, value, formula, run and kept string at nine eighths, rounded up (`cost::text_bytes` and `Budget::charge_text` in the codec, `read::cost::text` in the `.odg` reader), and the codec charges a formula's tree for the strings it copies of the source (`cost::tree_text_bytes`: a string literal, a name, a GUID), which made a formula of one string keep twice its text. The `.odg` reader read DiaCraft's cells with a sheet reader and charged none of the bytes it priced them at, so a cell of a formula of 5,000 arguments kept 280 KB and was charged a ninth of what the law asks (`formula_nodes`, 129 of them, 0.112); it is charged them now. The kinds pass by a few bytes in a thousand, as the law asks of text and no more, and the same in `ubuntu:24.04`. No capacity test changed its outcome: a rectangle holds no text, so the `.odg` save's gate for 300,000 of them moves by 512 bytes, and the files of kept markup and of every budget hold 1.4 to 3.0 percent more items.

**On macOS these tests do not all run** (on a real Intel Mac). macOS cannot limit a process's address space (`ulimit -v` fails there) and has no `/proc/self/status`, so the 60 tests that run a child under `ulimit -v 3000000` or read the growth of the process from `/proc` are ignored on macOS with that reason (`#[cfg_attr(target_os = "macos", ignore = "…")]`), and run on Linux, in the gate, as before. Some other tests read `/proc` too and pass on macOS without measuring anything (they read no figure and find no growth): only those that failed for it are marked. A new test of either kind takes the same mark.

## Tests of what an edit costs

An edit costs what it touched, and the tests say so by a **count**, never a time: a time moves with the load on the machine (a comparison of two times failed a test at a load of 46).

- **What `calc` was asked** (`crates/engine/tests/it/edit_index.rs`). `diacraft_calc::work::formulas_asked()` counts the formulas the dependency walk was made to ask whether they read beyond their own sheet. On a page of 1,500 shapes (21,000 formulas) the first edit asks them all, once, and each edit after it asks the formulas of the shapes it replaced and no others: a move asks none, a fill asks the fourteen of one shape and its new formula, and an undo asks those of the shapes it changed and no more. `calc` keeps what reads what through other sheets in a `ReaderIndex` (`crates/calc/src/index.rs`), which the engine's session owns (`crates/engine/src/calc_index.rs`) and counts in its hold on the process's ledger (`Session::calc_index_held`). In a drawing of two pages or more the first edit also lists the sheets whose formulas name a page (`Pages[..]`, `crates/calc/src/pages.rs`: a step for 64 bytes of formula text, and none for the pages of a drawing of one, which a change to the pages themselves lists all the same), and the sheets no page holds (the document's, the styles', the masters' and what an instance inherits from them; the sheets that name `TheDoc!`, `Styles!` or `Masters[..]!`, and the formulas a shape inherits from a style, asked only of a shape whose links name a style that holds such a formula), which the edits after it put right by what they replaced and do not repeat; `crates/engine/tests/it/sheet_hostile.rs` counts both (`a_write_in_a_drawing_of_64_pages_whose_formulas_name_no_page_costs_the_page_and_a_listing_once`), and `crates/engine/tests/it/page_readers.rs` counts the changes to the pages on 256 pages (a rename in a chain, a write through 255 instances of a master, 256 pages that read at run time, 256 pages that name no page), each with a timed twin that is `#[ignore]`d; `crates/engine/tests/it/unpaged_readers.rs` counts the cells of 255 pages that read the document's cell, 255 shapes that inherit a style's formula and 256 pages that name nothing (the sheets no page holds cost a step for each style and nothing for a page), and `crates/engine/tests/it/reached_pages.rs` the fields of 255 reached pages (one commit for the resize, and one for the text of each field, at most 256), each with a timed twin that is `#[ignore]`d.
- **The old walk is the oracle** (`crates/calc/src/affected/tests.rs`). `affected/oracle.rs` is the walk of every formula of the page that each edit made before the index, kept as it was. A property test (1,000 cases: a generated page of up to 27 shapes with groups, instances of masters, qualified references by `ID` and by name, frame functions, text measures, path functions, cells read through a call, cells that name a shape that is not there and `Connect` rows, and up to 13 generated edits: a value, a formula, a cached result, a row with no key, a shape added or taken out, a name, a master, a master's cell, a `Connect` row, a page's name, two shapes given one `ID`, an undo to an earlier document) holds the index, kept through all the edits of a case, to the walk **at every step**: the graph entry for entry in the order a walk lists them and the memory it is charged for them, the cells an edit reaches in the order they are handed out, the document after a commit and its report, and `changes_between_with` to `changes_between`. A second test says the generated edits go down every path of the index, and that the graphs held entries of every kind. The property runs in about three seconds in the test profile; nextest's 120-second limit is far off, and the case count is in the test (an explicit `cases` beats `PROPTEST_CASES`), so a longer run changes the number there.
- **The timed test** (`crates/engine/tests/it/native_speed.rs`, ignored): 300 moves and 100 fills on a drawing of 12,000 shapes opened from its `.vsdx` and from its `.diacraft`, in a process of its own for each run, the edits counted in microseconds of the thread's CPU, with the load beside each run and a yardstick in the same process. Run it by hand, alone, on a quiet machine: `cargo test -p diacraft-engine --test it -- --ignored an_edit_after_a_diacraft_open --nocapture --test-threads=1` (not nextest: it ends a test at 120 seconds). It holds the `.diacraft` side to 1.25 times the `.vsdx` side on the least of five runs of each.
- **What a test of many shapes or many files is made of**. A test that needs thousands of shapes makes them in one edit and does not drop them one command at a time: a `shape.drop` reads the page's list once for the containers it might fall into (one step for each shape of the page, `draw::container::arrive`), so a drop costs what the page holds (17 ms into a page of 20,000 shapes and 0.9 ms into one of 2,000, beast, 2026-11-26: `odgfile::tests::a_drop_costs_a_read_of_the_pages_list_so_it_follows_the_shapes_on_the_page`, ignored) and 3,000 drops into 20,000 shapes took a minute. The flattening of 3,000 new shapes in a drawing of 20,000 is counted in steps instead (286,001 of the 6,000,000 the cap allows: two for each shape of the file, 82 for each new one and one for their master), and its timed twin is ignored. The two sweeps of chains of saves (`resave_sweep::chains_keep_the_rule` and `save_check_before::a_dry_run_before_each_save_changes_none_of_them`) run 100 and 60 chains of a fixed seed and **count what the chains cover** (`assert_covers`: every start, every type of Save As, every edit and every option appears in them), because each chain writes about three files and reads each back: 400 chains took 17 seconds of CPU, and a machine that gave the process a seventh of a core ran the test past the 120 seconds nextest allows. The 400 and the 150 chains they ran before are ignored tests (`the_old_four_hundred_chains_keep_the_rule`, `a_dry_run_before_each_save_changes_none_of_them_over_the_old_150_chains`). The grid of `drop_resave` (9 drawings by 4 types by 4 options by 2 shapes, 288 chains) is nine tests, one for each drawing, of 32 chains at the most (`edit_grid_tests!`), and the whole grid is an ignored test. **The time of these tests is the disk's, and not the engine's**: the grid in one test took 44 to 100 seconds alone on a busy machine for 7 seconds of CPU, the threads of its saves made no difference (`DIACRAFT_THREADS=1` took as long), a sample of its threads found them waiting in the file system's commits (btrfs's `wait_log_commit` and `barrier_all_devices`: a save writes a file and renames it over the old one), and the same test with its files on a RAM disk took 9 seconds. So a test of many saves is bounded by the count of the files it writes, never by a time, and the gate's scratch folder (`TMPDIR`) belongs on a disk that other builds are not writing to when the gate runs at a load. A script of the packages that looks a name up in a list does not pipe the list into `grep -q`: under `pipefail` a `grep -q` that has found its name leaves the pipe while the writer still writes, and the pipeline fails (`packaging/linux/make-rpm.sh`, `xtask/tests/it/packaging_rpm.rs`).
- **The kept routing scene** (`crates/engine/src/draw/route_scene/tests/`). `Scene::reads()` counts what the scene read since it was made: top-level pointers walked, shapes looked at, shapes whose kind was told by four cells, `Connect` rows passed, route rows read and pages read whole. A page of 10,000 shapes and 10,000 connectors costs, by those counts and by the steps charged to the edit's `Work`: 20,000 pointers, 20,000 shapes, 10,000 routes (30,000 rows) and 40,000 rows of glue the first time; **one shape and one walk of the pointers for a move** (no connector, no row of any route, no `Connect` row, and the model's own `rows_merged` count at 0, the readers' count of poses at 8 or fewer); one connector and its rows for a change of its own cell; one pass over the `Connect` rows and one shape for a new connector; and every shape again only for a change of the page's sheet, a style or a master. 30,000 shapes read 10,000 and cost a compare for the other 20,000 (`peeks`), a group of 20,000 members is read to the cap, and a chain of 150 groups down to 8 levels. `a_scene_put_right_equals_a_fresh_one` (300 random sequences of up to 40 edits of a session, **from a fixed seed**, so that the gate runs the same sequences every time and the counts of what worked are the same every time: a seed taken from the clock made the redos that worked 16 to 43 of the 20 the test asked for, and it failed in 3 of 8 runs of one build and 1 of 8 of another; `ROUTE_SCENE_SEED` and `ROUTE_SCENE_CASES` make another or a longer run by hand, and then the counts are not held; the edits are undo, redo, save and reopen in each format, duplicate, group, ungroup, a change of a master's cell and of the page's clearance, a cell made to read another shape's (`Sheet.2!PinX`), a group added whose member repeats the `ID` of a shape that is there, and a put right given too little work) holds the scene put right to a scene read whole and to an oracle that works the obstacles, glue and legs out with readers the scene does not use (the first shape of an `ID` holds it, an obstacle or not), and what each put right that is complete reports to a model of the boxes the scene was settled on, kept apart from the scene's own table. A put right that stops, for work that ran out or for the retry a repeated `ID` asks for, puts the candidates back as the last complete one left them, so that the next reports from the same boxes however many stops came between (`route_scene::tests::diff`); a group's members are charged to the work before each is read, so that a put right with one step left for them reads one (`a_wide_group_is_not_read_past_the_work_the_put_right_has_left`); and `route_scene::tests::links` holds that a shape whose cell reads another shape's is read again, and reported, when that one moves. The prices of the charge are pinned by count (`each_price_is_pinned_and_they_add_up`) and measured by hand (`cargo nextest run -p diacraft-engine --lib --run-ignored only --no-capture -E 'test(/route_scene::tests::memory::(measure_|a_scene_is_charged)/)'`); a scene at the caps is built in a child under `ulimit -v 3000000`. The times are ignored tests beside a yardstick (`route_scene::tests::timed`).

## Threads in the renderer

`DIACRAFT_THREADS` (a whole number, cut to 1 and 64) sets how many threads the window, the PNG export and the thumbnail of a saved file draw a frame on (`diacraft_render::default_threads`); unset, it is the machine's cores less one, and **1 is the old single-threaded way**. The web build always draws on one. `Renderer` draws on one thread until `set_parallel` is called, so no test or tool changes without saying so.

- **The same bytes at any count** (`crates/render/tests/it/par.rs`): each scene is drawn at one thread and at 2, 7 and 31, with `Parallel::eager` (no floor, so a small page is shared out), and the pixels and the list of what was left out are equal; and **`Renderer::par_stats` says the frame was drawn on threads** (a count of shares walked, walks done in order, frames drawn in bands), since a test that drew on one thread every time would pass for ever. The scenes are the 2,130-shape page (with and without shadows), a generated page of gradients, hatches, dashes, turned shapes, arrowheads, groups, text and shadows on four seeds, whole, zoomed and seen turned and sheared, odd frame sizes, a column of blurred shadows and text with a band edge across each, clips and pictures, background pages, a print sheet in colour and in greys, a newer request that stops a frame, and the budgets that send a frame to one thread. Unit tests of the recording, the bands and the tally are in `record.rs`, `par.rs` and `share.rs`, and the faults (a panic in a band, a panic in a share) in `fault.rs`.
- **The threads hold no more between them than one thread does.** Counted: `ParStats::share_shapes` (the shares of a page that passes a budget stop together), `most_band_threads` (the pixels of the bands' contexts and of their blur layers fit `Parallel::scratch_bytes` and `Parallel::blur_pixels`), `walked_shapes` (a frame whose recordings pass `Parallel::max_steps` is walked once). In a child under `ulimit -v` (`memory.rs`, the pattern of the blur tests there; 52 GB for a child on threads, which the address-space rule leaves room for 31 threads in): `RENDER_MEMORY_THREADS=31` draws the scenario on 31 threads and the frame may add what one thread's frame adds; `RENDER_MEMORY_UNBUDGETED=1` lifts the two budgets, to see what they save (the children abort).
- **The timings, by hand** (`crates/render/tests/it/par_bench.rs`, ignored): `BENCH_THREADS=1,4,16,31 [BENCH_SHADOWS=1] [BENCH_BIG=1] cargo test -p diacraft-render --release --test it par_bench -- --ignored --nocapture` prints the least of the frames at each count with the mean time of the walk and of the pixels. On the shared 32-thread machine run it with the load in view (`uptime`), more than once, and pin with `taskset` if it helps; profile in user space (`perf record -e cpu-clock:u -F 2000`).

## The picture of a saved file

The preview an `.odg` or a `.diacraft` save draws of the first page is held to `Limits::preview`: no time, and a budget of work charged before the work is done (`Limits::max_work`; the units are in `crates/render/src/limits.rs`), so the same drawing saves to the same bytes however loaded the machine is. A frame reads the time from the renderer's `Clock`, and `Clock::stepping` is a clock for which every deadline has passed by the time a frame looks.

- **The same bytes with every deadline passed** (`crates/engine/src/odgfile/save.rs`): a save made while the test's thread holds a stepping clock writes the file the machine's clock gives, for a plain drawing and for a hostile one cut by its work; `crates/render/tests/it/preview.rs` counts what each kind of work is charged (`Renderer::work_done`), cuts each kind with a budget a unit short of it, and draws the hostile pages (the same long text in hundreds of shapes, a page of shapes that show one big picture, a metafile of many items in each) to the same frame on two runs, with every deadline passed and on four threads.
- **The timed test** (`crates/engine/src/odgfile/preview_cost.rs`, ignored): `cargo test -p diacraft-engine --lib odgfile::preview_cost -- --ignored --nocapture --test-threads=1`, run alone, times the preview and the `.odg` save of five hostile drawings against a yardstick of twenty thousand boxes and holds each to six times the yardstick's CPU time; the last run (beast, load 21 to 23): the yardstick's preview 0.20 s wall (0.76 s of CPU on seven threads) and its save 4.8 s, the hostile previews 0.38 to 1.28 s and their saves 1.3 to 5.2 s, each cut by its work or a metafile's cap of items, and two saves of each the same file.

## Threads and the timing of a save

A save may use the machine's cores (see [`architecture.md`](architecture.md), Threads). **`DIACRAFT_THREADS=n`** sets the count for a run of the app, the CLI or a test: 1 is the single-threaded path, which makes no thread; unset, it is the cores less one, at least 1 and at most 64. It is read when a save begins; a test sets it for a child process (a test cannot set the environment of its own process). The renderer and an open take the count from the same function (above and below): `the_frame_the_save_and_the_open_read_diacraft_threads_alike` (`par_save.rs`) reads the three counts in a child process for each of twelve settings, and `under_an_address_limit_a_frame_and_a_save_are_held_by_the_rule_of_an_open` reads, in children under `ulimit -v` of 3 and 16 GB, that a frame and a save take the threads the rule gives (`diacraft_container::spare::threads_fit`).

- **The same bytes at any count.** `crates/engine/tests/it/par_save.rs` saves a drawing as `.vsdx`, as `.diacraft` and as `.diacraft` with large pictures in a child process at 1, 2, 7 and 31 threads and compares a digest of each file. The crates have the same test at their own level, with more cases: `crates/container/tests/it/par_write.rs` (`ArchiveWriter::add_many`), `crates/vsdx/tests/it/par_write.rs`, `crates/sheetxml/tests/it/model_save_threads.rs` (the parts made together, the blobs numbered by first use, a hold too small to keep a part) and `crates/native/tests/it/par_write.rs` (with a previous package to copy from, and under a meter that is not generous). A worker that panics is an error: `crates/container/src/par.rs`, `zipwrite.rs` and `crates/vsdx/src/write/par.rs` each have a test. **The lane starts no more workers than the tasks in flight need, under any schedule** (`par.rs`): its tests count the starts exactly, with no sleep and no retry: one task given and taken at a time is one worker over 200 rounds, a caller that keeps k tasks pending has at most k, a burst of tasks that all wait has one for each up to the count, and a worker held back as it starts (a test hook) is free, so no other is started for the task it will take.
- **The timed test** (`par_save_times`, ignored): a drawing of `PAR_SHAPES` shapes in `PAR_PAGES` pages saved as `PAR_FORMAT` (`vsdx`, `diacraft`, `odg` or `pictures`) `PAR_RUNS` times, printing the least, the machine's load before and after, and the size written. Run it in a release build, alone, one process for each count: `PAR_FORMAT=diacraft PAR_SHAPES=12000 DIACRAFT_THREADS=4 cargo test --release -p diacraft-engine --test it -- --ignored par_save_times --nocapture --test-threads=1`. `PAR_FRESH=1` opens the drawing again before each run, so that every run is a first save. The machine is shared: read the load beside the time.
- **The memory at 31 threads.** The tests that set `ulimit -v 3000000` in a child (`vsdx_save_peak.rs`: 69,000 shapes, 76,000 before a change priced a node of cells at the law of the memory tests; `vsdx_held_parts.rs`: two parts of 256 MiB; `native_memory.rs`) pass at `DIACRAFT_THREADS=31`, and their children print the peak beside the figure at 1 thread. `odg_memory.rs` saves 50,000 new shapes of an `.odg` asked for 31 threads, with the thumbnail drawn on threads before the save (it aborted when a frame took half of what the limit left).

## Threads and the timing of an open

A file opens on the machine's cores (see [`architecture.md`](architecture.md), Threads of an open). **`DIACRAFT_THREADS=n`** sets the count for a run of the app, the CLI or a test, 1 being the single-threaded path, which makes no thread; unset, it is the cores less one, at least 1 and at most 64. It is read when an open begins; a reader takes the count in its limits (`diacraft_vsdx::Limits::threads`, `diacraft_odg::Limits::threads`, `diacraft_native::Limits::threads`; 1 by default, so a test of a reader that sets nothing is the single-threaded read).

- **The same open at any count** (`crates/container/tests/it/par_read.rs`, `crates/opc`, `crates/vsdx`, `crates/odg` and `crates/native` `tests/it/par_read.rs`, `crates/engine/tests/it/par_open.rs`): each reader is run at 1, 2, 7 and 31 threads over generated drawings and the results compared whole (the document by value, the report, the error), over files with damaged entries, parts that are not XML, parts denser than a thread is given the room for, parts that two rows name, and a budget walked from too little to enough. The engine's test opens a file of each format in a process for each count and compares what `file.open` says and a hash of the document. A thread that panics is made to by a test-only mark in a part (`work.rs`, `test-support`) and must be an error in words; that test makes the read wait for the threads to parse the parts it asked them for (`work::wait_for_the_work_ahead`, on the read's own thread), since a read parses a part that no thread has begun itself, and on one core it came to the marked part first.
- **The trees in flight** (`vsdx` `par_read.rs`, `the_memory_the_threads_hold_is_never_more_than_the_budget_set_aside_for_it_whatever_the_read_abandons`): a test build tells the budget's door every time what is set aside changes, and counts every time the bytes of the trees in flight (parsed and not taken, handed over to be dropped and not dropped) are more than it; the test walks the budget over reads that abandon parts, are refused at each edge and end the work early, and holds the count at none. It fails on the three ways the bytes were once paid out too early (a charge that took the set-aside without waiting for the work, a tree handed over and given back at once, the end of an index that gave its set-aside back with trees in flight).
- **Children under an address limit** (`par_read_child` in `vsdx` and `hostile_child` in `container`, each run by a test in a process of its own under `ulimit -v 3000000`, as the capacity tests are): the largest drawing the VSDX budget admits and one it refuses end alike at 1 and at 31 threads and never abort, and entries that say they are 2 MiB and hold 200 MiB are refused alike in the address space of one thread and of the threads.
- **The timed test** (`crates/engine/tests/it/par_open.rs`, ignored): `PAR_FORMAT=vsdx|odg|diacraft|pictures PAR_SHAPES=12000 PAR_PAGES=40 DIACRAFT_THREADS=4 cargo test --release -p diacraft-engine --test it -- --ignored par_open_times --nocapture --test-threads=1`, one process for each count; it prints the least of `PAR_RUNS` (five) opens, the load before and after, and the address space and resident memory the process reached. `PAR_KEEP` names a folder that keeps the generated files, so that a profile (`perf record -e cycles:u`, which is all `kernel.perf_event_paranoid=2` allows) holds the open and not the making of the file; `par_open_stages` times the package read, the document read, the weight of the model and its drop. Run it alone: the machine's load moves the figures more than the threads do.

## The person's settings

**One store keeps everything the person sets** (the proofing and AutoCorrect options and lists, the editing languages, and the keys the translation, help and Options designs add), for the window, the command line and the MCP server: the crate `diacraft-prefs` (L0, standalone, below the engine so that its hostile-input parts have their own fuzz target; the engine re-exports it as `diacraft_engine::prefs`), on **craft-settings** (pinned with the other craft-libs crates). `config.toml` has a `[section]` for each area and `schema_version = 1` first; the dictionaries and AutoCorrect lists are files beside it.

| | Linux | macOS | Windows | The web |
|---|---|---|---|---|
| `config.toml` | `$XDG_CONFIG_HOME/diacraft/` or `~/.config/diacraft/` | `~/Library/Application Support/diacraft/` | `%APPDATA%\diacraft\` (roams) | the `localStorage` key `diacraft.config` (the same TOML text) |
| Custom dictionaries, AutoCorrect lists | `<config>/proofing/dictionaries/<name>.dic`, `<config>/proofing/autocorrect/<language>.tsv` | the same | the same | the keys `diacraft.proofing.dictionaries/<name>.dic` and `diacraft.proofing.autocorrect/<language>.tsv`; **all of DiaCraft's keys take at most 1 MiB** (names and values), and a write past that is refused in words with nothing changed |
| The log | `<config>/diacraft/logs/` | the same | the same | none |

- **Which folder** is craft-settings' rule, first match wins: `DIACRAFT_CONFIG_DIR` (the folder itself, and the log's `logs` folder in it), a file named `portable` next to the program (settings in `config/` beside it; next to the `.app` on macOS), then the platform's folder. **`DIACRAFT_NO_PREFS` set to anything (the empty text too), and a `DIACRAFT_CONFIG_DIR` that is set and empty, open the profile in memory**: nothing is read or written, the log has no file, and the run keeps its changes and its words until it ends. Every test is isolated this way or with a folder of its own, and none reads the real profile; a script or an agent that must not touch the person's settings sets one of the two.
- **What programs do.** A program changes the settings as the window does, in the same store, so that "add DiaCraft to the dictionary" lasts; `Profile::update` returns the keys it changed (`proofing.ignore_uppercase: true -> false`, read off the keys, so a key added later is named with no change to the store), and a word added or removed is merged into the file as it is then, under a lock, so two programs adding words at once keep both. A program that is the window's session shares the window's profile; `diacraft-cli run` and `mcp` (not `--connect`) open the same file with the engine's sections and keep the window's own keys as they are. `diacraft_engine::prefs::Prefs` is what a type of settings implements: the window's `WindowPrefs` holds the engine's sections and its own `[interface]`, and the designs that add keys (the interface language, the help's tips and search, the connection points' minimum distance) add fields there.
- **Hostile files.** `config.toml` is read only up to 1 MiB, and a file that is bigger, is not UTF-8 text, or has more than 256 top-level keys is moved aside unread (`config.broken-<time>.toml`, as a file that is not TOML is) and the defaults are used. Every list is capped and every entry checked (at most 32 dictionaries, each a plain file name, once, one the default; at most 1,000 exceptions of at most 64 characters; at most 32 editing languages, each a well-formed tag), the files beside `config.toml` are read by size first and never past 1,000,000 bytes (a dictionary) or 1 MiB (an AutoCorrect list), only if they are regular files, and written whole through `craft-atomic`; a name that is not a plain name, a word that is not one word of at most 64 characters, and a list past 100,000 words are refused in words. A file from a newer build is shown and never written over, a folder that cannot be written opens the profile read-only, and **none of it stops the app**: what was wrong is said once, in the status bar and in the log (the window) or on standard error (the command line), and the defaults or the file's values are used. `cargo fuzz run prefs_load` and `crates/prefs/tests/it/prefs_fuzz.rs` hold this to hostile input.
- **The first editing language** of a profile that has none is the system's (`sys-locale`; the browser's languages on the web), and is saved with the rest; a profile that has one keeps it. **A system that names no language** (`C`, `POSIX`, no language variable, a text that is no locale) gives none to save: the profile stays undecided (`language.editing` is empty in `config.toml`), the programs read `en-US` meanwhile (`LanguagePrefs::preferred`), and a later run under a real locale decides, so that a first run under `LANG=C` (a script, a container, a service) does not keep `en-US` for good.
- **A note on tests that start the program.** `apps/diacraft/tests/it/window.rs` sets `DIACRAFT_NO_PREFS`; a test that starts `diacraft-cli run` or `mcp` as a process must set it too, or it reads and writes the real profile. A test that starts the window and may see the start fail also sets `DIACRAFT_NO_ERROR_BOX` (see "The window's graphics adapter").

## The window's graphics adapter

On macOS and Windows the desktop window checks a graphics adapter before it draws on it (`apps/diacraft/src/graphics.rs`): a device made as the window will make it clears a small texture and reads it back, and an adapter that reads back anything else is passed over, with a warning in the log, for the next one (when none passes, that try ends with an error that says why each failed, and the start goes on to the next try, below). macOS prefers the power-saving GPU and turns wgpu's check of indirect draws off; Windows keeps eframe's high-performance preference and **puts DirectX 12 before Vulkan for the same kind of GPU** (`Rules::dx12_first`, after the name, hardware before software, OpenGL last and the power preference: a Windows machine's own graphics stack is tested before a Vulkan driver that may be installed and broken; a `WGPU_BACKEND` the person set keeps wgpu's order); Linux keeps eframe's choice and makes no probe. `WGPU_POWER_PREF` (`low`, `high`, `none`) sets the preference, `WGPU_ADAPTER_NAME` (a part of an adapter's name, in any case) puts that adapter first, and `WGPU_VALIDATION_INDIRECT_CALL=1` turns the check of indirect draws back on on macOS. Every adapter and the choice are logged. The tests are `apps/diacraft/tests/it/graphics.rs`.

**A test that never returns** (public issue #17: Intel UHD Graphics through Vulkan on a Windows 10 laptop ended 0.2.3 with a log that stopped after the list of adapters; a crash or a blocked driver call never returns an error, so the tries below cannot help). Four defences, in `graphics.rs` and `marker.rs`:
- **The log says which adapter is tested, first**: `testing <adapter> (try usual, test 1)`, and the log is flushed to the disk (`log::logger().flush()`, `fsync` on the file) before the driver is called, so a report shows where the start died, even when the machine went down.
- **A marker** in the settings folder (`graphics-testing.<process id>.txt` next to `logs`, `%AppData%\diacraft` on Windows), written and flushed before the test of an adapter and removed when the test returns. It names the adapter (its `Key`: name and back end) and DiaCraft's version, and is **locked** while the test runs (`File::try_lock`), so a start that finds one knows whether it is a start that is gone (the lock is free: the process died, or was ended while the driver hung) or one that is still running (locked: several drawings opened at once start several programs, each testing; it is not blamed). A run with `DIACRAFT_NO_PREFS` (or no settings folder) keeps no file.
- **The left-out list** (`graphics-left-out.txt`): the next start adds the adapter of a marker of a gone start of the same version to it (`the last start ended while testing <adapter>: it is left out`), and every try leaves out the adapters of the list (`graphics::Memory::excluded`; the log lists such an adapter as `left out`). It holds at most 16 adapters and lasts until DiaCraft's version changes (a newer build may have mended the driver) or the person starts `diacraft --reset-graphics`, which forgets it. A file that is too long, not text, of another version or not ours is ignored with a line in the log, and a folder that cannot be written is a line in the log: **nothing here stops a start**. When no adapter is left, the message box names the adapters left out and says how to test them again.
- **A hang is given up on**: each test runs on a thread of its own (`graphics::run_within`) and the start waits for it `PROBE_GIVE_UP` (12 s: the GPU's own 4 s wait does not cover a call that blocks making the device). A test that is still running by then is passed over, left out of every later try of the start and put in the list for the next, its thread left behind, and the choice goes on to the next adapter. A test that panics is a test that failed.

**A diagnostic for trying all this on a machine whose drivers work:** `DIACRAFT_GPU_PROBE_FAIL=<part of an adapter's name>:<abort|hang>` makes the test of that adapter end the process (`abort`, as a crashing driver does) or block for ever (`hang`). The part is looked for, in any case, in the adapter as the log writes it, `Intel(R) UHD Graphics (dx12)`: `UHD:abort` is every adapter of that name, `Intel(R) UHD Graphics (vulkan):hang` one of them; nothing else does anything. It is in `diacraft --help` and is never set by DiaCraft. On Linux the usual try makes no test, so a run that reaches one starts with `WGPU_BACKEND=" "` (the usual try then fails and the software try tests `llvmpipe`): `DIACRAFT_CONFIG_DIR=<an empty folder> DIACRAFT_NO_ERROR_BOX=1 WGPU_BACKEND=" " DIACRAFT_GPU_PROBE_FAIL=llvmpipe:abort diacraft` leaves the marker, the next `diacraft` leaves `llvmpipe` out, and `diacraft --reset-graphics` tests it again. `tests/it/graphics.rs` runs the test binary itself with `:abort` (Unix) and reads what the dead start left; `tests/it/marker.rs` holds the files' cases.

**A start that cannot make its window tries again, and then says so** (`apps/diacraft/src/fallback.rs` and `failure.rs`; a public report: the Windows Start menu entry did nothing, because the program is a GUI program with no console and the failure went to a standard error nobody could see). Whether the window opens depends on the machine (a virtual machine or a Remote Desktop session, an old or missing driver, a Vulkan driver that is installed and broken), so `main.rs` runs `eframe::run_native` once for each **try** (`fallback::Rung`), and a graphics error before the app was built (`step_of`: eframe's `Error::Wgpu`, which is what `Failed to create surface for any enabled backend` and a failed adapter choice are) goes on to the next, in the same process (eframe keeps its event loop for the next run, `run_and_return`; it was run twice on Wayland and on X11, and has not been run on Windows by the project). The tries: **Windows** the usual try, DirectX 12 alone, the software adapter (wgpu's fallback adapter, WARP; `Rules::SOFTWARE`), OpenGL alone, and last the first adapter that can show the window with no test of it (`Rules::UNTESTED`, the rule the window had before it had tries, for a machine where none passed the test); **macOS** the usual try and the untested adapter; **Linux** eframe's own choice, then the software adapter (llvmpipe, lavapipe) and OpenGL alone. The adapter the last try chose is remembered as failed (`graphics::Memory`) and the next leaves it out; every try and every failure is in the log (`graphics try 2 of 5: DirectX 12 only`), and the status bar says when the window was drawn by a try after the usual one. **`WGPU_BACKEND` is the person's choice and no try swaps it for another:** with it set to anything but blanks the tries are the usual one and, on macOS and Windows, the untested adapter of that back end (`WGPU_BACKEND=metal` on Windows, or `vulkan` with a `VK_ICD_FILENAMES` that names no file, ends in the box, whose text says the variable is set and that only it was tried); blanks are no choice (`WGPU_BACKEND=" "` makes the usual try fail as a back end with no adapter does, so the later tries can be seen on a machine whose graphics work). A panic ends the start at once, and an error of a window that was running is not retried.

**When every try fails** `failure::report` logs the failure once, writes one line to standard error (as it always did) and, where nothing would show that line, asks `dialogs::failure_box` for a message box: `rfd`'s message dialog (`MessageBoxW` on Windows, an alert on macOS, zenity on Linux, which shows nothing where it is missing). The box says in plain words that DiaCraft could not start (or stopped on an internal error), the reasons (one for each try, at most five, each cut to 240 characters), the full path of the log file (or that no log file is kept for the run), and what to try (update the graphics driver, or set `WGPU_BACKEND` to `dx12` or `gl`; the advice fits the system). **When the box is shown:** not when a terminal reads standard error, not with `--control` (a script reads the exit code and the log, and a box would hold it up), not with `DIACRAFT_NO_ERROR_BOX` set (any value) and not where there is no screen (Linux without `DISPLAY` or `WAYLAND_DISPLAY`); a mistake in the command line is boxed on Windows only, where nothing else would show it. Every early exit goes through it: the command line (exit code 1), a folder the control channel is kept to (2), the window (1) and a panic anywhere in the start (1), which `main` catches. The box goes through a hook (`report`'s `show`), so no test opens one; `tests/it/failure.rs` and `tests/it/fallback.rs` hold the text, the order of the tries, the choice of adapters (`choose`, with a fake probe), the climb and the hook, and start the program with no display. **A test or a script that starts the program as a process on a machine with a screen, and may see the start fail, sets `DIACRAFT_NO_ERROR_BOX=1`** (as it sets `DIACRAFT_NO_PREFS`), or a message box waits for a click.

## The language tables

`crates/doc/src/lang/lcid.rs`, `names.rs`, `quotes.rs` and `scripts.rs` are **generated and committed** (each starts with `// @generated` and names its sources, releases and licence; `rustfmt` skips them). They hold: the LCID numbers of the legacy XML paired with tags (`lang::from_lcid`, `to_lcid`, `known`: 432 numbers, 454 tags with their spellings, 427 tags a person can pick), the English names of languages, scripts, regions and variants with CLDR's own patterns (`english_name`), each language's quotation marks (`quotes`: 148 rows, a locale that says what its parent says is left out) and its likely script (`script_of_language`). The rules the generator applies to ICU's table are in the header of `lcid.rs` and in `xtask/src/langdata.rs`: a number is read as ICU reads it (the first subtable whose language ID is its low ten bits, the first row for it whose language CLDR names), a sort-order keyword is dropped (`1034` is `es-ES`), the root and the invariant locale are no languages, and a number past 16 bits is a sort order stacked on a language ID and so no pair.

**To regenerate** (a change of a pin in `PINS` of `xtask/src/langdata.rs`, or of the generator): read the new source's licence file first (it must say Unicode-3.0) and make two folders. For CLDR, unpack the release's JSON archive (`cldr-<release>-json-full.zip` of the `unicode-org/cldr-json` release, the one craft-i18n's `crates/i18n/data/generate.sh` keeps in its cache) into a new empty folder; the tool reads `LICENSE`, `cldr-core/package.json`, `cldr-core/supplemental/likelySubtags.json`, `cldr-localenames-full/main/en/` and `cldr-misc-full/main/*/delimiters.json`, so `unzip <zip> -d <dir> LICENSE cldr-core/package.json cldr-core/supplemental/likelySubtags.json 'cldr-localenames-full/main/en/*' 'cldr-misc-full/main/*/delimiters.json'` is enough. For ICU, put `icu4c/source/common/locmap.cpp` and `locmap.h` of the pinned tag and the repository's `LICENSE` into one folder. Then `cargo xtask langdata --cldr <cldr dir> --icu <icu dir> --i18n-source <craft-libs>/crates/i18n/data/source.txt` writes the files, and the same command with `--check` says whether the committed ones match. The ignored test `regenerating_from_the_real_sources_gives_the_committed_bytes` in `xtask/tests/it/langdata.rs` does the same with `LANGDATA_CLDR` and `LANGDATA_ICU` naming the folders (`cargo nextest run -p xtask --run-ignored only -E 'test(langdata)'`). The tests that need no download (the miniature sources of `xtask/tests/it/langdata.rs`, and the check that the committed headers name the generator's pins) run in the gate. Nothing is fetched at build or run time.
